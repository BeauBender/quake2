# FIX196: a TERM in the instant a poll exits no longer ends bench.sh before its stop

## What happened

A merge gate on main at `3812dba2` (FIX192, #728) failed `tests/check-bench.sh` in `t_core_id`, in
the lock-shell-TERM leg:

```
check-bench: core-id: lock shell TERM: the lock was freed while the bounded command it could not stop still ran: lock=free
check-bench: core-id: lock shell TERM: the release's hold was not said: ...: set: can't access tty; job control turned off|bench: this shell has no job control (set -m), so a stop reaches only the command's own pid|
check-bench: failed: t_core_id
```

## Reproduction

The leg was run alone (taken out of `t_core_id` into a scratch harness, the rest of the check
unchanged) under `/bin/sh`, bash 3.2.57, with the lock shell and the inner `bench.sh` in dash, as the
check runs them.

| run | failures |
|---|---|
| the leg as it is, on `3812dba2` | 0 of 44 |
| the leg with a clock read (one `perl` fork, about 5 ms) at the top of `bench_on_signal`, on `3812dba2` | 4 of 14 |
| the same, with the fix | 0 of 12 |

The clock read widens the window below; it changes nothing else. Every instrumented failure ended
the lock shell inside `bench_poll_end`: its log shows `bench_on_signal` entered and never left
`bench_poll_end`, then the release, with no stop of the inner `bench.sh`.

## Cause

`scripts/bench/core/common.sh`, `bench_poll_end` (line 362 on `3812dba2`): `kill -s TERM "$_pe_p"`,
a plain command. `scripts/bench/bench.sh` runs under `set -eu` (line 49), and `bench_on_signal`
(line 86) calls `bench_poll_end` as a plain command, so errexit applies to it.

The poll may have exited in the instant the signal came. The shell has then reaped it, though no
wait has collected it: bash reaps a child when it exits, and dash in its next wait for any child,
which is the `wait` the signal came in (or any foreground command before `bench_poll_end`). It keeps
the status for the wait, but the pid is gone, so the TERM fails (no such process), and errexit ends
the shell with status 1 before the stop. The EXIT trap then releases the lock.

- In the inner `bench.sh` (the card's failure): it exits without stopping or recording the bounded
  command it could not tell about (`bench_record_untold`), so the lock shell's stop of it ends at
  once, the lock shell exits 143 as wanted, and its release finds no record: the lock is freed while
  the bounded command runs, and the hold line is never printed.
- In the lock shell (the instrumented failures): it exits 1 without stopping the inner `bench.sh`,
  frees the lock, and the inner runs on.

The callers of `bench_deferred` (pins.sh, ios-sim.sh, ios-device.sh) call it in an `if`, where
errexit does not apply, so only bench.sh was affected. A TERM in the trap's later steps is guarded
already (`bench_signal_group`'s `kill ... || return 1`).

## Fix

`bench_poll_end` gives the TERM `|| :`: a TERM that fails means the poll has exited already, and the
`wait` after it collects it as before. So the trap always reaches its stop, and the lock is released
only after the stop has finished, and, for a command it could not tell about, only once that command
is gone (the hold of FIX184).

## The staged case

`tests/check-bench.sh` `t_poll_end_reaped`: a `set -eu` shell sources `core/common.sh`, traps TERM
with a function that calls `bench_poll_end` as a plain command and then prints `the stop ran` and
exits 143, as `bench_on_signal` does. `BENCH_POLL_PID` is a `true` job, and the shell signals itself
only once `kill -0` fails for that pid (reaped, not collected), so the case has no race. It runs in
dash, `/bin/bash` 3.2.57 and `/bin/sh`.

| tree | dash | bash 3.2 | sh |
|---|---|---|---|
| `3812dba2` | exit 1, no output | exit 1, no output | exit 1, no output |
| this branch | exit 143, `the stop ran` | exit 143, `the stop ran` | exit 143, `the stop ran` |

The mutant `poll-end-kill-fails` takes the `|| :` off again, and `t_poll_end_reaped` catches it.
