# FIX156: a server's alias or bind runs as the server's text, whoever runs it

FIX151 ([its runbook](FIX151.md)) made the commands that refuse a server's use read
`Cbuf_ExecutingServerText()`, which is true while `Cbuf_Execute` runs a line that holds a byte a
server sent (FIX113's tag, [its runbook](FIX113.md)). FIX153 ([its runbook](FIX153.md)) closed the
`nextserver` way around it. This card closes the two that remain: a server, or a demo, defines
`alias x "<gated command>"` or `bind <key> "<gated command>"`, and the body runs later from the
player's text, a key press, or the console's `d1`, as the player's. Running console commands from
a server or a demo stays by design (CLAUDE.md, "Security-relevant boundaries").

FIX148 ([its runbook](FIX148.md), section 3) left a server's aliases out of the threat model,
because each later run starts from a player action. This card takes the other view: the player
picks when the body runs, the server picked what it runs, and a gated command refuses what the
server picked.

## The property

A body that a server-tagged line wrote, as an alias or a bind, runs as server text whenever it
is expanded, so `Cbuf_ExecutingServerText()` is true while it runs. That holds until the
player's text defines that alias or binds that key again. It carries through nesting: a player
alias that names a server alias runs the server's body as server text, and an alias that a
server's body defines is the server's.

One refinement keeps a server from taking over what the player already has. For an alias, a
server line that writes the body the alias already holds leaves its owner as it was, so a server
that runs `exec autoexec.cfg` again leaves the player's aliases the player's. For a key the rule
is stronger: **a server write never removes or replaces, in what is saved, a binding the player's
own text wrote**, and a server line that runs the player's `config.cfg`, its leading `unbindall`
included, leaves every key the player's and the next `config.cfg` the same as before. Each key
keeps the player's own last binding apart, and a server line that writes that binding gives the
key back to the player (Binds, below). The body is the player's choice either way, so nothing of
the server's gets through.

Round 1 compared a server's bind with the binding the key held at that moment. That fails for
`config.cfg`, which starts with `unbindall` when `cfg_unbindall` is 1 (the default). The server's
line ran the `unbindall` first and cleared every key to `""` as the server's, so each `bind` line
after it was compared with `""`. Every key became the server's, and the next `config.cfg` had no
bind line at all (round-1 review B1, I2). Two server lines do this:

- `exec config.cfg`;
- `game <dir>` on a remote client: the cvar change runs `FS_BuildGameSpecificSearchPath`, whose
  `Qcommon_ExecConfigs` queues `exec default.cfg` and `exec config.cfg` inside that line, so both
  run as the server's text.

## Aliases

`cmdalias_t` is private to `src/common/cmdparser.c`; it takes a `server` field. `Cmd_Alias_f`
sets it from `Cbuf_ExecutingServerText()` when it writes the body (with the refinement above).
`Cmd_ExecuteString`, the one place an alias is expanded, inserts a server alias's body with the
buffer's source set to `CBUF_SERVER` for the insert, and restores it after; a player alias's body
is inserted with the source of the line that names it, as before, so a server line that names a
player alias still queues server text. `Cbuf_InsertText` keeps the source of the text queued
behind the body, so the player's text on the same line or after it stays the player's.

Aliases are not written to `config.cfg`: `CL_WriteConfiguration` (`src/client/cl_main.c`) writes
`Key_WriteBindings` and `Cvar_WriteVariables`, and the latter writes only `set` lines for archived
cvars (`src/common/cvar.c`). There is no other writer. So an alias has no round trip to close.

## Binds

### The decision: a key bound by a server runs its binding as the server's

Pressing the key is not taken as the player's choice of the body. Three reasons:

- **The press picks when, not what.** A server can bind any key the player presses anyway (a
  movement key, the fire button), so a press is no sign that the player chose the command.
- **It matches aliases.** A bind and an alias are the same thing, a stored body run later by the
  player. A bind that names a server alias already runs it as server text through the alias
  path; tagging the bind itself makes the two agree.
- **Nothing that works today stops.** Only the commands that read `Cbuf_ExecutingServerText()`
  notice. `+attack`, `impulse`, `say`, `cmd ...` and the rest run as before. A server bind
  refused outright (the other choice) would break every server and mod that stufftexts a bind,
  which the project's no-breaking-changes rule forbids.

The bindings and who wrote them live in `src/client/keybind.c`, moved out of `cl_keyboard.c` so
that the unit suite links them. The file needs no SDL, no menu and no key name table but
`Key_KeynumToString`. It holds three arrays:

- `keybindings[]`, unchanged, as are its readers in the menu, the inventory and the input probe;
- `keybindserver[]`, the owner: true if a server line wrote the binding;
- `keybindplayer[]`, the player's own last binding of each key, written only by the player's text.

`Key_SetBinding` is the one writer, which `bind`, `unbind`, `unbindall`, the menu's unbind and
iOS's default pad binds all go through. From the player's text it writes the binding, the
player's saved binding, and the player as owner. From a server's text it writes the binding, and
the server as owner unless the binding equals the player's saved one, in which case the key is
the player's again. A key the player never bound counts as saved empty. The player's `unbind`,
`unbindall` and the menu's unbind clear the saved binding too; a server's do not. `Key_Event`
queues the binding through `Key_AddBindingText`, which uses `Cbuf_AddServerText` for a server's
binding, on the press and on the release of a `+` command. `Key_FreeBindings`, which
`Key_Shutdown` calls, frees both bodies and clears the owner.

So after a server line runs `config.cfg`, the `unbindall` makes every key the server's with `""`.
Each `bind` line after it writes the player's saved binding, which gives that key back. A key the
player had cleared is saved as `""`, so the `unbindall`'s `""` already gives it back. That holds
with `cfg_unbindall` 1 and with 0. On the `game <dir>` route, `default.cfg` runs first and
`config.cfg` puts every key back. One case stays the server's with `cfg_unbindall` 0: a key that
`default.cfg` binds and the player had cleared, since that `config.cfg` cannot clear it again. It
then keeps `default.cfg`'s binding until the player binds it, and that binding is not saved. That
is the same binding the stock code gave it, and the next start gives it again.

### The `config.cfg` round trip: only the player's bindings are written

`Key_WriteBindings` writes `config.cfg`, which the next start runs as the player's text: its
`unbindall` line, then `Key_WriteBindingLines`, which writes each key's saved player binding and
never the live one. A server's binding lasts for the session and does not come back as the
player's. A server that binds over a player's key does not lose the player's binding either:
`config.cfg` still saves it, and the next start has it back. Refusing `bind` from server text
would also close the round trip, but would break servers that bind keys (above). Binding a key
again from the console or the menu makes it the player's and saves it.

### Bounds

A server's `bind "<0x80>" x` reached `Key_SetBinding(-128, …)`: `char` is signed on arm64, and
`Key_StringToKeynum` returned `str[0]`, with only -1 refused. That read, freed and wrote
`keybindings[-128]`, before this card, and round 1 added a write to `keybindserver[-128]`
(round-1 review I1). Now:

- `Key_StringToKeynum` returns a single byte as `unsigned char`, 1 to 255, all below `K_LAST`;
- `Key_SetBinding`, `Key_BindingIsServer`, `Key_AddBindingText`, `bind`, `unbind` and `Key_Event`
  refuse a key number below 0 or from `K_LAST` up;
- the writer and `unbindall` loop over `0` to `K_LAST - 1` only.

### How the tests guard the bind half

`tests/unit/test_keybind.c` links the real `keybind.c` (the Makefile's unit-test object list;
`tests/unit/stub_client_full.c` gives `Key_KeynumToString` for printable keys). Lines run through
the real `Cbuf_Execute` and `exec`; `unbindall` is the real `Key_UnbindAll`. `bind` and `unbind`
are stand-ins for `Key_Bind_f` and `Key_Unbind_f`, which `cl_keyboard.c` keeps with the key name
table: they join the arguments as `Key_Bind_f` does and call the same `Key_SetBinding`. A press is
`Key_Event`'s path for a plain binding, through the real `Key_AddBindingText`. "Saved" is the real
`Key_WriteBindingLines` output.

every run, so a refusal is shown to be the gate's and not a body that never ran. Server lines go

## Out of scope

Carded separately:

- a downloaded `.cfg` (`CL_DownloadFilter` accepts it) that the next start runs as the player's
  text, its binds and aliases with it;
- `vstr` and `$` expansion of a cvar a server set, run from the player's alias or bind as the
  player's (FIX158);
- `bindlist`, `bind <key>` and the menu do not show which keys are bound by the server.
