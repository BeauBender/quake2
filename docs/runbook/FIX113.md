# FIX113: server text in the command buffer does not outlive its connection

A server's `svc_stufftext` goes into the command buffer (`src/common/cmdparser.c`) with the
player's own text. When a line of that text drops the connection (`disconnect` raises
`Com_Error(ERR_DROP)`, which runs `CL_Drop` and `CL_Disconnect`), the rest of the buffer was kept
and ran on the next frame, with the client disconnected. A command that refuses to run while
connected, so that a server cannot start it, ran anyway. Running console commands from a server
is by design and stays; only the ordering past the end of the connection is closed.

## The design

Each byte of the command buffer (and of the defer buffer a map change parks it in) records where
it came from: the server or the player. This is the "tag buffer text by source" candidate. The
other two were rejected:

- Recording how much of the buffer is the server's, as one range, does not hold: `exec` and
  `alias` insert at the front, the player's key bindings append at the end between two server
  packets, and the server's text can then sit in more than one place. A list of ranges, kept
  through every insert and every line taken off, is the per-byte record with more code.
- A separate buffer for the server's text changes the order in which server and player text run
  (today they run in the order they arrived), and the text a server line queues through `alias`
  or `exec` would land in the player's buffer.

The record is an array of one byte per buffer byte (`cmd_text_src`, `defer_text_src`), moved
with the text by the same `memmove` and `memcpy` calls:

- `Cbuf_AddServerText`, called by `svc_stufftext` in `src/client/cl_parse.c`, appends the text
  marked as the server's. `Cbuf_AddText` marks with the current source, which is the player's
  except while a server line runs.
- `Cbuf_Execute` treats a line with any server byte in it as the server's, and runs it with the
  current source set to the server, so the text that line queues (an alias it expands, a file it
  execs) is the server's too. A nested `Cbuf_Execute` inside a server line stays the server's.
- `Cbuf_DropServerText` removes the server's bytes from both buffers, keeping the player's in
  their order, and resets the current source to the player's (a server line that dropped the
  connection through `Com_Error` never returns to restore it).
- `CL_Disconnect` (`src/client/cl_network.c`) calls it first, before its early return when
  already disconnected. Every way a connection ends passes there: the `disconnect` command (via
  `Com_Error(ERR_DROP)` and `CL_Drop`), any other `ERR_DROP`, the server's `svc_disconnect`
  (`ERR_DISCONNECT`, then `CL_Drop`), a connection timeout, `connect`, `reconnect` from an
  active state, a local `map` (`SV_InitGame` calls `CL_Drop`) and `quit`.

Nothing in the protocol, the savegame format or a module API changes. A map change on a
connected client (`changing`, then `reconnect` while `ca_connected`) does not pass through
`CL_Disconnect`, so the server's text queued around it still runs, as before.

What a player types or binds is the player's, even when the server defined the alias or the
binding it runs: the player chose to run it.

## Commands that gate on the connection state

Found with `git grep -n "cls.state\|CL_UpscaleAllowed\|Com_ServerState()"` over `src/client`,
`src/common`, `src/server` and `src/backends`, keeping the functions a `Cmd_AddCommand` registers.
"Before" is what a server could get by queuing the command behind a `disconnect` in its text;
"after" is what it gets now. Commands a player types behave as before in both columns.

| Command | Gate | Before | After |
| --- | --- | --- | --- |
| `upscale_textures` (`cl_upscale_cmd.c`) | refused while connected to a remote server or while a demo plays (`CL_UpscaleAllowed`) | ran after the drop, with the client disconnected: the gate was bypassed | dropped with the rest of the server's text; does not run |
| `cmd` (`CL_ForwardToServer_f`) | needs a connection | after the drop it printed "not connected" | does not run |
| `rcon` (`CL_Rcon_f`) | uses the connection's address when connected, else `rcon_address` | after the drop it sent to `rcon_address` | does not run |
| `record` (`CL_Record_f`) | needs `ca_active` | after the drop it refused | does not run |
| `timerefresh` (`SCR_TimeRefresh_f`) | needs `ca_active` | after the drop it refused | does not run |
| `togglechat` (`Con_ToggleChat_f`) | chat only when `ca_active` | after the drop it toggled the console instead | does not run |
| `toggleconsole` (`Con_ToggleConsole_f`) | when disconnected it opens the console and shows the demo loop's state | after the drop it ran in the disconnected branch | does not run |
| `pause` (`CL_Pause_f`) | only with a local single-player server | after the drop it refused (the server is gone) | does not run |
| `connect` (`CL_Connect_f`) | kills a running local server first | after the drop it connected, from the disconnected state | does not run |
| `reconnect` (`CL_Reconnect_f`) | `new` when connected, a fresh connect otherwise | after the drop it reconnected to the last server | does not run |
| `changing` (`CL_Changing_f`) | sets `ca_connected` | after the drop it set `ca_connected` with no connection | does not run |
| `menu_savegame` (`M_Menu_SaveGame_f`) | only with a local server | after the drop it refused | does not run |

Only `upscale_textures` refuses while connected so that a server cannot start it; it is the one
the ordering defeated. The others either refuse while disconnected (so the drop made them refuse)
or act on the disconnected state; none of them now runs from text the server queued before it
dropped the connection.
