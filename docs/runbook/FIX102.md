# A pin record's capture stall stays out of the timedemo clock (FIX102)

FIX102 follows [FIX96](FIX96.md), which found that 5120 x 2880 records with `r_metalfx 2` differ
because `refdef_t.time` differs on the frames after a capture. The harness is
[doc/100_renderpins.md](../../doc/100_renderpins.md) (its *Determinism* section).

## The cause and the fix

In a timedemo every client frame plays the next demo frame, and the clamp in `CL_ParseFrame` and
`CL_AddEntities` puts the client time one server frame (100 ms) behind the server's. Only a step of
100 ms or more escapes the clamp: the time then follows the host. In a pin record at 5K that step is
the frame after a capture. `CL_ClockStep` (`src/client/cl_entities.c`, called from `CL_Frame`) cuts
the step to 99 ms when `timedemo` is set and a pin capture runs (`CL_PinsCapture() > 0`); the time of
every frame that brings a server frame is then one server frame behind it, from the demo alone.
Anywhere else the step is the host's time, as before. The fix is commit `ccc46a70`; the base is main
at `9a0d5948`.

## Runs

The bare-metal host, the screen unlocked for every run (`ioreg` 0), one-minute load 1.6 to 3.6.
`PINS_SEED=1`, `water.dm2` (FIX81's), `PINS_EVERY=30`, `ref_metal`; the 5K cases at 2560 x 1440 with
`PINS_HIDPI=1`. Scratch scenarios `h1fx2` and `h0fx2` are `rt-water.cfg` plus `r_rt_water_hits` 1 or
0 and `r_metalfx 2`, as FIX96's. Frames are compared byte for byte (`cmp`), each pair of records.

### The stall

From the engine's own log: `host_speeds 1` on the base build, and a scratch probe build (the fix
plus one print a frame of the raw step, the client time and the server time; never committed).
The step of the frame after each capture (frames 40, 70, 100 and 129 of 148):

| Size | Records | Step after a capture | First capture (frame 10) |
|---|---|---|---|
| 5120 x 2880 | 2 (probe) | 66.9 to 103.4 ms | 170.4 and 221.0 ms |
| 5120 x 2880 | 1 (`host_speeds`, base) | 63 to 92 ms (frame time) | 209 ms |
| 1920 x 1080 | 1 (probe), 1 (`host_speeds`, base) | 39.0 ms, then under 30 ms | 83.5 ms, 89 ms |

Every other frame takes 16 to 17 ms. So at 5K the first capture always passes 100 ms, and the
later ones do in some runs; at 1920 x 1080 none does. With the fix, every frame from 9 to 146 is
one server frame behind (probe). Frames 1 to 8 (the demo's start, before the first capture) and
147 to 148 (after the demo's end, with no new server frame) still follow the host.

Its `// nondeterministic` note stays: a comment line is part of a scenario's pin id, and removing
it would orphan every stored `skywater` reference.

### Every other pin

Every committed scenario (25) recorded once on `metal` at its defaults (`demo1.dm2`, 640 x 480,
`PINS_EVERY=30`; `cinematic` from `idlog.cin`), `PINS_SEED=1`, by the base build and by the fix
build in the same hold: every frame of every scenario is byte-identical (23 of 23 frames, `cinematic`
3 of 3). No record stalls past 100 ms at that size, so the fix does not act there.

## No change outside a pin record

`CL_ClockStep` returns `timedelta / 1000`, the old expression, unless `timedemo` is set and a pin
capture runs. The unit tests in `tests/unit/test_cl_entities.c` (`cl_clock_*`) pin it: the host's
step with no record, timedemo or not, and with a capture but no timedemo; the cut only in a
record's timedemo; and a stalled record frame given the time of a frame that did not stall.

## Not covered

- TASK168's no-scaler 5K records at `PINS_EVERY=1` (issue comment) were not repeated: each is about
  5 GB of frames. Its middle frame fits this cause; its last frame does not: the last frames come
  after the demo's end, with no new server frame, so the clamp does not act and the step is the
  host's (frames 147 and 148 above). A fixed step there is a follow-up.
- The unit tests were not run red before the fix (the function did not exist on main).
