# FIX172: the bench lock signals only its own command, or that command's process group

## What was wrong

The bench lock (`scripts/bench/core/`) runs every gate, every pins run and every `heavy.sh` hold. Its
command is started by `bench_spawn` as the leader of a process group of its own. FIX171's audit found
that the core knew that command only by its PID:

- `bench_watch` polled `kill -0` and `ps -o stat=`. If the command exited and its PID was given to
  another process within one nap (up to 1 s), the lock shell went on watching that process.
- `bench_signal_group` sent the signal to `-pid`, and when that failed (no such group) to the bare PID.
  `bench_stop_group` sends TERM, CONT and KILL that way, and `bench_lock_stop_child` and
  `bench_on_signal` call it. So a TERM to the lock shell, or a stopped stranger in the watched PID, could
  end in a signal to a process the lock never started.
- `bench_end_group` stopped whatever process group had the command's PID as its id once the command
  had been reaped.

`/bin/sh` here is bash, which collects an exited child from its SIGCHLD handler at once, so the PID is
free for reuse as soon as the command exits (FIX171).

## The fix

All in `scripts/bench/core/common.sh`. One rule, FIX171's and FIX177's: the identity is the start time
(`ps -o lstart=`, which exec does not change), in one form; liveness comes from `kill -0`; a PID that
answers `kill -0` while `ps` gives no answer is "cannot tell", never gone, and gets no signal.

- `bench_proc_read <pid> [<field>]` reads one `ps` line: a field (`stat` by default) and the start time,
  its words one blank apart (`ps` pads it, and puts two blanks before a day of one digit). Every start
  time the core compares comes from it.
- `bench_proc_same <pid> <start>` is 0 while the PID is still the process with that start time (a
  zombie too), 1 when the PID is gone, 3 when another process has it, 2 when the shell cannot tell.
- **Identity at spawn.** `bench_spawn` calls `bench_spawn_id`, which records `BENCH_SPAWN_START` (the
  start time; `-` when the command has already gone, `?` when `ps` gave no answer in three tries 0.1 s
  apart) and `BENCH_SPAWN_GROUP` (the PID when the command leads its own group, `-` when not). Each
  spawn appends `;<pid>|<group>|<start>` to `BENCH_SPAWNED`, and `bench_spawned <pid>` reads the latest
  entry. The watch and the stops read a PID's identity there and nowhere else, so a PID this shell did
  not spawn is never signalled. Callers, `bench.sh`'s `bench_on_signal` included, are unchanged.
- **Identity on watch.** `bench_watch` takes another start time on the PID as the command gone (0). A
  PID it cannot tell about is said once on standard error and polled on: the watch neither signals nor
  reports a stop then, and its end time still applies.
- **No signal to a stranger.** `bench_signal_group` returns 0 when it sent the signal, 1 when nothing of
  the command is left to signal, and 2 when it cannot tell, and then it sends nothing.
  - A command that led its own group at spawn is signalled as a group only, never by its bare PID. The
    group signal goes while the PID is still the command, or while no process has the PID: the system
    gives no new process the id of a process group that still has a member. When another process has
    the PID, the command's group is gone, so nothing is sent.
  - A command that led no group (a shell without job control) is signalled by its PID alone, only while
    the PID is still the command, and never once it has been reaped (`group`).
- `bench_stop_group` stops at the first signal that has nothing to reach, and sends nothing more. When
  it cannot tell, at the TERM or at the KILL, it says so (`bench_untold`) and returns without reaping,
  since a wait for a command that still runs, stopped, would not return.
- `bench_group_alive` (the stop's wait) and `bench_end_group` (the end of what a command left running)
  treat a group whose id's PID another process has as not the command's, so they wait for it and stop
  it no more.
- The two notes go to the caller's standard error through fd 8 (`} 8>&2 2> /dev/null`). The rest of the
  watch and the stop keep standard error on `/dev/null`, as before (the shell's job notices). The
  short commands they run (`ps`, `date`, the nap's `sleep`) inherit fd 8, as they already inherit
  standard output. If the lock shell is KILLed in a nap, the `sleep` can hold the caller's standard error
  open for up to one nap (1 s) more.
- `bench_lock_stop_child` (`scripts/bench/core/lock.sh`) is unchanged but for its comment: it calls
  `bench_stop_group` with the lock child's PID, and the identity comes from `BENCH_SPAWNED`.

What is left: a group signal after the command was reaped could still reach a stranger's group in one
case. The command's group must have emptied, its PID must have gone to a new process that made itself a
group leader, and that process must have exited and left members behind. The core does not try to
identify a group with no leader.

## The disposition probe

`t_core_id`, in `tests/check-bench.sh`, sources the core in a subshell. `kill` is wrapped there to note
every signal it sends but `-0`, and then to send it, since every process in the case is the check's own.
Its decoys (`core_decoy`) are shells that lead their own process group, with a `sleep` in it. Each is
started as `bench_spawn` starts a command, from a subshell that exits at once, so it is no child of the
check, as a process that took a reused PID would not be. Each ends by itself within 30 s, and the case
KILLs them at its end only while they still have their recorded identity (`listed_same`). The case puts
a decoy in the command's slot by writing `BENCH_SPAWNED` itself:

| case | slot | what must happen |
| --- | --- | --- |
| own | the command `bench_spawn` started, whose sleep is in its group | identity as `ps` reads it; seen running past its end (1); `bench_lock_stop_child` stops the command and its group member with a TERM to `-pid`, and no signal goes to the bare PID |
| other | the decoy, with PID 1's start time | the watch says gone (0) at once; no signal from `bench_stop_group`, `bench_end_group` (status 0), or `bench_lock_stop_child` |
| other, no group | the same, recorded as leading no group | no signal |
| no group, reaped | its own start time, no group, `group` mode | no signal, and `bench_end_group` stops nothing |
| never spawned | nothing in `BENCH_SPAWNED` | no signal |
| none | no start time read (`?`) | the watch says "cannot tell" and returns 1 at its end; the stop says so, sends nothing, and returns well inside its 5 s grace |
| nops | its own start time, `ps` failing | the same |
| bare | a second decoy, its own start time, no group | TERM to its PID alone; it is gone, and the sleep in its group still runs |
| deaf | a third decoy, which ignores TERM, as a group; `ps` goes silent once the TERM is out | TERM to `-pid`, no KILL, and the stop says it cannot tell |

The first decoy and its member must still run after all the cases that send nothing.

The real command is still stopped on TERM and on INT: `t_lock_stop` sends TERM to the lock shell and
INT to its group, and `t_bounded` stops commands past their wall time and stopped ones. Both pass
unchanged.
