# FIX152: is the `retro-filter` pin reproducible?

TASK197 recorded `retro-filter` on its branch and on `7550c9bc` (TASK185's head, the same filter code) and saw
frame 12 of 23 differ. This card measured whether that is the code or a nondeterministic frame.

## Method

`retro` and `retro-filter`, Metal, seeded (`PINS_SEED=1`), 640 x 480, `demo1.dm2`, 23 frames, recorded with
`scripts/pins.sh record metal <scenario>` into a fresh store per run. Builds: the head of this branch
(`2d176b7f`) and a `git archive` copy of `7550c9bc`, both `make client game ref_metal ref_soft`. Two holds
of the heavy lock: hold 1 was three rounds of base then branch (12 runs, the card's table); hold 2 was three more
rounds in the opposite order, branch then base (12 more runs, to see whether the order or a first run matters).
Frames were hashed (`shasum` of each TGA) and never viewed.

The tables hold 4 odd runs with 2 distinct run hashes (`065cfd5ceed3`, `5bbafb4d2dbf`). Both are explained by frame 12
alone: each run that shows one has the rare variant in frame 12 and 22 identical other frames.

Three of the 4 odd runs were the first run of their build's block, which hints at a warm-up effect; n is small.

## Outcome

Neither of the card's first two cases: both builds vary, and they vary the same way.

- Each build produced the common frame 12 in most runs and the rare variant in some: the branch in one `retro`
  and one `retro-filter` run, the base in one `retro` and one `retro-filter` run. The builds produce the same two
  variants per scenario. The difference TASK197 saw (`13e096a71b18` against `78660fd859cd`) was this one frame flipping
  in one of the two recordings, not a code difference.
- The variation is not in the filter pass: `retro`, which does not run the box filter, varies at the same frame
  and at the same rate. The filter is not implicated (`retro`, with no filter, flips too); nor are the scratch
  copy and `rmb_post_pass`.
- Both builds equal each other once the variant is accounted for, so nothing in `7550c9bc..2d176b7f` reaches
  the frame.

So a `retro` or `retro-filter` pin recorded in one run can show a frame-12 difference that is not a regression.
The source is upstream of the Retro pass and probably shared by every `demo1.dm2` scenario on Metal at frame 12;
other scenarios were not tested (a frame-time or demo-state input; this card did not find it). It is left open:
FIX155 (#613) finds the source, recording other scenarios at frame 12 and bisecting what the frame depends on. No code changed and no pin was re-recorded. PM4 should
compare `retro`/`retro-filter` with that in mind (three runs, take the common variant) until the source is found.
