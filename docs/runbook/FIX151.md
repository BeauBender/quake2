# FIX151: a demo the local server plays counts as a demo for the upscale gate

FIX148 ([its runbook](FIX148.md)) took "a demo" to be `sv.attractloop`, which the client keeps as
`cl.attractloop` and passes to `CL_UpscaleAllowed` as its `demo` argument. Its review found a demo
that is not one by that flag: `map demo1.dm2` goes through `SV_GameMap_f` and `SV_Map(false, ...)`,
so the server is `ss_demo` with `sv.attractloop` 0. Running console commands from a server or a
demo stays by design (see CLAUDE.md, "Security-relevant boundaries"); this card is about the demo
leg of a gate that is meant to refuse while a demo plays.

## What the client's flag really is

For a demo, the server does not send its own `svc_serverdata`: `SV_New_f` (`src/server/sv_user.c`)
returns after `SV_BeginDemoserver` when the state is `ss_demo`, and the client then reads the
demo file's messages, the first of which is the `svc_serverdata` written when the demo was
recorded. `CL_ParseServerData` sets `cl.attractloop` from that byte. So for any demo,
`sv.attractloop` never reaches the client: `cl.attractloop` is whatever the demo file says.
`CL_Record_f` writes 1 ("demos are always attract loops"), so a stock demo closes the gate through
either command. A demo file that says 0 opened it through either command, `demomap` included.

## The choice: the gate also reads the server's state

`CL_UpscaleAllowed` (`src/client/cl_upscale.c`) now refuses while `Com_ServerState()` is `ss_demo`,
as well as when `demo` (`cl.attractloop`) is set. The server's state is set by `SV_Map`'s branch on
the level's extension, which a demo's content cannot change, and it is `ss_demo` for every demo
the local server plays, whichever command started it. The client does not include the server's
header, so the value is a named constant beside the function; `tests/unit/test_demo_gate.c` drives
the real `SV_Map` to a demo, so the test fails if the two values part.

The other option, setting `attractloop` on the `.dm2` branch of `SV_Map` the way `demomap` does,
was rejected:

- It does not fix the gate. `sv.attractloop` is not sent for a demo (see above), so the client's
  flag would still come from the demo file.
- It would change more than the gate: `SV_SpawnServer` clears `paused` when `attractloop` is set,
  `sv_conless.c` refuses remote clients, and FIX148's drop at the top of `SV_Map` would then also
  fire when a `map x.dm2` demo is replaced by a game.

Nothing on the client's side of `cl.attractloop` changes: the key that ends a demo
(`cl_keyboard.c`), the console, the `SV_DemoCompleted` and `nextserver` flow, the attract loop and
`timedemo` read the same values as before. The new check refuses only `upscale_textures`.

## What is left as it was

`sv_conless.c` still refuses remote clients only when `sv.attractloop` is set, so a server running
`map x.dm2` still accepts a remote client. That is a server's choice about who may watch, not the
local client's gate, and changing it would change what a dedicated server does with `map x.dm2`;
the card's acceptance criteria name the gate only. `cinematic` and picture levels (`.cin`, `.pcx`
and the others) carry no text of their own and stay allowed on the local server, as before.

## The `nextdemo` decision: out of the threat model

A server can set `nextdemo` with the archive flag (`set nextdemo ... a`). It is then written to
`config.cfg`, and the next local `SV_Map` without a `+` copies it into `nextserver`, which
`SV_Nextserver` queues as the player's text when a demo, cinematic or picture level ends. This is
the same class of persistent change as `bind`, which a server can also archive and which runs as
the player's text on a key press, so it stays out of the threat model, as FIX148 section 3
recorded. A later card that filters archived settings from a server would cover both.

## Proof

The test is `tests/unit/test_demo_gate.c`: each case runs the real `SV_Map` with a game module that
spawns nothing, in a forked child, then checks `Com_ServerState()` and
`CL_UpscaleAllowed(1, 1, demo_byte)`.

- `demo_gate_map_dm2_is_a_demo`: `SV_Map(false, "t_gate.dm2")`, demo byte 0, refused.
- `demo_gate_demo_byte_zero_is_a_demo`: `SV_Map(true, ...)`, demo byte 0, refused.
- `demo_gate_stock_demo_refused`: demo byte 1 through either command, refused, as before.
- `demo_gate_pic_level_allowed`: a picture level, allowed, as before.

Red on the base (FIX148's head plus the new test only), green on this branch; the runs are in the
pull request. `upscale_allowed` in `tests/unit/test_cl_upscale.c` keeps every earlier answer with
no server running, and the `cbuf_` tests of FIX148 cover the demo text. The `world` pin (the stock
`demo1.dm2` by `+demomap`, `timedemo`) gives the same frames on the base and on this branch.
