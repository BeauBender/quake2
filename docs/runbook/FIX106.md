# FIX106: the host lock serves waiters in arrival order

The host lock (`scripts/bench/core/lock.sh`, plan
[`docs/plans/bench-harness.md`](../plans/bench-harness.md), "The host lock") was a plain `mkdir`
race. A waiter polled every `BENCH_LOCK_POLL` seconds (2 by default), so a caller that released
the lock and asked again at once usually made the directory before a waiter that had polled for
an hour woke up.

## The problem, measured

On the M6 on 2026-11-17 a timing lane ran its report in chunks, each under 20 minutes and back
to back. A queued `scripts/test.sh` gate waited its whole `BENCH_LOCK_WAIT` (3600 s) and gave up
with exit 75, "the lock is still held by TASK114-m6 … after 3600 s; giving up": it lost the race
to each new chunk in turn. A merge waited more than an hour the same way. The gate cannot take a
shorter poll from its caller, either: the tests-green stamp accepts only the plain
`cd <worktree> && scripts/test.sh` form, with no `VAR=value` prefix.

## The design

A ticket queue in the lock's state directory, `<state>/queue/`, beside `lock/`. It uses the
primitives the lock already uses (`mktemp`, a rename, `kill -0`) and no new protocol:

- On arrival a waiter makes one ticket with `mktemp` (`tmp.<pid>.XXXXXX`, a name no other
  process knows ahead), writes `pid=`, `label=` and `since=` (UTC) into it, and renames it to
  `w.<time>.<pid>.<random>`. The time is `perl -MTime::HiRes` zero-padded to 12 integer and 6
  fractional digits (whole seconds from `date` when perl fails), the pid zero-padded to 10, the
  random part the `mktemp` suffix. `bench.sh` sets `LC_ALL=C`, so the glob sorts the names by
  arrival.
- Only the waiter whose ticket sorts first among the live ones tries the existing `mkdir`, and
  only it runs the existing reclaims (a dead holder, a holder-less directory past its grace).
  Every other waiter naps one poll and looks again.
- A ticket, or a temporary, is removed by whichever waiter sees it, and left out of `lock
  status`, only when its waiter is gone (`bench_lock_waiter_running` on its pid): `kill -0`
  fails, or `ps` succeeds with a state starting with `Z` (a zombie; review round 1, below). A
  failed or empty `ps` keeps the ticket (review round 2, below). A ticket that carries the
  reader's own pid but is not its own (a dead waiter's pid, reused by this one) is removed too.
  A waiter killed while queued, by any signal including KILL, reaped or not, holds up the next
  one for one poll.
- Only regular files in the queue are read (`[ -f ]` and not a symbolic link). Anything else
  with a ticket's name, such as a FIFO, which would block whoever opens it, is skipped and left
  in place, by the waiters and by `lock status`: removing it would act on something the lock
  never made.
- A waiter takes its ticket out the moment its `mkdir` succeeds, so the next waiter heads the
  queue while the holder runs. A maker that backs off (its holder file landed in a directory a
  reclaimer had made again) puts its ticket back under its first key, so it keeps its place.
- On every other exit the ticket goes: the wait running out (exit 75) removes it before
  returning, and the EXIT trap (which INT, TERM and HUP reach through `bench_on_signal`) removes
  it, and its temporary, in `bench_lock_release`.

So a holder that releases and asks again gets a later ticket than every waiter already there,
and goes behind them. Unchanged: the re-entrant path (`BENCH_LOCK_TOKEN` equal to the holder's
token passes straight through, before any ticket), the `--quiet` marker, the holder file's
format, `lock status`'s existing first line, and the exit codes 74 and 75. `bench.sh lock
status` adds one line per live waiter, in order: `waiter=<n> label=<label> pid=<pid>
since=<UTC>`.

Limits, the same as the holder's: a waiter stopped (SIGSTOP) while it heads the queue holds the
queue up, as a stopped holder holds the lock; a dead waiter's pid reused by another process keeps
its ticket alive until that process ends. A caller that does not queue (the copy under the
artifacts folder's `tools/bench/` until it is refreshed from the merged tree) still races the
head's `mkdir`; it cannot take the lock from a holder.

Further limits, from review round 1:

- `BENCH_LOCK_WAIT=0` now also gives up (75) when a live waiter is ahead, even with the lock
  free; before the queue it failed only when the lock was held.
- The names sort by the wall clock, so a step of the clock backwards between two arrivals can
  put the later one first.
- `kill -0` reads EPERM (a process of another user) as dead. The queue, like the lock, is per
  user, so that is outside its model.
- Only the head tries the `mkdir`, so the head's own `BENCH_LOCK_POLL` and `BENCH_LOCK_GRACE`
  set the pace of a hand-off, whatever a later waiter polls at.
- A waiter KILLed by a parent that has not reaped it is a zombie, which still answers
  `kill -0`. Before round 1 it held the queue's head until it was reaped; now it is skipped.
- Rollout: a worktree that forked before this merges runs the old lock, which takes no ticket
  and races the head's `mkdir`, until it merges main.

Further limits, from review round 2:

- A reader whose `ps` fails or prints nothing judges a waiter by `kill -0` alone, so to it a
  zombie waiter is still running until it is reaped; any reader whose `ps` works removes it.
- The regular-file check comes before the `cat`, so a process of the same user can swap a ticket
  for a FIFO or a link in between. That is the same user, so outside the per-user model.

## The tests

Six tests in `tests/check-bench.sh`, each in its own scratch state directory under the check's
temporary directory, never the real `~/.cache/bench-state`. The commands under the lock log
their start and end with `Time::HiRes` times, and the order is read from those times.

- `t_lock_fifo` (release and re-ask): A holds; B waits with a poll of 3 s; A releases and runs a
  second `lock run` at once. B must start before A's second call.
- `t_lock_order` (order of three): C1, C2 and C3 arrive in that order, spawned in the reverse
  order (so their pids run against arrival) and each later one polling faster (2 s, 1 s, 0.1 s,
  so a plain race would go to C3). They must get the lock as C1, C2, C3.
- `t_lock_dead_waiter`: W1 and W2 queue behind a holder; W1's ticket is first; W1 is KILLed and
  reaped. W2 must get the lock within 3.1 s of the release (one poll, the 1 s grace, 1 s for the
  holder's lock shell to see its command end, and 1 s of slack), and no ticket is left.
- `t_lock_giveup`: a waiter with `BENCH_LOCK_WAIT=1` shows its ticket (`pid=`, `label=`) while it
  waits, exits 75 naming the holder, and leaves no ticket; a waiter TERMed while it waits exits
  143 and leaves nothing in the queue.
- `t_lock_queue_reentry`: a waiter is queued; the holder's command runs a nested `lock run` with
  `BENCH_LOCK_WAIT=0`, which must pass straight through, without waiting and without a ticket
  (the queue seen from inside holds the waiter's ticket alone).
- `t_lock_queue_status`: three waiters behind a holder; `lock status` prints the holder's line
  unchanged, then `waiter=1` to `waiter=3` with each one's label and pid, in arrival order.

The helper `wait_held` now reads the holder's line alone (it starts `lock=held label=`), since a
waiter's line carries a label too.

## Review round 1

The three-pass panel found two Importants and five notes. Each fix has its own commit and a test
written red first.

### The findings and the fixes

- **A zombie waiter blocked the head** (security, Important). The head check judged a ticket
  with `bench_lock_alive`, which is `kill -0`, and a zombie answers `kill -0`. So a waiter KILLed
  by a parent that had not reaped it stayed at the head, and the next waiter gave up with 75
  while the lock was free. Fix: a ticket's `pid=` is judged with `bench_pid_running` (alive and
  not a zombie), in the head check, for the temporaries and in `lock status`. Test
  `t_lock_zombie_waiter`: Z is the child of a perl parent that reaps it only when the test says
  so; Z queues behind a holder, W behind Z; Z is KILLed and left a zombie (the test checks that
  `kill -0` still answers); the holder releases; W must get the lock within 3.1 s and no ticket
  is left. Mutant `queue-zombie-alive` (the ticket check back to `bench_lock_alive`).
- **"A maker that backs off keeps its place" was untested** (correctness, Important). Neither
  re-enqueue, the back-off in `bench_lock_acquire` nor the "ticket gone" one at the top of
  `bench_lock_head`, was reached with two waiters queued, so a mutant that resets the key passed
  every test. Tests: `t_lock_stall_place` (the reviewer's test, adapted: N makes the lock and
  stalls 6 s before its holder write, C with a grace of 1 s reclaims the bare directory and
  holds, W queues behind C before N backs off, which the test checks; the order must be
  `C N W`), and `t_lock_ticket_back` (W1 and W2 queue; W1's ticket is removed by hand; W1 puts
  it back under its first key, and the order is `H W1 W2`). Mutants `queue-backoff-new-key` and
  `queue-back-new-key` (each resets `BENCH_LOCK_KEY` before its re-enqueue). A ticket put back
  keeps its key (`w.<time>.<pid>`) but takes a new random part from `mktemp`, so the comments
  and this runbook now say "first key", not "first name".
- **A ticket with the waiter's own pid** (security N1, correctness N4). A `w.*` ticket that
  carries `pid=$$` but is not this process's own ticket is stale: a dead waiter's pid, reused
  by this one. It looked alive, so the waiter counted itself behind it. Fix: `bench_lock_head`
  removes it. Test `t_lock_own_pid`: a ticket with W's pid (known before W queues: `late.sh`
  keeps its pid through `exec`) is planted ahead; W must get the lock once the holder releases,
  and the planted ticket must be gone. Mutant `queue-own-pid-kept`.
- **Regular files only** (security N4). A FIFO named `w.*` blocked every reader that opened it.
  Fix: `bench_lock_head` and `lock status` read an entry only when it is a regular file and not
  a symbolic link, and skip anything else, leaving it in place (removing it would act on
  something the lock never made, and skipping is enough to keep it from blocking). Test
  `t_lock_queue_fifo`: with a FIFO planted first in the queue, `lock status` must print
  `lock=free` and a waiter must get the lock, each within 5 s; the FIFO must still be there.
  The test bounds its readers by waiting, not by a signal: a shell blocked in a read of a FIFO
  defers a signal until the read ends. It then frees any blocked reader (it moves the FIFO out
  of the ticket names and opens it for writing). Mutants `queue-fifo-head` and
  `queue-fifo-status`.
- **Anchored readers** (correctness N2). A waiter's status line carries `label=` too, so the
  status readers that matched any `label=` passed on a waiter's label. `t_lock_stall` now
  matches `lock=held label=taker ` at the start of the status, and
  `tests/check-metalfx-report.sh` greps `^lock=held label=gate `, as `wait_held` already does.
- **Docs** (spec notes 1, 3 and 4; security N2 and N3): the limits above (a wait of 0 with a
  waiter ahead, the wall-clock key, EPERM, the head's pace, the zombie, the rollout), here and
  in the plan.

## Review round 2

Both delta reviewers found the same Important, each with a reproduction; security added a note.

### The findings and the fixes

- **A failing `ps` made a live waiter read as dead** (correctness and security, Important).
  Round 1 judged a ticket with `bench_pid_running` (`common.sh`), which returns "not running"
  when `ps` fails or prints nothing. So a caller whose `ps` failed (not on `PATH`, a fork
  failure, a sandbox) removed every live waiter's ticket and went first; the reproduction (a
  `ps` that exits 1 on the late arrival's `PATH`) gave the order `H W2 W1`, the control
  `H W1 W2`. The same reader could remove a live enqueuer's `tmp.*` between its write and its
  rename, so that waiter exited 2. Fix: a helper of the queue's own in `lock.sh`,
  `bench_lock_waiter_running`, at the three sites (the tickets, the temporaries and `lock
  status`). It reads a waiter as dead only when `kill -0` fails, or `ps` succeeds with a state
  starting with `Z`; a `ps` that fails leaves the answer to `kill -0`, asked again, and one that
  succeeds and prints nothing is no `Z`, so running. `bench_group_alive` keeps
  `bench_pid_running` as it is.
- **Links** (security N1). The regular-file check skipped a symbolic link, but no test planted
  one. Test `t_lock_queue_link`, below.

### The tests

- `t_lock_ps_fails`: `$E/shim/ps` is `#!/bin/sh` and `exit 1`. W1 queues behind a holder with
  `BENCH_LOCK_POLL=3`, so it naps; W2 queues with the shim first on its `PATH` and polls every
  0.1 s; the holder releases, and the order must be `H W1 W2 `. A second round does the same
  with a shim that exits 0 and prints nothing.
- `t_lock_ps_tmp`: a temporary `tmp.<pid>.live00` whose pid is the test's own shell survives a
  waiter whose `ps` exits 1, and the waiter runs.
- `t_lock_zombie_waiter`, extended: after the KILL, and before any waiter polls (so the ticket is
  still there, which the test checks), `lock status` must print no `pid=<zombie>` line. W now
  queues after the status check.
- `t_lock_queue_link`: a `w.*` link to a regular file that names the test's live shell; `lock
  status` must print `lock=free`, a waiter (a wait of 3 s) must run, and the link and its
  target must be left as they were.
