# FIX221: the bench check's stand-in engine sets its TERM trap first

## The race

`tests/check-bench-quake2.sh` writes one stand-in engine (`$B/release/quake2`). The
run case, the metalfx cases and the pre-warm's pieces all start it through the adapter,
which sends TERM after `seconds=1`. The stand-in used to set `trap '...; exit 0' TERM`
only after its argument loop and five echo lines. Under the merge gate's load (six
checks at once) it could still be before that line when the TERM came, die with 143, and
the adapter reported `the engine exited with status 143`. It was seen twice: in the run
case, and in the pre-warm's piece (`bench: quake2: TERM after 1 s`, then status 143).
Both use the same stand-in; there is no other script in the check that is TERMed.

## The change

- Stand-in: `trap ... TERM` is now line 2, directly after the shebang. The handler is
  unchanged. A check right after the file is written refuses a stand-in whose line 2 is
  not the trap (that is the mutant that moves the trap back).
- A knob, `FAKE_DELAY=<s>`, sleeps right after the trap; only the race case sets it.
- The race case: `FAKE_DELAY=2` with `seconds=1`. The TERM arrives mid-delay, so the
  trap must already be set: the teardown line is in the log and there is no status 143.

## Red and green

Old order (trap late, the delay first), commit b35950ad:

```
check-bench-quake2: FAIL: a stand-in still starting at the TERM did not tear down: bench: quake2: TERM after 1 s
check-bench-quake2: FAIL: a stand-in still starting at the TERM died of it: bench: quake2: TERM after 1 s
check-bench-quake2: 2 failures
```

New order: `check-bench-quake2: ok (32 cases)` (33 with the line-2 check).

The trap's disposition at the stand-in's first line is what the race case shows: TERM
sent while the process is in its first command is caught (handler output, exit 0), not
defaulted. No load was added; the only sleep is the case's 2 s delay.
