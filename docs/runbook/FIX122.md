# FIX122 (slice 1): one reader of the pin scenario format

Card FIX122 (#501), finding AR-13 of `docs/reviews/2026-11-17-fork-window.md`. This slice covers
the scenario reader only. The bounded-run primitive (AR-14, the watchdogs) is slice 2.

## What was wrong

Three readers of the pin scenario format (`scripts/pins/scenarios/*.cfg`) each kept their own list
of what they refuse:

- **`scripts/pins.sh`** (`build_args`) refused `pins_*`, the cvars the driver sets, `basedir`,
  `cddir`, `game`, `datadir` and `cfgdir`, `..` in a value, and a value starting with `-` that is not
  a number.
- **The quake2 bench adapter** (`q2_scenario_args` in `scripts/bench/adapters/quake2.sh`) said it
  refused "as scripts/pins.sh does". It used its own list, `q2_cvar_ok`, which is the one for case
  settings, with three exceptions written into the scenario path (`timedemo`, `r_vsync`,
  `vid_maxfps`).
- **The MetalFX report generator** (`parse_scenario` and `scenario_cvars` in
  `scripts/metalfx-report/mfx.py`) dropped every line that was not `set` with three words, without a
  word. It refused none of the path cvars or `pins_*`. Its `VALUE_RE` (`^[A-Za-z0-9_.-]+$`) let `..`
  through, and a missing file was a `FileNotFoundError`, not a refusal. The generator writes a
  scenario's cvars into the engine's console script for its timed runs, so these cvars reached the
  engine.

## The one source, and why

The one source is `scenario_sets` in `scripts/pins.sh`, reached as `scripts/pins.sh scenario-args
<file>`. It prints `<cvar> <value>`, one line for each set line, and only once the whole file is
accepted. On a refusal it prints nothing on stdout, gives the reason on stderr, and exits 1.
`build_args` (the record) calls it, and so do the adapter and the generator. Neither of them keeps a
list of refused names.

A data file of refused names and rules was the other way. It was not chosen for three reasons:

- **Three parsers.** Each reader would need its own parser of the rules file, in bash, in bash
  3.2-compatible sh and in Python. Each parser would be one more place where a rule can be read
  wrong, which is the class of bug this card removes.
- **A subcommand cannot drift.** There is one parser of the format itself, not just one list.
- **No new dependency.** The adapter and the generator already run `scripts/pins.sh` from the same
  checkout: the adapter to find the tree's scripts, the generator for its records. Calling
  `/bin/bash scripts/pins.sh` adds nothing to either runtime. The adapter finds it at
  `$BENCH_ROOT/../pins.sh`, and the generator at `ROOT/scripts/pins.sh`.

### Fail closed

| Case | `pins.sh` | Adapter | Generator |
|---|---|---|---|
| A file that cannot be read | refuses: `<label>: not a readable file` | refuses (pins.sh's reason) | `Refuse` (pins.sh's reason) |
| A line that is not `set <cvar> <value>` | refuses with the line number | refuses | `Refuse` |
| `scripts/pins.sh` missing, or not runnable | n/a | refuses | `Refuse` |
| `scenario-args` exits non-zero, whatever it printed | n/a | refuses | `Refuse` |
| An output line that is not `<cvar> <value>` | n/a | refuses | `Refuse`, never skipped |
| Output with no newline after its last line | n/a | reads the line as it is | `Refuse` |

No reader falls back to a private list.

### Extra restrictions, never allowances

The adapter and the generator keep one restriction beyond the shared rules. A value holds only
`A-Z a-z 0-9 _ . -`, with no `/`. The adapter applies it as a character check, and the generator
through `CVAR_RE` and `VALUE_RE`. Neither restriction can let through anything `scenario_sets`
refuses, because both run only on what it accepted.

### Two messages moved

- **The adapter's.** It now names `scripts/pins.sh scenario-args` and gives its reason.
- **The generator's.** A scenario value such as `1;quit` is now refused by the shared reader, before
  `check_console_set` sees it. The message names the file, the line and the cvar: `unsafe.cfg line 2:
  the value of r_drawworld must hold only ...`. The `e2e-unsafe` assertion of
  `tests/check-metalfx-report.sh` follows that message. The stub `scripts/pins.sh` of that check's
  tree copies passes `scenario-args` to the real one.

### What the format holds

The cases of the format are in `scripts/pins/scenario-cases.txt`: `refuse` or `accept`, a tab, then
one scenario line. The pin selftest (`st_scenario_lines`) used to keep its refusal cases inline. It
now reads them from that file, and the check gives the same cases to every reader. The file holds
the selftest's old cases and the card's cases (`basedir`, `game`, `datadir`, `cfgdir`, `cddir`,
`pins_*`, `..` in a value, a non-numeric leading `-`), plus a few more line shapes.

## The check

`tests/check-scenario-parsers.sh` is POSIX sh. The gate picks it up through its `tests/check-*.sh`
glob, as it does `check-pins.sh`, and it is listed in `tests/ci-checks.txt`. It works on a copy of
`scripts/` and runs five readers:

- `pins.sh scenario-args`;
- the record, as a dry run;
- the adapter's `q2_scenario_args`;
- the generator's `parse_scenario`;
- the generator's `scenario_cvars`.

It has four tests:

| Test | What it requires |
|---|---|
| `t_refuse` | Every `refuse` case of `scenario-cases.txt` is refused by all five readers. |
| `t_accept` | Every `accept` case, and every scenario of the tree, is accepted by all five. Each passes on exactly the file's set lines, and `scenario_cvars` their names. |
| `t_closed` | A missing scenario is refused by all five. With `scripts/pins.sh` removed, or replaced by a stub that exits 1 with good output, the adapter and the generator refuse. They also refuse when the stub prints a `set` line, one word, two spaces, an empty line, a capital or a leading space. |
| `t_shared` | A canary name (`zzqcanary`) is accepted by all five. Once it is added to `scenario_sets`'s refusals in a copy, all five refuse it. A reader that kept a private copy of the rules would go on accepting it. |

`tests/check-scenario-parsers.sh <root>` runs the four tests on another tree, with this checkout's
cases and no mutants. That is how the red run below was made.

### The mutants

Each mutant is one literal change to a copy of `scripts/`. The test named must fail on it.

| Mutant | Change | Caught by |
|---|---|---|
| `mfx-allows-basedir` | The generator lets a refusal through when it names `basedir`. Its allow-list readmits `basedir`. | `t_refuse` |
| `mfx-cvars-own-parse` | `scenario_cvars` goes back to its own line parser. | `t_refuse` |
| `dotdot-dropped` | The `..` rule is removed from `scenario_sets`, so no reader has it. The adapter's and the generator's character checks still refuse `../x`. | `t_refuse`, on `pins` and `record` |
| `mfx-skips-malformed` | The generator skips an output line that is not `<cvar> <value>`. | `t_closed` |
| `mfx-ignores-status` | The generator ignores the shared reader's exit status. | `t_closed` |
| `adapter-skips-malformed` | The adapter skips a malformed output line. | `t_closed` |
| `adapter-ignores-status` | The adapter ignores the shared reader's exit status. | `t_closed` |
| `adapter-private-copy` | The adapter calls a copy of `pins.sh` kept beside it, which has the same rules today. | `t_shared` only |
| `mfx-private-copy` | The generator calls a copy of `pins.sh` kept beside it. | `t_shared` only |
| `record-private-rules` | `build_args` reads the file itself and skips `scenario_sets`. | `t_refuse` |

## Not in this slice

**The bench case settings.** The adapter's `cvar.<name>=<value>` words are a bench case format, not
the scenario format. They still go through `q2_cvar_ok` and `q2_value_ok`. Their list repeats the
scenario refusals and adds the adapter's own (`r_vsync`, `timedemo`, `vid_maxfps`). Moving them onto
`scenario_sets` would be a follow-up.
