# FIX122 (slice 1): one reader of the pin scenario format

Card FIX122 (#501), finding AR-13 of `docs/reviews/2026-11-17-fork-window.md`. This slice covers
the scenario reader only. The bounded-run primitive (AR-14, the watchdogs) is slice 2.

## What was wrong

Three readers of the pin scenario format (`scripts/pins/scenarios/*.cfg`) each kept their own list
of what they refuse:

- **`scripts/pins.sh`** (`build_args`) refused `pins_*`, the cvars the driver sets, `basedir`,
  `cddir`, `game`, `datadir` and `cfgdir`, `..` in a value, and a value starting with `-` that is not
  a number.
- **The quake2 bench adapter** (`q2_scenario_args` in `scripts/bench/adapters/quake2.sh`) said it
  refused "as scripts/pins.sh does". It used its own list, `q2_cvar_ok`, which is the one for case
  settings, with three exceptions written into the scenario path (`timedemo`, `r_vsync`,
  `vid_maxfps`).
- **The MetalFX report generator** (`parse_scenario` and `scenario_cvars` in
  `scripts/metalfx-report/mfx.py`) dropped every line that was not `set` with three words, without a
  word. It refused none of the path cvars or `pins_*`. Its `VALUE_RE` (`^[A-Za-z0-9_.-]+$`) let `..`
  through, and a missing file was a `FileNotFoundError`, not a refusal. The generator writes a
  scenario's cvars into the engine's console script for its timed runs, so these cvars reached the
  engine.

## The one source, and why

The one source is `scenario_sets` in `scripts/pins.sh`, reached as `scripts/pins.sh scenario-args
<file>`. It prints `<cvar> <value>`, one line for each set line, and only once the whole file is
accepted. On a refusal it prints nothing on stdout, gives the reason on stderr, and exits 1.
`build_args` (the record) calls it, and so do the adapter and the generator. Neither of them keeps a
list of refused names.

A data file of refused names and rules was the other way. It was not chosen for three reasons:

- **Three parsers.** Each reader would need its own parser of the rules file, in bash, in bash
  3.2-compatible sh and in Python. Each parser would be one more place where a rule can be read
  wrong, which is the class of bug this card removes.
- **A subcommand cannot drift.** There is one parser of the format itself, not just one list.
- **No new dependency.** The adapter and the generator already run `scripts/pins.sh` from the same
  checkout: the adapter to find the tree's scripts, the generator for its records. Calling
  `/bin/bash scripts/pins.sh` adds nothing to either runtime. The adapter finds it at
  `$BENCH_ROOT/../pins.sh`, and the generator at `ROOT/scripts/pins.sh`.

### Extra restrictions, never allowances

The adapter and the generator keep one restriction beyond the shared rules. A value holds only
`A-Z a-z 0-9 _ . -`, with no `/`. The adapter applies it as a character check, and the generator
through `CVAR_RE` and `VALUE_RE`. Neither restriction can let through anything `scenario_sets`
refuses, because both run only on what it accepted.

### Two messages moved

- **The adapter's.** It now names `scripts/pins.sh scenario-args` and gives its reason.
- **The generator's.** A scenario value such as `1;quit` is now refused by the shared reader, before
  `check_console_set` sees it. The message names the file, the line and the cvar: `unsafe.cfg line 2:
  the value of r_drawworld must hold only ...`. The `e2e-unsafe` assertion of
  `tests/check-metalfx-report.sh` follows that message. The stub `scripts/pins.sh` of that check's
  tree copies passes `scenario-args` to the real one.

### What the format holds

The cases of the format are in `scripts/pins/scenario-cases.txt`: `refuse` or `accept`, a tab, then
one scenario line. The pin selftest (`st_scenario_lines`) used to keep its refusal cases inline. It
now reads them from that file, and the check gives the same cases to every reader. The file holds
the selftest's old cases and the card's cases (`basedir`, `game`, `datadir`, `cfgdir`, `cddir`,
`pins_*`, `..` in a value, a non-numeric leading `-`), plus a few more line shapes.

## Slice 2: one bounded-run primitive (AR-14)

"TERM, a grace period, then KILL" was written five times: `run_engine` and `make-demo` in

### The guard

Part one of `tests/check-bounded-run.sh` reads every line of every file under `scripts/`. A file
it cannot read is a failure, and so is a `find` that exits non-zero or writes to its standard error
(a directory it cannot read).

**What the guard is.** It is a lint over the common spellings, which a reviewer keeps honest. It
is not a trust boundary: a static reader of shell cannot be made complete. The disposition probe is
the behavioural proof for the callers.

**Why it tracks no regions.** Round 1's guard allowed KILL and signal code inside named functions
(`selftest`, `gate_reap`, `stop_group`), which it found by following function bodies and here-docs
in its own reader of shell and Python. Review round 2 showed that this leaks. A one-line stub with a
trailing comment, a `( )` body, or an indented `}` left the region open, so a top-level KILL after
it passed. Here-strings, `<<\EOF`, an indented terminator and `\"` confused the here-doc tracking.
So the guard lints the shape of each logical line instead.

**The marker.** A line the rules below refuse passes only when it ends with the comment
`# bounded-run: allowed: <reason>`. `MARKED` in the check pins each file's reasons by their exact
text, and a reason is unique within its file. A marker whose reason is not listed fails. So do a
listed reason that no line carries, a reason on two lines, and a marker on a line that no rule
refuses. A marker followed by a quote is inside a string, so it is no marker, and it is refused. A
marked line may hold one `kill`, `pkill`, `killall` or `timeout` word, or one Python KILL form, so
joining two marked lines, or adding a KILL to one, is refused. There is no whole-file entry.

What the pinned reasons guarantee: a marker with a new reason needs an edit to `MARKED`, and so does
one taken away. They do not record which line a reason is on. A KILL removed and another added
elsewhere under the same reason passes, and only the reviewer reading the diff sees it.

| File | Pinned reasons |
|---|---|
| `scripts/bench/core/common.sh` | `the primitive: bench_pid_alive`; `the primitive: the group a spawn made`; `the primitive: a group still has a member` |
| `scripts/bench/core/lock.sh` | `the lock: its holder group still has a member; it signals none` |
| `scripts/gate-checks.sh` | `gate_reap: the gate scheduler polls its checks; it signals none`; `gate_alive: the group test of gate_end, card FIX186` |
| `scripts/test.sh` | `the gate parent watch: it polls the caller, and sends TERM only` |
| `scripts/ios-sim.sh` | 15 selftest reasons: the fake `xcrun` terminate, the signal under test, the waits for it, and the ends of the fake's hung calls, its hung launcher read and its decoy |
| `scripts/ios-device.sh` | 7 selftest reasons, in the same way (the INT to the script's group and the other signals under test are now two lines) |
| `scripts/metalfx-report/mfx.py` | `stop_group`'s KILL to the group after TERM and the wait, and the two `p.kill()` of `run_engine`'s pty run |
| any other file | none |

Two `ios-sim.sh` reasons were on two lines each. Their second copies, in the launcher-read case, now
say "hung launcher read". The full text of every reason is in `MARKED`.

`run_engine` in `mfx.py` is a TERM, 5 s, KILL watchdog that round 1's guard did not see, because it
had no rule for `.kill()`. It is marked here and is a remaining copy, like `gate_end`.

**The rules.** The guard reads logical lines. A shell line that ends in an odd number of backslashes
goes on to the next (a whole-line comment does not), and a Python line goes on while a parenthesis
is open, for 50 lines at most. Each logical line is lowered, and its `"` and `'` are deleted, so
`kill -s "KILL"` reads as `kill -s kill`. Here-doc bodies, strings and comments are scanned too. A
signal number may have leading zeros.

- **A KILL**, in every file:
  - `kill`, `pkill` or `killall` with `-9`, `-KILL`, `-SIGKILL`, `-s KILL`, `-s 9`, `-n 9` or
    `--signal KILL` (or 9), and `-09`, `-s 09` and so on;
  - `timeout` with `-s KILL` (or 9), any prefix of `--signal` followed by KILL or 9 (`--sig=KILL`),
    `-k`, or any prefix of `--kill-after` (`--kill=1`).
- **A KILL in a `.py` file**, as well:
  - the word `SIGKILL` (`signal.SIGKILL`, `signal.Signals.SIGKILL`, `from signal import SIGKILL`);
  - `.kill()`, `Signals(9)` and `send_signal(9)`;
  - `kill` or `killpg` (`os.kill`, `os.killpg`) with 9 as the last argument (a trailing comma
    allowed), through one level of nested parentheses (`os.kill(os.getpid(), 9)`). A whole-line
    comment inside an open parenthesis does not end the join.
- **A liveness test**: `kill -0`, `kill -s 0`, `kill -n 0`, `kill -00`, `kill -EXIT` or
  `kill -s EXIT` on a shell line that is not a whole-line comment. This replaces round 1's loop
  detector. Every such test outside a marker is refused, so no loop has to be parsed.
- **In the four callers** (`pins.sh`, `ios-sim.sh`, `ios-device.sh`, the quake2 adapter):
  - any `kill`, `pkill` or `killall`, comments included (comments that said "kill" now say
    "signal" or "SIGKILL");
  - a `bench_*` function of their own (`bench_on_signal` aside);
  - for the adapter, no call of `bench_bounded`.

### Round 2's findings, folded in

- **Security I1.** In round 2, `ios-sim.sh`'s cleanup ran `trap - INT TERM HUP` before its late

  above). The probe's `ios-sim late` row is red on `2ff317e8` and green here.
- **Correctness I1.** `bench_watch` checked its until test only on entry. A test unset inside the
  watch ran as an unknown command (127), was read as false, and the run ended as `wall`. It now

  its 3rd call) gives `status 124 how wall` on `2ff317e8`. Here it gives status 2 and

- **Security and correctness I2 and I3** are the guard changes above: logical lines, leading zeros,

### Round 1's notes, folded in

- **Correctness N1.** `ios-sim.sh`'s cleanup ignores a second INT, TERM or HUP during its group
  stops. A command started while a signal is ignored inherits that, so cleanup's later `bounded`
