# FIX161: downloads land under the write directory and never replace a file

Property: every download is written under `FS_Gamedir()` and never replaces an existing file.

## History of the players special case

`CL_DownloadFileName` (`src/client/cl_download.c`) sent every name starting with `players` to
`BASEDIRNAME/<name>`, a path relative to the working directory. It dates from the 2001 id code (the history of the
file shows only the later moves, "Den Autodownload-Code in eine eigene Datei"), where the working directory was the
install directory and the aim was, as an inference from the code (no commit message or other source states it), to share player skins across mods. In this engine the write directory is under
the user's home (or next to the binary with `-portable`), so that path is outside the write directory, outside the
existence check (`CL_DownloadFilter` tests `FS_FileExists` on the search path, not on that path) and, unless the
working directory is the install directory, not on the search path at all.

## The choice

Route `players*` like every other name, under `FS_Gamedir()`. The alternative, a shared `baseq2` write directory,
needs a second write location the filesystem does not have. A skin downloaded while a mod is active now lands in that
mod's write directory; the client finds it there through the search path, so loading player models is unchanged
(`download_players_lands_in_gamedir` loads it with `FS_LoadFile`). The only difference is that a skin is no longer
shared across mods without being fetched again.

## The overwrite

The final rename in `CL_ParseDownload` is refused when the target exists at write time: the temp file is removed
and a line is printed. This covers every route, not only `players`, and the window left is the gap between the check
and `rename`, in a directory only the user writes.

## Tests

`tests/unit/test_download.c`: `download_players_lands_in_gamedir` and `download_players_existing_target_kept`, red on
`3d711786` (file not found through the filesystem; existing file replaced), green after the change.

## Round 2

- `.tmp` is in the `CL_DownloadFilter` extension table (case-insensitive). The temp name of a download is the name
  cut at its first dot plus `.tmp`, so a final name such as `maps/x.tmp` equalled its own temp name and the
  no-replace guard deleted the file it had just written. No final name can collide with a temp name now.
  Test: `download_tmp_name_refused`, plus `maps/x.tmp`, `maps/x.TMP`, `maps/x.tmp.1` refused and `maps/x.tmpl`
  allowed in `download_filter_extension_table`.
- `CL_DownloadFileName` fails closed: when `gamedir/name` does not fit in `destlen` it sets the buffer to the empty
  string (the declaration in `cl_parse.c` stays `void`) and every caller refuses the download, so a path is never
  truncated into another name (a 256-byte `MAX_OSPATH` build could otherwise cut `A...A.pak/y.pcx` to a top-level
  `.pak`). Test: `download_filename_too_long`, built with a name longer than `MAX_OSPATH`, which works on the
  Apple 4096-byte size too.
- The players tests use `T_REQUIRE` for the working-directory change, and `cwd_leave` does nothing if `getcwd` failed.

## Round 3

- `FS_CreatePath("")` read past the terminator (`strchr(old + 1, '/')`), and `CL_ParseDownload` reached it with the
  empty name that the fail-closed `CL_DownloadFileName` returns. `CL_ParseDownload` now skips the call on an empty
  name, and `FS_CreatePath` itself returns at once on a path of length 0 or 1 (the `..` refusal is unchanged).
- The refused-rename branch removes the temp file when the temp name fitted and the final name did not.
- `CL_Download_f` uses `Q_strlcpy`/`Q_strlcat` and refuses a name whose temp path cannot fit, before any request.
- Tests: `download_parse_name_too_long` (both too-long cases, no temp file left), `fs_refused_paths` (empty and
  one-character paths). Run under `make test ASAN=1`: the old code is reported by ASAN, the new code is clean.
