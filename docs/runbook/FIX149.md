# FIX149: check-image-decoder when leaks(1) cannot attach

## What happened

On a build host with Developer Mode off (`DevToolsSecurity -status`: "Developer mode is currently
disabled") and a locked screen, leaks(1) cannot inspect a process: the developer-tools authorization
it waits for is never answered. `leaks --atExit -- /usr/bin/true` under a 60 s alarm is killed by
the alarm (status 142). `tests/check-image-decoder.sh` then:

- printed the test's own "20 loops of 81 cases, 12863 checks, 0 failed", waited out its whole bound
  (`IMGDEC_CHECK_SECONDS`, default 300 s) and failed with "leaks(1) outlived its 300 s bound";
- left the `imgdecode_plain` that leaks(1) ran behind, stopped (state `T`), orphaned. A stopped
  process cannot end itself at `--bound`, so it stays until someone kills it.

leaks(1) starts its target as its own child and holds it stopped (`TN` under a hanging leaks(1));
killing leaks(1) reparents the target to launchd, still stopped.

## The fix

- **A probe.** Before the leak run, the check runs `leaks --atExit --` on a program that only
  exits (`leakprobe`, built from the check's own `probe.c`), with a bound of
  `IMGDEC_LEAKS_PROBE_SECONDS` (default 20, validated like `IMGDEC_CHECK_SECONDS`: a whole number
  of seconds, not 0). If the probe outlives it, the check fails at once with one line:
  "leaks(1) could not inspect a process within 20 s: it needs Developer Mode (DevToolsSecurity
  -enable) or an unlocked session that answers the developer-tools authorization". It fails; it
  does not skip: the leak run is required wherever leaks(1) exists. Only a probe that outlives its
  bound fails there; any other leaks(1) failure shows in the leak run, with its output.
- **No stopped leftovers (`reap`).** When a bound passes, the watchdog calls `reap <run> <name>`
  instead of a plain `kill`. `reap` is only ever given the check's own `$!`, which the shell,
  blocked in `wait` for it, collects only when it ends. The run could end and be collected between
  the watchdog's check that it runs and its signal, but that window is a few instructions long and
  macOS hands out PIDs in sequence up to 99999 before it wraps, so the PID is not reused in
  practice. `reap` leaves the PID alone when `ps` names a parent other than the check's shell
  (`$$`). When `ps` gives no answer it kills the run all the same (as the check did before
  FIX149), so the bound always ends the run, and prints one line saying a stopped `<name>` may be
  left. Otherwise it stops the run first (a stopped process collects no child, and a child that has
  exited stays its zombie, so each child's PID stays that child's while `reap` works), kills with
  SIGKILL each child whose program basename is `<name>` (`leakprobe` for the probe,
  `imgdecode_plain` for the leak run, `-` for the runs without leaks(1)), then kills the run. If
  `ps -A` cannot list the processes, the run is still killed, with the same line. There is no PID
  file and no name-only match: a process is a target only if it is the stopped run's own child and
  runs the named program.
- **A TERM or INT to the check** (the gate stopping it) runs a trap that kills the watchdog and
  reaps the run in progress the same way, then exits 143 (130 for INT). A signal ignored when the
  check starts stays ignored: the merge gate starts `test.sh` with INT ignored, so only the TERM
  path is tested. The trap runs inside the redirections of the `bounded` call it interrupts, so
  what `reap` says goes to the check's own stderr, kept as descriptor 3 (closed for the run and the
  watchdog).
- **A self-test**, `tests/check-image-decoder-selftest.sh` (in `tests/ci-checks.txt`), runs the
  whole check with stub leaks(1) first on PATH, in scratch: (a) a stub that hangs; (b) a stub that
  spawns its target suspended (`POSIX_SPAWN_START_SUSPENDED`, as leaks(1) does), sends it SIGSTOP
  and hangs; (c) a stub that passes the probe and does (b) to the leak run's target, with an
  unrelated `imgdecode_plain` started by the self-test beside it; (d) a stub that behaves; (e) an
  invalid probe bound (`abc`, `0`); (f) `reap` itself, extracted from the check, under its own
  30 s alarm; (g) a `ps` stub that fails, first on PATH with the hanging stub, and a `ps` stub that
  answers for one PID but cannot list processes (`-A`), with the stub of (b): each must fail at the
  probe's bound with the cause and its `ps` line, under a 40 s alarm; (h) a TERM sent to the check
  while the stub of (b) holds the probe's target stopped: status 143, and the target and the stub
  leaks(1) are both gone.

## Known gaps

- When the gate sends TERM to the whole process group, leaks(1) itself gets it too. If leaks(1)
  dies and the check's shell collects it before the trap runs, the run is no longer the check's
  child, its target has been reparented to launchd, and the trap cannot find it; that target can be
  left stopped. The trap covers a TERM that reaches the check while leaks(1) still runs.
- `bounded` sends a plain TERM to its watchdog once the run ends, as it did before FIX149. A
  watchdog that has already exited may have been collected by then, so that signal can go to a PID
  that no longer exists (seen in the disposition probe below as an empty parent and program).
  Reuse would need the PID allocator to wrap in between.
- A TERM that arrives between the fork of the run and `run=$!`, or between the fork of the watchdog
  and `dog=$!`, finds the variable still empty (or still the previous run's), so the trap does not
  know that process: the new run or watchdog is not ended by it. The windows are a few instructions
  long; the watchdog still ends itself at its bound, and the run is left to leaks(1)'s own end.
- When `ps` gives no answer in the trap (or in the watchdog), `reap` sends KILL to the PID it was
  given (the run, collected only by this shell) and prints "ps(1) gave no answer, so the run was
  killed without looking for its <name>". The line is worded for a run that had a named child, and
  it is printed also when the run had none or its children were already gone, so it can say a
  stopped program may be left when none is. The collected-PID KILL itself is deliberate: the bound
  must end the run.

## Disposition probe (case f)

`reap` called on a PID that is not the caller's child (an orphan running `imgdecode_plain`, as a
PID the caller reaped and the system reused would be), then on a run that is the caller's child
with two children, `imgdecode_plain` and `other`. A SIGKILLed process answers `kill -0` until it is
collected, so the probe waits 1 s and reads the orphan's state with `ps -o stat=` (present and not
`Z`):

```
orphan: alive
run: killed
named child: killed
other child: alive
```

Case (c) shows the same end to end: the unrelated `imgdecode_plain` started by the self-test is
still alive after the check reaped the leak run's stopped `imgdecode_plain`.

With the guard removed (the `ps` parent test in `reap` replaced by `false`), case (f) now reads
`orphan: killed` and the self-test fails ("1 case(s) failed"); before the settle it stayed green.

## On a host where this fires

Enable Developer Mode (`DevToolsSecurity -enable`, an administrator's password), or run the gate in
an unlocked session and answer the developer-tools authorization once.
