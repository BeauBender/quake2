# FIX184: the bench lock knows the bounded command it could not stop

## What was wrong

[FIX181](FIX181.md) made the inner `bench.sh` hold the lock when its signal handler cannot stop a
bounded command (no group, `ps` silent, stop status 2). The lock shell did not know about that
command. Two paths freed the lock while it could still run:

- **A TERM to the lock shell.** The lock shell gives the inner `bench.sh` TERM, which its hold
  ignores, then KILL after the lock grace. The KILL ended the hold, the lock shell reaped the inner
  shell, and its EXIT trap freed the lock. The bounded command ran on.
- **The 125 path, with no signal.** On `bench_bounded`'s wall-time path a stop that returns 2 makes
  the bound return 125 while the command may still run. `host.sh` then runs `bench_die 2`, the inner
  `bench.sh` exits, and the lock shell freed the lock.

A smaller window was also there: `bench_bounded` forgot the command (`bench_spawn_forget`) before it
cleared `BENCH_BOUNDED_PID`, so a signal between the two found a PID the identity table no longer
knew. Its stop then sent nothing and reported success, and no hold started.

## The fix

**The record.** When a stop of a bounded command returns 2, the shell records the command in the
lock directory before it forgets the command. This happens in `bench_on_signal` before its hold, and
in `bench_bounded` before it returns 125. The record is `<state>/lock/untold.<pid>`, written by
`bench_lock_record` (`scripts/bench/core/lock.sh`) to a temporary file `mktemp` makes in the lock
directory (`untold.tmp.XXXXXX`, a name no other process knows ahead, as the quiet marker's is) and
renamed into place:

```
pid=<the bounded command's pid>
start=<its start time as bench_spawn read it, or ? when ps gave none>
written=<when the record was written: bench_proc_read's form of a start time, C locale>
token=<the hold's token>
```

A record is written only under a lock: the one this shell holds, or the one its `BENCH_LOCK_TOKEN`
names. The lock directory is resolved there when the shell has not done so yet, as `bench.sh host`
has not. When `BENCH_LOCK_TOKEN` is set but the lock state cannot be resolved, or the lock it names
is not found, the shell says "cannot record pid N in the lock state" with the reason, so the lock
is never freed silently. A caller of `bench_bounded` without the lock code (`core/lock.sh` not
sourced) writes nothing (`bench_record_untold` in `core/common.sh`). No new lock mechanism is added.
The record is a file in the existing lock directory and is read with the core's existing identity
rule. The holder file's temporary file is made with `mktemp` the same way (`holder.tmp.XXXXXX`).

**Who honours it.** `bench_lock_untold_live` takes a record as live while its PID answers `kill -0`
and `bench_proc_same` gives 0 (the recorded start time, not a zombie) or 2 (`ps` cannot tell, or the
start is `?`). This is the rule the core keeps for its own commands. A record with start `?` has one
more way to expire: when `ps` answers for its PID with a start time later than `written=`, that
process is not the recorded command, which started before its record was written, and the record
holds nothing (`bench_lock_untold_reused`). While `ps` is silent, or the start is not later, or
`written=` is missing or unreadable, the record stays live. Each of the following uses the rule:

- `bench_lock_alive`, for waiters, the reclaim and `lock status`, takes the lock as alive while any
  record is live.
- `lock status` adds ` untold=<pid>[,<pid>...]` to the held line, and to the line of a lock
  directory with no holder file (`lock=held label=none holder=unwritten untold=<pid>`). A waiter
  kept by such a directory says it is held by a command that could not be stopped, with the PID.
- The lock shell's release (`bench_lock_release`, when it owns the lock) waits while any record is
  live, polling every second, and says so before and after. INT, TERM and HUP are ignored during the
  wait. A KILL ends the wait, but it leaves the lock directory to the waiters, and they keep taking
  the lock as alive while a record is live. The quiet marker the lock shell wrote is removed after
  the wait, with the lock, so other sessions keep holding their work while the command may run.
- The reclaim of a holder-less lock directory refuses while a record is live.

**Clearing.** A record whose PID has gone, or that `ps` shows another process has (another start
time, or for `start=?` a start later than `written=`), holds nothing. The release removes every record with the holder file, and so does a reclaim.
No reader removes a record by itself, so a reader cannot remove a record that was just written for a
reused PID. Nothing signals a recorded PID except the shell that started it. The lock shell only
waits.

**The window.** `bench_bounded` clears `BENCH_BOUNDED_PID` before `bench_spawn_forget`, on the stop
path and on the exit path. Together with the record written before both, a signal at any point finds
one of two things: the bounded command still known (it is stopped again and recorded again), or no
bounded command, with the record already in place.

No timing case's verdict depends on the machine's speed (round 1, after FIX181's "bounded hold"
case flaked on a CI runner: its `system_profiler` stand-in's `exec sleep 3` ended before the check
of the lock, about 1.5 s after the TERM). Every command a case checks while it runs (in "lock: no
group", "bounded: no group", both "bounded hold" cases, "lock shell TERM" and "125") is a stand-in
that runs while a flag file is there, 30 s at most, and the case removes the flag only once its
checks of the running command are done. A late check can then never read "gone" for a command that
really ran past it. "bounded: no group" checks that the command still runs when the bound returns,
instead of a 3 s bound on the bound's own time.

FIX181's "bounded hold, lock shell" case also requires the lock shell to be gone within 8 s after
`ps` answers again. The release would otherwise keep the lock until the bounded command's own end
(its life flag's removal after the verdict, 30 s at most), and the case could no longer tell whether the hold's renewed stop ran. That bound keeps
`bounded-no-hold` and `bounded-hold-lock-grace` red. It passes on `27cc84ff` too.

## Limits

- The release's wait has no wall time. It lasts as long as the recorded command runs, or a process
  that took its PID while `ps` cannot tell. For a record with start `?`, it also lasts while a
  process that took the PID started in the same second as the record was written, or earlier:
  `written=` is compared to the second, in local time. So a PID taken within that second, or a
  `ps` that answers in another locale's form, keeps the record live until that process ends. Across
  a fall-back of daylight saving time, local times repeat for an hour, and a recorded command started
  in that hour could read as started after its record and be let go early. The wait is said on the
  lock shell's standard error and shown in `lock status`.
- The quiet marker is released after the wait, so other sessions also keep holding their work for as
  long as it lasts (bounded by the marker's own `expires`, `BENCH_QUIET_TTL`).
- The lock shell never stops a recorded command, even once `ps` answers again. Only the inner shell's
  hold renews the stop. After the inner shell is KILLed, the command runs to its own end.
- A record is written into the lock directory the writer's token names. A rename that races a release
  of that same lock could land in a directory that is being removed. The release runs only after the
  lock's command, the writer's ancestor, has exited, so this needs a writer outside that command.
