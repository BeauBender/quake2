# FIX222: the denoisers' history-weight tests go through integer helpers

## Why

- The Metal shaders build with fast math. Metal compiles a float compare as `fcmp fast`, and fast math
  includes `nnan`: the compiler may assume no NaN comes. So a NaN can pass a compare written so that a NaN
  fails, and the `!(x > 0.0f)` form does not help.
- FIX219 (#826) moved every G-buffer depth and normal alpha compare onto the integer helpers of FIX212 and
  FIX213. Its correctness review found the same class on another input: the history texture's weight lane,
  the sample count the denoisers read from the temporal kernels' history (`hc.w`, `hn.w`, and RT-primary's
  `h.a`).
- No input that makes a NaN history weight has been found. This is a robustness gap, not an observed bug.

## The inventory (acceptance line 1)

Found with a grep of `src/client/refresh/metal/` (every `.metal` file and `common/*.h`) for a relational
compare of a history read's weight lane (`hc.w`, `hn.w`, `h.w`, `hl.w`, their `.a` in RT-primary's light
history), of `mtl_rtd_strength(...)` of one, and of the parameters that carry one into a header function
(`n`, `cn`, `hcount`, and `s`, the strength of `n`), then confirmed in each shader's LLVM IR (the
`fcmp fast` counts below). Line numbers are main's, `c8ceeaf5`.

The NaN column says whether a NaN at that site, folded by fast math as if it were a number, could change
which pixels keep (are filtered from) their history, or which neighbours enter the filter.

| Site | Compare | What it decides | NaN could change which pixels keep history |
|---|---|---|---|
| `common/mtl_rtd_math.h:71`, `mtl_rtd_strength` | `!(n >= MTL_RTD_COUNT_FULL) \|\| !(n < MTL_RTD_COUNT_NONE)` | the blur's strength is 0, or the ramp from 1 at 1 sample to 0 at 16; every site below reaches it | yes: a NaN folded as in range gives a NaN strength |
| `common/mtl_rtd_math.h:131`, `mtl_rtd_weight` | `!(cn >= 1.0f)`, `cn` the neighbour's `hn.w` (`hn.a` for RT-primary) | a neighbour with no sample weighs 0 | yes: the neighbour enters the filter |
| `common/mtl_rtd_math.h:183`, `mtl_rtd_result` | `!(s > 0.0f)`, `s = mtl_rtd_strength(n)`, `n` the pixel's `hc.w` (`h.a`) | the pixel's value moves toward the mean, or is kept | yes |
| `common/mtl_rtpd_math.h:63`, `mtl_rtpd_on` | `mtl_rtd_strength(n) > 0.0f`, `n` the pixel's `hc.a` | RT-primary's filter writes the pixel | yes |
| `rm_rtdenoise.metal:120`, `rm_rtao_denoise` | `!(mtl_rtd_strength(hc.w) > 0.0f)` | AO's filter writes the pixel | yes |
| `rm_rtdenoise.metal:167`, `rm_rtsun_denoise` | `!(mtl_rtd_strength(hc.w) > 0.0f)` | the sun's filter writes the pixel | yes |
| `rm_rtsun.metal:574`, `rm_rtsun_denoise_lo` | `!(mtl_rtd_strength(hc.w) > 0.0f)` | the sun's filter at the traced size writes the pixel | yes |

7 compares in all: 3 in 2 kernel files, 4 in 2 headers.

Read and not listed:

- `rm_rtmodel.metal:183`, `(h.w > 0.0f) ? h.xyz / h.w : v.eye.xyz`: `h` is the homogeneous point
  `p.winv * float4(...)`, not a history read.
- The temporal kernels' history counts (`h.w` in `rm_rtao.metal` and `rm_rtsun.metal`, `hc` in
  `rm_rtshadow.metal`, `hl.a` in `rm_rtptemporal.metal` and `rm_rtmtemporal.metal`) reach only FIX212's
  `mtl_rtt_reject`, `mtl_rtt_blend` and `mtl_rtt_count`, whose guards are integer tests (`mtl_rtt_atleast1`).
- `common/mtl_rtt_math.h:262`, `mtl_rtt_count`'s `hcount + 1.0f < MTL_RTT_COUNT_MAX`: a float compare of a
  history count, but behind `!mtl_rtt_atleast1(hcount)` two lines above, so `hcount` there is a number of 1
  or more or `+inf`, never a NaN. It is FIX212's and is left as it is.
- `mtl_rtd_rresult` passes the constant `MTL_RTD_COUNT_FULL`, no history.
