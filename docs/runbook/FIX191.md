# FIX191: `run_engine`'s read after the engine exits has a total bound

## What happened

FIX186 slice 2's review (round 2) traced `scripts/metalfx-report/mfx.py`'s `run_engine`. After the engine
exits, a loop reads what is left on the pty with `while select(..., 0.2)`. A reviewer showed in a scratch
copy that a fake engine which forked a writer in a session of its own (`setsid`), the writer writing for 8 s,
and then exited 0 made `run_engine` return after 9.1 s.

## The trace

The loop ended only when the pty was quiet for 0.2 s (or read end of file). A writer outside the engine's
session still holds the pty slave, and the master stays open in `run_engine` until the loop is done, so
the master never reads end of file and never goes quiet while the writer writes. Nothing in the loop looked at
a clock; `timeout` bounds only the main loop. The drain the round added in the `finally` already had a
`time.monotonic()` deadline (`ENGINE_DRAIN`), so this loop was the one read left without one.

## The change

The leftover loop now ends at `time.monotonic() + ENGINE_DRAIN`, the constant the drain in the `finally` uses,
documented beside it: the two reads together take at most `2 * ENGINE_DRAIN`. The engine's own lines come
first on the pty, so they are in the log before the bound.

## The proof

`tests/check-metalfx-report.sh`, case `engine-escaped-log` (group `engine`): a fake engine writes `engine-ready`,
starts a Python writer that calls `setsid` and writes to the pty until its write fails or a stop file appears,
and exits 0 once the writer is up. `ENGINE_DRAIN` is 1 s; `run_engine` must return within 6 s with
`engine-ready` in the log. The check makes the stop file after 15 s at the latest and kills the writer by the
pid it wrote, so nothing is left running.

- On the old code the case failed: `status 0 in 17.1` (the run ended only when the check stopped the writer).
- On the new code it passes.
- Mutant `engine-leftover-unbounded` drops the deadline from the loop; the case kills it.

## Not done

The `free` half of `engine-held-log` (FIX186) fails now and then on a loaded runner, on the old code too
(observed once in four runs there). It is not touched here.
