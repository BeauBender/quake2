# FIX171: the test cleanups signal only a process that is still the one they recorded

## What happened

While gate runs were going in other worktrees, a CI-wait script's `perl` sleep got SIGTERM: its shell
printed `Terminated: 15` for it and lived on. The shell traps nothing, and `perl` leads no process
group of its own, so the signal was a TERM to that one PID, not to a group.

macOS hands out PIDs in sequence and reuses a freed one once the counter laps back to it. Under the
load of a gate run that takes 15 to 30 minutes, less with several gates running (during this fix's
probes, PIDs went from about 79000 to 99000 in under a minute). `/bin/sh` here is bash, which collects an
exited child from its SIGCHLD handler at once, so even an unwaited `$!` does not keep its PID.

## The finding

The audit of every signal site in the gate's checks (phase 1) put `tests/check-bench.sh`'s `cleanup`
first. It sent TERM to every PID on its list, `$tmp/pids`. The list held each `start` child and three
grandchildren read from files (the lock shell from the holder file, the INT test's `_h`, the
reclaim guard's group member), was never trimmed, and was checked only with `pid_running` (the PID
exists and is not a zombie). The list lives for the whole run, minutes under a loaded gate, so by
cleanup a recorded PID can belong to an unrelated process. This fits the evidence, though the
victim's PID was not captured, so it is the likely source, not a proven one.

The audit found the same class, with shorter windows, in:

- `tests/check-bench-entry.sh` `cleanup` (its `forget` already trimmed the list);
- `tests/check-metalfx-report.sh`: a `kill -KILL $pid` after the `wait` that collected `$pid`, and
  TERM2's second TERM to a PID read from a file;
- `scripts/ios-sim.sh` selftest: the KILL of the PID in `hang.pid`, checked only with `kill -0`.

The process-group signals in these files were already safe (`stray_stop` checks the command line,
the group and that the group is not the check's own; `check-bench.sh`'s guard test signals the group
only while it still has its member).

## The fix

**The primitive** (the same functions in `tests/check-bench.sh` and `tests/check-bench-entry.sh`):

- `pid_id <pid>` is a checksum of `ps -o lstart=`, the start time, which exec does not change. It
  fails when the PID does not run or `ps` gives no answer.
- The command line is not part of the identity. It guards against no PID reuse that the start time
  does not already cover: another process in the PID with the same start second would need the PID
  counter to go round within that second. It did make cleanup skip the check's own children once they
  exec'd: `bench.sh baseline put` re-execs under the lock, and so does `scripts/test.sh`. Round 1 of
  this fix had it in, and a review probe showed 6 of 6 such children left running by `stop_listed`.
- `record <pid>` puts the PID on the list with its identity at that moment. A PID that has already
  ended, or that `ps` gives no answer for, is put on it with an empty identity. The list holds
  `<pid> <identity>` lines.
- `pid_same <pid> <identity>` is true only while the PID runs with that identity, and never for an
  empty identity. `stop_listed <list>` sends TERM only to the PIDs that pass it, and `cleanup` calls
  it. A PID that has gone, or that `ps` gives no answer for, gets no signal. A PID listed with no
  identity is never signalled. It stays on the list, so check-bench-entry's end-of-run check that the
  list is empty still sees a test that did not forget it.
- `settle <pid>` runs before a `$!` child is recorded. It waits, at most 1 s, until the child is no
  longer showing this shell's command line (a fork has it until its exec) or `env`'s (env execs the
  command next), so that a signal to it reaches the command and not the forked shell. The identity
  does not depend on it.

**`tests/check-bench.sh`:**

- `start` settles and records its child.
- The three grandchildren read from files are recorded with their identity when they are read.
- The two PIDs signalled straight from a file, the quiet probe's grandchild (`gc.quiet`) and the
  zombie waiter's `Z` (`z.pid`), are read with their start time and signalled only while they still
  have it.
- A PID comes off the list once it has been waited for or seen gone. `wait_gone` forgets a PID it
  sees gone. `collect` (wait, then forget) replaces every `wait` on a PID. The lock shell is forgotten
  once its wrapper has written its end. The group member is waited for after the TERM to its group.
- New test `t_cleanup_id` puts its own live processes on a list with identities that do not match:
  another process's (PID 1's start time) and its own command line with another start time. It also
  adds lines that name no PID, and a PID recorded after it ended, which must be listed with no
  identity. All of these survive `stop_listed`. The one listed with its own identity is stopped. So is
  one recorded before it exec'd another program: the same start time with another command line is
  still the check's own. Its processes are shells that end on TERM, and by themselves within about
  30 s, and every wait on them is bounded, so a check started with TERM or PIPE ignored cannot stall
  there.

**`tests/check-bench-entry.sh`:**

- `run`, and the `$!` children of `t_nested`, `t_kgrp` and `t_grace`, settle and record. The orphan's
  PID read from `run.pid` is recorded when it is read. `forget` matches the PID field.
- `stray_stop <pid> <start> <text> [<group>]` keeps its command-line and group checks. It also needs
  the start time that `pid_start` read along with the PID (the `start` line, the make line, `run.pid`).
- `t_cleanup_id` does the same as in `check-bench.sh`, and checks that `stray_stop` with another start
  time leaves its process running. `stray_stop` keeps its command-line and group checks on top of the
  start time: it ends strays a failed test left, which it did not start, so it is stricter than the
  cleanup list.
- The end-of-run check that the list is empty prints only the PIDs.

**`tests/check-metalfx-report.sh`:**

- The KILL after the collecting `wait` is gone. When the stub never started, the run is KILLed only
  while it answers `kill -0` and is then waited for. The wait for the stub's child now also ends when
  the run is gone.
  The e2e-group case logs every `kill` and `wait` that names the run's PID. A signal after the wait
  that collected it fails the case.
- TERM2's two TERMs are `term_twice <pid>`. It reads the generator's `ps -o lstart= -o args=` before
  the first TERM and sends the second only while that is unchanged. If `ps` gave no answer, or the
  generator had changed, TERM2 now fails with that reason instead of skipping the second TERM
  silently. A new case runs `term_twice` on two processes the check starts. One execs another program
  on the first TERM, so it gets no second TERM and is still there. The other does not change, gets
  both, and ends on the second. Here the command line is part of the identity on purpose: the
  generator does not exec between the two TERMs, and an exec is the only change a test can make.
- The KILL of the second run (`$p2`) after its TERM loop goes only to a PID that answers `kill -0`.
- The TERM to the lock holder (`$hp`) was removed, not guarded: its `sleep 10` has ended by then on
  every passing run and bash collects an exited `$!` at once, so a `kill -0` could only answer for
  another process. The `wait` stays.

**`scripts/ios-sim.sh`:** the fake `xcrun`'s hung calls go through `hang <seconds>`. That writes
`sleep <seconds>.<pid>`, a command line unique to the PID, to `hang.cmd`, then writes `hang.pid`, then
execs that command, as the fake launch already does with `app.cmd`. The two selftest KILLs of the PID
in `hang.pid` first compare its `ps -o command=` with `hang.cmd`. A PID that runs but that `ps` gives
no command line for fails the case with that reason. For each of the two sites, a new case has the
fake start a decoy, a `sleep` in its own process group that `hang.pid` names but that runs another
command (`FAKE_SCENARIO=hangdecoy` for the check after the smoke, `FAKE_LAUNCHER=hang1decoy` for the
check after a signal). `st_decoy` fails if the decoy was killed, then stops it while it still runs its
own command.

## Phase 3

Phase 3 covers the sites on the "Not changed" list above, except the bench core, which is FIX172.
Every signal it changes goes to a PID only while that PID still has the start time (`ps -o lstart=`)
read when it was recorded. A PID that has ended, one that runs with another start time, one recorded
with no start time, and one that `ps` gives no answer for all get no signal.

**`reap`, in `tests/check-bench.sh` and `tests/check-bench-entry.sh`.** Every PID `reap` is given in
either file comes from `start` or `run`, or from a `$!` that was settled and recorded. The TERM goes
only while `listed_same` holds: the PID runs, and one of its lines on the cleanup list holds the
identity it has now. The KILL that follows `wait_gone`'s bound is checked the same way. The KILL is
the site the card named, sent 30 s after the TERM. The TERM is guarded as well, because one caller
(`t_nested`'s) reaches it after a 60 s gate run, not straight after a wait that saw the PID. When
`reap` skips a signal to a PID that still runs, it prints `reap: no TERM|KILL to pid <pid>: it is not
the process this check recorded (another identity, none, or no answer from ps), so it is not waited
for`, counts that as a failure, and returns false (round 1). A PID that has gone is skipped silently.
`reap` takes an optional bound (`reap <pid> [<seconds>]`, 30 by default), so the new case can wait
1 s.

The new case is `t_reap_id`, in both files. It starts six shells of its own. Each one notes a TERM and
carries on, so only a KILL ends it, and each ends by itself once a stop file exists, or after 30 s:

| process | how it is listed | what `reap` must do |
| --- | --- | --- |
| `t` | PID 1's identity | no TERM, and say so |
| `k` | PID 1's identity | no KILL, and say so |
| `none` | no identity | no signal |
| `off` | not listed | no signal |
| `ps` | its own identity, with `ps -o lstart=` failing | no signal, and say so |
| `own` | its own identity | the TERM, then the KILL |

### Phase 3, round 1

**One form of a start time.** `ps -o lstart=` pads its output with blanks at the end, and `read -r`
strips them, so the stray check in `tests/check-stop-invariants.sh` compared a padded start time with
a stripped one and could not fail. Each file now normalises a start time inside the one helper that
produces it: `start_of` (through `start_form`) in check-stop-invariants and check-metalfx-report, and
`id_of` in both check-bench files. No caller derives it again. A new run of `term_hook`, on a copy of
the hook whose TERM trap leaves the check's group running, must see that group left running.

**A signal `reap` does not send is a failure.** `reap` says so, counts it, and is false. The wait that
follows runs only when `reap` ended the PID: `ended` in check-bench, `reaped` in check-bench-entry.
`t_reap_wait`, in both files, lists a child of the check with no identity, and with PID 1's identity.
That child ends only by its stop file. The case runs each kind of caller on it (`finish` and `ended`;
`run` and `reaped`), and each must return within 10 s and count the failure. Its last step, in this
round, refused only a line that ended in `reap "<x>"`, with nothing after the call but characters other
than `|`, `&` and `;`, where the call started the line or followed one of those three. A function whose
name held a digit or a capital kept the previous function's exemption. Round 2 replaces it (below).

**`listed_same`** replaces `listed_id`. `reap` and `stop_listed` judge a PID the same way: it runs, and
one of its lines on the cleanup list holds the identity it has now.

**The three signals to a PID read from a file** go only while that PID still has the identity read
with it:
- the TERM to the stubborn command's lock shell (`_sl`, from the holder file);
- the STOP to the stopped command's group (`-$_c`, by its leader's identity);
- the first TERM of TERM2's `term_twice <pid> <start>`.

**Decoys.** Each of those sites, and the `group_left` and `lock_left` call sites in metalfx, runs first
on decoys, in the flow, and then as before:
- In check-bench (`decoy`, `decoy_end`), the site runs with the identity read replaced by another, by
  none, and with `ps` failing. Meanwhile `kill` only notes what it is asked to send, and a noted signal
  fails the case.
- In check-metalfx-report (`decoy_id`, `decoy_end`, on the real code only), the site runs on a stand-in
  the check starts (`standin`, which ends by its stop file). The stand-in is read with another start
  time, with none, and with `ps` failing. It must survive. What that run fails is dropped, since the
  run judged the stand-in and not the case.

**The "cannot tell" rule.** A check that has read a PID compares start times at signal time. Either no
start time was read with the PID, or the PID answers `kill -0` but `ps` gives no start time for it now.
Then the check cannot tell whether the process is still the one read. It sends no signal, and it fails
the case, saying that it cannot tell. This holds in metalfx `group_left`, `lock_left` and `term_twice`,
and in stop-invariants `leave_stop`, `hook_sig` and the stray loop. In both check-bench files, `reap`
does the same through `reap_skip`. A PID that has gone is not a failure.

### Phase 3, round 2

**The reap lint.** `reap_lint <file> <helpers>`, in both check-bench files, prints every line that holds
the word `reap`. A word ends at any character other than a letter, a digit, `_` or `-`, so `reaped`,
`reap_skip` and `t_reap_id` are not the word, and neither is a path's `/reap`. Lines continued with a
trailing `\` are joined first. A line is let through only when it is a whole-line comment or lies in one
of the helpers: `reap`, `reap_skip`, `ended` (check-bench) or `reaped` (check-bench-entry), `reap_lint`,
`t_reap_id` and `t_reap_wait`. A function runs from a line that starts with its definition, a name
matching `[A-Za-z_][A-Za-z0-9_]*`, to the next line that starts with `}`. Code at the top level is not
exempt. No call form is exempt either. The four `reap "$BG" || true` lines in check-bench (`t_gate`,
`settle_put`, `t_quiet_marker`, `t_gate_poll`) now go through `ended 0 "$BG" || true`, which forgets a PID
that has gone and reaps one that has not, as before.

`t_reap_wait` checks the lint on a fixture. Each shape is written as the body of a function that
follows `ended`'s (or `reaped`'s), and each must be refused:
- `reap "$x"`, then the same followed by `; collect "$x"` or `; wait "$x"`, by `|| wait "$x"`, by
  `2>&1`, and by `2>&1; wait "$x"`;
- after `then`, after `else`, inside `{ ...; }`, and after `foo &&`;
- unquoted (`reap $x`), under `eval` (`eval reap "$x"` and `eval 'reap "$x"'`), and called through a
  variable (`r=reap; $r "$x"`);
- `wait_gone 60 "$_gp" || reap "$_gp"` (check-bench-entry);
- `reap "$x" || true`, alone and with `collect "$x"` or `wait "$x"` on the next line;
- a call split with `\`, after the name and inside it;
- a bare `reap "$x"` in `t_x2()` and in `Tx()`, and in `t_x2()` with no `}` before it.

The same step requires a plain `ended`/`collect` use and a plain `reaped` use to pass. The lint passes
on the branch's two files and refuses the four `reap "$BG" || true` lines in the round 1 file. The round 1
lint, run on the same fixture, refuses 2 of the 21 shapes in check-bench and 3 of the 21 in
check-bench-entry: only `reap "$x"` and `foo && reap "$x"`, plus entry's `|| reap "$_gp"`. The first
shape it lets through is `reap "$x"; collect "$x"` (`reap "$x"; wait "$x"` in check-bench-entry). These
are text runs and need no lock.

**A signal inside a decoy window.** `decoy` defines `kill`, and for `nops` also `ps`. Every EXIT and
signal trap in the four files now starts by removing the test overrides, before it signals anything:
- `cleanup` in both check-bench files: `unset -f kill ps`;
- the EXIT trap in check-metalfx-report: `unset -f kill ps wait`;
- the EXIT trap and the `HUP INT TERM` trap in check-stop-invariants: `unset -f kill ps`.

Today the round 1 trace does not reach `cleanup`. Each case runs in a subshell, `( cd ... && "$_t" )`.
The system `sh` does not run a subshell's EXIT trap on a signal unless the subshell has a trap of its
own for that signal. The main shell, whose `cleanup` does run on a signal, never defines `kill` or `ps`.
A probe showed it: a subshell with only an EXIT trap, sent a TERM, ended `Terminated: 15` without
running that trap. With `trap 'exit 1' TERM` added, it ran the trap. The first form of the new case
showed the same. It sent the TERM to a subshell that had only `trap cleanup EXIT`, and all three runs
failed with the `unset` already in place, because the trap never ran.

`t_decoy_term` therefore gives the shell it starts both traps, `trap cleanup EXIT` and `trap 'exit 1'
TERM`. In that shell, `cleanup` works on a list of its own. The shell lists a stand-in that ends on
TERM (and by itself within about 30 s) and opens a decoy window. It then waits there for at most 10 s,
and the case sends it a TERM. The stand-in must be gone within 5 s, for `other`, `none` and `nops`. The
case passes in under a second. The check-bench-entry file has no decoy window. Its only overrides are
the `ps` functions inside `t_reap_id`'s subshells, which have no trap, so its `unset` has no case.
