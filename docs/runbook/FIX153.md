# FIX153: a server's text cannot come back as the player's through `nextserver` or `nextdemo`

FIX151 ([its runbook](FIX151.md)) made the commands that refuse a server's use read
`Cbuf_ExecutingServerText()`, which is true while `Cbuf_Execute` runs a line that holds a byte a
server sent (FIX113's tag, [its runbook](FIX113.md)). Its round 3 recorded one way around that
check, the cvar-laundering path. This card closes it. Running console commands from a server or a
demo stays by design (CLAUDE.md, "Security-relevant boundaries").

## The path

1. A server line sets `nextserver` (it is never registered with `Cvar_Get`, so it has no flags),
   or sets `nextdemo`, which the next `SV_Map` without a `+` copies into `nextserver`
   (`src/server/sv_init.c`).
2. When a demo ends, `SV_DemoCompleted` (`src/server/sv_send.c`) calls `SV_Nextserver`
   (`src/server/sv_user.c`); when a cinematic ends, the client's `nextserver` command
   (`SV_Nextserver_f`) does.
3. `SV_Nextserver` queues the value with `Cbuf_AddText`, from `SV_Frame`, outside any server line,
   so the text is tagged as the player's, and a gated command in it runs.

## The choice: a server line may not set either cvar

The card names two designs. This one refuses the write: while `Cbuf_ExecutingServerText()` is
true, `nextserver` and `nextdemo` keep their value, and the console says
`<name> may not be set by the server.` The other design, tagging the value with its writer and
queuing it as the server's, was not taken, for three reasons.

- **One check covers every route.** The refusal sits in the three places the cvar layer writes a
  value (`src/common/cvar.c`, below), so `set` with three or four arguments, the bare cvar name,
  `inc`, `dec`, `toggle`, `reset`, `resetall`, the game module's `cvar_set` and `SV_Map`'s own
  writes all refuse a server line, with no list of commands to keep in step.
- **A tag has nowhere to live and further to travel.** `cvar_t` crosses the game API
  (`shared.h`), so it cannot take a field, and a side table would have to carry the tag through
  `SV_Map`'s copy of `nextdemo` into `nextserver`. It would also need its own answer for `set
  nextdemo ... a`, which writes the value to `config.cfg`, where the next launch reads it back as
  the player's text: FIX151 left that out of the threat model, and the refusal closes it too.
- **No stock flow needs it.** The attract loop's aliases (`d1`, `d2`, `d3` in the game data's
  `default.cfg`, of the form `demomap ... ; set nextserver d2`) are the player's text, and so is
  what `SV_Nextserver` queues from them. The game module does not write either cvar.

The check is by name, with the cvar layer's own case-sensitive compare, and only while a server
line runs: the player, the command line, `config.cfg`, `rcon` and the dedicated server (which has
no server text) set them as before. A refused write to a cvar that does not exist yet creates it
empty, so `Cvar_Set` still returns a cvar.

### The routes, and where each refuses

Line numbers are at `4956fe6b`. `Cvar_RefusedFromServer` is `src/common/cvar.c:365`.

| `inc`, `dec` (`cvar.c:856`), `reset` (`884`), `resetall` (`907`), `toggle` (`940`, `944`, `959`) | `Cvar_SetVar` | `cvar.c:384` |
| `SV_Map` inside a server line: the `+` suffix (`src/server/sv_init.c:584`), the copy of `nextdemo` (`589`), its clear (`591`), the coop victory value (`597`), also after `SV_Map` dropped server text earlier in the same line (round 2, below) | `Cvar_Set`, `Cvar_Set2` | `cvar.c:384` or `494` |

There is no `seta`, `sets`, `setu` or `cvar_set` console command in this tree: `set`'s fourth
argument is the archive, userinfo and serverinfo form. `Cvar_Get` writes only the engine's own
default, and `Cvar_GetLatchedVars` only a latched value, which these two cvars never have.

`SV_Map` run from a server line (`map`, `gamemap` or `demomap x.cin+y`, say) finds both of its
writes refused: the `+` suffix is not stored, and `nextserver` and `nextdemo` keep the player's
values. That is the server's text staying out, at the cost of a stale value in a flow no stock
data takes. Round 1 claimed this and was wrong on two paths, both of which drop server text inside
`SV_Map` before the write; round 2 below names them and fixes the primitive.

`SV_Nextserver`'s own clear (`Cvar_Set("nextserver", "")`, `src/server/sv_user.c:559`) is refused
too when `SV_Nextserver` runs inside a server line. A demo's `demomap <bsp>` line at the demo's
last chunk gets there: `SV_Map`, then `SV_SendClientMessages`, then `SV_DemoCompleted`. The
player's value is then queued as the server's text, since the line's source tags what it queues,
and stays set, so it can run again later. That is the safe direction: the player's own text runs,
refused where a server's is. No stock data takes it.

## Round 2: a line keeps its source for its whole run

Both round-1 reviews found the same gap. A server line such as
`map t.cin+x";upscale_textures;"`, or a demo's own `gamemap ...+...`, reaches `SV_Map`, and inside
that one command server text is dropped before the `+` suffix is written:

- **On a client that hosts no server** (`svs.initialized` false, `sv.state` `ss_dead`, the remote
  server's threat model): `SV_Map` calls `SV_InitGame`, whose client branch calls `CL_Drop`, then
  `CL_Disconnect`, then `Cbuf_DropServerText`.
- **On a demo** (`sv.attractloop`, or `ss_demo` for `map x.dm2`): FIX148's and FIX151's drop at the
  top of `SV_Map` calls `Cbuf_DropServerText`.

`Cbuf_DropServerText` also set the source to the player's (`src/common/cmdparser.c:177` at
`5984d259`), for the line that dropped. So when `SV_Map` then wrote `nextserver`,
`Cbuf_ExecutingServerText()` was false, the write was stored, and the value later ran as the
player's. The round-1 tests missed it: `ns_setup` hosts a local server in a game
(`svs.initialized` true) with no client connected, and the one `+` case was `demomap` on a
running cinematic, so neither drop ran. That is the class of earlier catches: a test stand-in
narrower than the real path.

**The fix is at the primitive.** A line that started as the server's stays the server's for its
whole run, whatever it drops. `Cbuf_DropServerText` removes the server's queued bytes, as before,
and no longer changes the source of the line that runs. The source returns to the player's only
where it must:

- at the start of the next line, which `Cbuf_Execute` already tags itself: it saves the source,
  sets the line's own (`cmdparser.c:357` and `385` at the round-2 head), and restores the saved
  one after `Cmd_ExecuteString` returns (`387`), so a drop inside a line ends with the line;
- when the line ends in `Com_Error`, which never returns to `Cbuf_Execute` (the case the old
  reset's comment was there for). An error ends the line that raised it, so `Com_Error`
  (`src/common/clientserver.c`) calls the new `Cbuf_ResetSource` (`cmdparser.c:191`) once, before
  its teardown (`SV_Shutdown`, `CL_Drop`) and so before either `YQ2_LONGJMP(abortframe, 1)`, for
  `ERR_DISCONNECT` and `ERR_DROP`. `ERR_FATAL` passes the same call and ends the process
  (`Sys_Error`). This is round 3's site; round 2 reset at the landings instead, after the
  teardown, which left the teardown's text the server's (see "Round 3" below). No landing resets
  the source now: `Qcommon_Frame`'s two (`src/common/frame.c`), `T_EXPECT_DROP`'s
  (`tests/unit/test.h`) and the runner's per-test one (`tests/unit/main.c`) are all reached
  through `Com_Error`. The one harness reset left is where a failed assertion's longjmp
  (`t_abort_test`) lands in the runner: it can leave a server line mid-run with no `Com_Error`,
  and the next test's lines must not be the server's. The engine has no such landing.

This fixes the class for every command gated on `Cbuf_ExecutingServerText()`, not only these two
cvars: `upscale_textures` and `in_probe script` refuse the rest of a server line after a drop
too. `SV_Map` saving the flag at entry would have fixed only its own two writes.

FIX148's and FIX151's tests pass unchanged. Their comments and names describe the old reset in
two places, and both still hold at the next line: `cl_drop_resets_source_to_player` and
`cbuf_executing_server_text_false_after_error_drop` reach the next line through `T_EXPECT_DROP`,
after `Com_Error`'s own reset. They test the engine's reset, not the harness's: with that one line
removed, both fail, and so does `cl_drop_while_disconnected_resets_source_to_player` (the round-3
proof). The second test's comment is updated to
say so. The comments in `SV_Map` (FIX151's "the rest of that line runs as the
player's") and above `Cvar_RefusedFromServer` are updated.

**What the primitive change does to the rest of such a line.** After a server line's `map` that
drops without an error, the rest of that command, including the local level load, now runs as
the server's text. Any gated command it reaches is refused, and what it queues is tagged as the
server's. A line that ends in an error is not such a line: `Com_Error` makes the source the
player's before its teardown, so everything the teardown queues is the player's, as it was on
FIX151's base, and the rest of the line never runs. The flows a stock server or stock demo
drives keep their behaviour:

- `CL_UpscaleAllowed` refuses for that load, but its only caller is the `upscale_textures`
  command (`src/client/cl_upscale_cmd.c`), which no level load runs.
- `SV_Map`'s writes of `nextserver` and `nextdemo`, the coop victory value among them, are refused
  for that line. That is the fix. Stock servers and stock demos send no `map`, `gamemap` or
  `demomap` line; the attract loop's and the game module's level changes are the player's text
  (`d1`, and `gi.AddCommandString` from `SV_Frame`).
- A stock server's `reconnect` (`CL_Reconnect_f`) reaches `CL_Disconnect` only from `ca_active`;
  after the `changing` the server sends first, it takes the `ca_connected` branch and drops
  nothing. Where it does drop, the rest of the command sets connection state and prints, and
  reaches no gated command.
- **The error route is the player's again (round 3).** A stock server's `precache` line
  (stuffed after the baselines, `SV_AddBaselines` in `src/server/sv_user.c`) runs `CL_Precache_f`,
  which loads the map (`CM_LoadMap`), then `CL_RequestNextDownload`. A
  player whose copy of the map differs gets `Com_Error(ERR_DROP, "Local map version differs from
  server")` there, inside the server's line (`src/client/cl_download.c`); `CM_LoadMap`'s own
  `ERR_DROP` on a modded server's map takes the same route. `Com_Error`'s `CL_Drop` runs
  `CL_Disconnect`, whose revert of `game` (`Cvar_Set("game", userGivenGame)`, when a modded server
  had set it) rebuilds the search path at once on a client with no local server
  (`FS_BuildGameSpecificSearchPath`): it queues `vid_restart` and `snd_restart` and execs the
  player's configs (`Qcommon_ExecConfigs`). In round 2 the source was still the server's there,
  so those lines were tagged as the server's text: a gated command in the player's own config was
  refused, and the tagged bytes could be thrown away by a later drop. Now `Com_Error` resets the
  source before `SV_Shutdown` and `CL_Drop`, so they are the player's, as on the base. This loosens
  nothing the fix needs: the error ends the server line, nothing in the teardown writes
  `nextserver` or `nextdemo` (only `SV_Map`, `src/server/sv_init.c`, and `SV_Nextserver`,
  `src/server/sv_user.c`, do), and the rest of the line, after the error, never runs.

Two non-stock flows change, both in the safe direction: they refuse or discard the player's text,
and no server text gets through.

- **A change of `game` inside a line that drops without an error.** The search-path rebuild above
  is reached from the non-error drops too: `CL_Disconnect`'s revert of `game`, from a server or
  demo line's stuffed `disconnect`, `connect`, `map` or `reconnect` from `ca_active`, and a
  latched `game` that `SV_InitGame`'s `Cvar_GetLatchedVars` applies, from a server line's `map`.
  `Qcommon_ExecConfigs` runs a nested `Cbuf_Execute` (`src/common/frame.c`), whose lines take
  their source from the current one (`cmdparser.c`, `Cbuf_Execute`), so every line it runs is the
  server's: the player's configs, and any player text already queued behind the server line. A
  gated command among them is refused. After a `wait` in `autoexec.cfg`, the rest of the file
  stays queued as the server's (`Cmd_Exec_f` inserts it under the server's source), and the next
  `Cbuf_DropServerText` discards it. No stock server or stock demo sends such a line. A server
  line's `game x` on a client with no local server already did the same before this card, through
  `Cvar_Set2`'s `game` branch, with no drop at all.
- **A demo's own `gamemap <level>` at the demo's end.** `SV_GameMap_f` leaves `ss_demo` in
  place, so after the demo drop `SV_Map`'s plain-level branch calls `SV_SendClientMessages`
  (`src/server/sv_init.c`). If the demo is at its end, that reaches `SV_DemoCompleted` and
  `SV_Nextserver` (`src/server/sv_send.c`) inside the demo's line. `SV_Nextserver` then queues the
  player's `nextserver` value tagged as the server's, and its clear (`Cvar_Set("nextserver", "")`)
  is refused, so the player's old value stays set until the next `SV_Map` the player runs
  overwrites it. This needs a crafted demo; stock demos send no `gamemap`. It is traced, not run.

## Also: `in_probe script` refuses a server line

In test builds only (`-DYQ2_INPUT_PROBE`, TASK23), `in_probe script <file>` queues a file's
lines as the player's. It now refuses while `Cbuf_ExecutingServerText()` is true and prints
`in_probe: a server may not start a script` (`src/client/input/sdl3.c`, `IN_Probe_f`). The unit
suite does not link `sdl3.c`, so there is no unit test; the build proof is below.
