# FIX158: a cvar value a server line wrote runs as the server's through `vstr` and `$`

FIX156 ([its runbook](FIX156.md)) made an alias or a bind that a server line wrote run as the
server's text whoever runs it. A cvar is the third stored body. A server line sets an ordinary cvar,
`set x "<gated command>"` (FIX153, [its runbook](FIX153.md), refuses only `nextserver` and
`nextdemo`). Later the player's own text runs `vstr x`, or uses `$x` in a line
(`Cmd_MacroExpandString`). Before this card the value then ran as the player's text, so a command
that reads `Cbuf_ExecutingServerText()` (FIX151, [its runbook](FIX151.md)) let it through. Running
console commands from a server stays by design (CLAUDE.md, "Security-relevant boundaries").

## The decision: a cvar value that server text wrote is the server's

This is FIX156's rule, for the same reason: the player picks when the value runs, the server picked
what it runs. Accepting the route as the player's choice (the card's third option) would leave
`vstr` as the one stored body that launders a server's text, beside two that do not. Refusing the
write outright, as FIX153 does for two cvars, would break every server and mod that stufftexts a
`set`.

### Who wrote a value

`cvar_t` crosses the game API, so it takes no field. `src/common/cvar.c` keeps a private side table,
`cvar_servermarks`, a list of cvar names: a name is in it while a server line wrote the value that
cvar holds. Every write of a value goes through `Cvar_SetVar`, `Cvar_Set2` or `Cvar_FullSet`
(FIX153's list), and each write that is not refused calls `Cvar_NoteWriter`:

- **A write from the player's line clears the mark if it changes the value** (round 2: see below;
  round 1 cleared it on any write). That covers `set`, `set ... a`, the bare `name value` form,
  `inc`, `dec`, `toggle`, `reset` and `resetall`.
- **A write from a server line sets the mark if it changes the value**, and leaves the owner as it
  was if it does not. This is FIX156's refinement for aliases: a server line that runs the player's
  `config.cfg` writes each archived cvar with the value it already has, and does not take any of
  them over.
- **An engine write outside any line keeps the mark as it is.** No text chose the value, so nothing
  says the player did. Keeping it is the direction that cannot let a server's value through, and
  the cost is small: a mark only changes `vstr` and `$` of that cvar, and only for commands that
  refuse a server's use. Clearing would hand the player any value the engine wrote back unchanged,
  and `Cvar_GetLatchedVars` applies a latched value the same way. "Outside any line" is
  `Cmd_ExecutingLine()`, a depth count of the `Cmd_ExecuteString` calls that run, kept in
  `src/common/cmdparser.c`. A write inside a line, the engine's own side effects of it included,
  belongs to that line's source. `Com_Error` ends every line, so `Cbuf_ResetSource` sets the count
  back to 0.

A refused write (FIX153's two cvars, a write-protected cvar, an invalid info value) changes nothing,
so it does not touch the mark either. For a latched cvar the value it takes next is the latched
one, so the latched write's writer owns the cvar from then on.

### `vstr`

`Cmd_Vstr_f` inserts a marked cvar's value with the buffer's source set to `CBUF_SERVER` for the
insert, and restores it after. This is the alias expansion's pattern. `Cbuf_InsertText` keeps the
source of the text behind the value, so the player's text after `vstr x` on the same line, or on
the next one, stays the player's.

### `$` expansion: the whole line is the server's

The two choices were to refuse to expand a marked cvar (empty, with a console line), or to make the
line that expands one the server's. This card makes the line the server's, for three reasons:

- **It is the rule the buffer already has.** A line with any byte the server sent is the server's
  (FIX113, [its runbook](FIX113.md)). The expanded bytes are the server's bytes, so the line is too.
- **Nothing that works today stops.** Refusing the expansion would change what every `$x` of a
  server-set cvar prints and does, for `say`, `echo`, `connect` and the rest. Making the line the
  server's changes only what reads `Cbuf_ExecutingServerText()`.
- **It carries through on its own, which makes it simple to get right.** The line's writes are the
  server's, so `set y $x` makes `y` the server's. An alias the line defines is the server's
  (FIX156), and so is what it queues (an alias body, an `exec`'d file).

The one cost: the player's `bind <key> $x` binds as the server's, so FIX156 leaves it out of
`config.cfg`. The binding is the server's value, so that is the rule working. A quoted `"$x"` is
never expanded, as before.

`Cmd_MacroExpandString` sets `cmd_macro_server` when it expands a marked cvar, at any depth of
its re-expansion. `Cmd_TokenizeString` clears the flag first. `Cmd_ExecuteString` is the only
caller that expands. It now wraps `Cmd_ExecuteLine`, the old body. `Cmd_ExecuteLine` raises the
source to `CBUF_SERVER` right after it tokenizes, if the flag is set. The wrapper saves the source
before the line and restores it after, so the raise lasts for that line's run only. The text queued
behind it keeps its own bytes' source.

## Left for a card

- **The `config.cfg` round trip, at a restart.** The in-session round trip is closed (round 2,
  below). What is left is a restart: `Cvar_WriteVariables` writes every archived cvar, and the next
  start runs `config.cfg` as the player's text, when no mark exists any more. A value a server
  wrote to an archived cvar (`set x "<gated command>" a`, or a cvar the engine archives) then comes
  back as the player's. FIX156 closed the same round trip for binds by saving the player's own last
  binding of each key. For cvars that needs the player's own last value of each archived cvar
  beside the live one, which is wider than this card. Skipping a marked cvar in `config.cfg`
  instead would lose the player's setting, and change what a server's write of an archived cvar has
  always done.
- **`reset` and `resetall` of a server-created cvar** (security note, round 1). A cvar a server line
  created has that value as its `default_string` (`Cvar_AddToList`), so the player's `reset x` or
  `resetall` writes the server's value from the player's text, which changes it only when it
  differs and then takes the cvar. The player starts it, and it is counted as the player taking a
  value back. A card could make `reset` keep the mark when the default came from a server line.
- **A latched cvar** keeps the server's live value in `var->string` until `Cvar_GetLatchedVars`, so
  `vstr` and `$` of it run the server's value as the player's until then. Unchanged from round 1.
- **Values the engine copies from what a server sent.** The client's own code writes some cvars from
  the server's data outside any line, the `game` directory from `svc_serverdata` for one. These
  are not marked. They hold a directory name or a number, not a command, and running one through
  `vstr` is not a use the engine makes.

## Round 2: a write that leaves a value unchanged never changes who owns it

Round 1's review found that a server could clear its own mark within one session, with no player
action:

1. A server line `set x "<cmd>" a` marks `x` and archives it.
2. The server's `game <dir>` (a stufftext line, or `svc_serverdata`) runs
   `FS_BuildGameSpecificSearchPath`, which calls `CL_WriteConfiguration` and writes
   `set x "<cmd>"` to `config.cfg`.
3. `Qcommon_ExecConfigs` then runs that file as the player's text. Its same-value write cleared
   the mark, so the server's value ran as the player's.

The rule is now symmetric: **a write that leaves a cvar's value unchanged never changes who owns
it, whichever source wrote it.** In `Cvar_NoteWriter` the player branch clears the mark only when
`changed` is true, as the server branch already set it only when `changed` is true. The player
takes a value back by writing a different value (`reset` and `resetall` count when they change
it). Every caller passes the real `changed`: `Cvar_SetVar` (latched unchanged, latched changed,
unchanged, changed), `Cvar_Set2` for a new cvar (a new cvar is a change), and both `Cvar_FullSet`
paths. On the latched path the comparison is against `latched_string` if there is one, else
`var->string`, which is the value the cvar takes next, so `changed` describes it.

The cost: a player who wants to claim a server's value as their own, unchanged, must write another
value first. A bind or alias is unaffected.
