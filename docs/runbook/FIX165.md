# FIX165: Cvar_WriteVariables refuses a value it cannot write back

Cause: `Cvar_WriteVariables` wrote `set <name> "<value>"` for every archived cvar. The tokenizer has no escape
(`COM_Parse` ends a quoted token at the next `"`), and `Cbuf_Execute` splits a line at a `\n` always and at a `;`
outside quotes. A value holding a `"` could therefore end its quotes early, and the `;` after it would start a
second command from `config.cfg` at the next start.

Reachability, traced in the source:

| Route | Can it produce a bad value? | Why |
|---|---|---|
| `set x "<v>" a` from server text or console | no for a quote inside quotes | `COM_Parse` ends a quoted token at the next `"`, so a quoted token holds none |
| `set x a"b;c"d a`, an unquoted word | yes | `COM_Parse` keeps a `"` inside a word. `Cbuf_Execute` counts quotes and does not split at a `;` while the count is odd, and `Cmd_MacroExpandString` and `Cvar_Set_f` accept the token. The value is `a"b;c"d` |
| `set x a"b;c a`, one lone quote | no | `Cmd_MacroExpandString` discards a line with an odd number of quotes ("Line has unmatched quote, discarded."); the test pins it |
| a raw `\n` from text | no | a newline always ends the line in `Cbuf_Execute`, so no token holds one |
| a `;` alone | harmless | written inside quotes, it does not split |
| `set "t_n;set t_n_inj pwned;set t_n_end" 1 a`, a quoted name | yes (round 2, proven by a run) | a quoted token may hold `;`, a space or a `$`; `Cvar_Set_f` creates the archived cvar with that name, and `Cvar_WriteVariables` wrote the name unquoted, so the next start ran three commands |
| userinfo and serverinfo writes | no | `Cvar_InfoValidate` refuses `\`, `"` and `;` for those flags. `set x v a` sets the flag word to `CVAR_ARCHIVE` alone, so the validation does not apply to it |
| engine code that sets archived cvars from external text (`Cvar_Set`, `Cvar_FullSet`) | possible in principle | the value is whatever the caller passes, newline and `\r` included, and nothing in `Cvar_Set2` or `Cvar_FullSet` checks it |

So one route is reachable: an unquoted word with two quotes and a `;` between them, sent as `svc_stufftext`.

The change, in `Cvar_WriteVariables` only: an archived cvar whose value (or name) holds `"`, `\n` or `\r` is
not written, and a console line names it. The tokenizer has no escape, so refusing to write is the primitive.
The cvar keeps its value for the session. A cvar that is not written keeps its default at the next start.

Test: `cvar_write_refuses_unsafe_values` (`tests/unit/test_cvar_cmd.c`). Red before the change: the
unsafe cvars were written (3 lines). Green after: none are written, the console names each, and a value with a
`;` inside quotes and a plain value are written as one `set` line each.

## Round 2: the name, and the property

Property: every line `Cvar_WriteVariables` writes, fed back through `Cbuf_Execute`, runs exactly one `set`
with the same name and value.

Form chosen: refuse (the first of the two forms), in `Cvar_WriteSafe`. A value holding `"`, `\n` or `\r` is
refused, as in round 1. A name is refused when it is empty, holds `;`, `"`, `$`, `//`, a byte `<= ' '` or a
byte `>= 0x7f`. Why this form: the file format stays what older builds wrote and read, and no cvar with such a
name exists in the engine, the game or any known mod, so nothing legitimate is lost. The quoted-name form would
also need the `$` and `//` analysis below to hold, and would still refuse `"`.

Parse facts checked, so neither can change the read-back:
- `Cmd_MacroExpandString` expands `$` only outside quotes, so a `$` in a quoted value is inert, and an unquoted
  name holding `$` would expand, hence the name refusal.
- `COM_Parse` skips `//` only at the start of a token, but a name that starts with it is a comment, and one that
  holds it is refused to keep the rule simple.

FIX153 answer: it refuses only `nextserver` and `nextdemo`, so it does not cover a hostile cvar name or value.

The bind writer has the same shape and is FIX166 (#624), out of scope here.

Test: `cvar_write_refuses_unsafe_values` now creates archived cvars with hostile names and values, writes the
config, resets the safe ones, runs every written line back and asserts that exactly the four safe lines
restored their values and that no injected cvar exists. It uses `t_tmpdir()`. Red on `c2aebdf7`: the `\n` name was refused, and the space name and the `t_n;` name were written.

## Round 3: replay every line, and the length

- The test now replays every written line through `Cbuf_Execute` with no filter and asserts that the total cvar
  count does not grow (no injected cvar), then that each safe cvar holds its own value again.
- A `;` name with no spaces (`t_w_semi;set_t_n_inj3`) is in the cases and the written text must not hold
  `t_w_semi;`, so removing the `;` check from `Cvar_WriteSafe` fails the test.
- Length rule: `Cbuf_Execute` truncates a line of 1024 bytes or more, so the read-back would run no set.
  `Cvar_WriteSafe` refuses a cvar whose line, `set <name> "<value>"` plus the newline (name + value + 8 bytes),
  is 1024 bytes or more. The test pins both sides: `t_w_len` (1023 bytes) is written and restored, `t_w_lenx`
  (1024 bytes) is refused.
