# FIX170: FS_FOpenFile never opens a path outside its search paths

Cause: `FS_FOpenFile` (`src/common/filesystem.c`) stripped `./`, `//` and a leading `/` from a name but not
`..`, then joined the name onto each search directory. A server's `svc_serverdata` with `playernum == -1`
reaches `SCR_PlayCinematic` (`"video/%s"`, or `"pics/%s"` for image extensions), so a name such as
`../../../file` read a local file outside the search paths into the cinematic or image decoder. Read-only,
nothing goes back to the server, but untrusted parsers saw arbitrary local files.

The rule: `FS_NameEscapes(name)` is true when any `/`- or `\`-separated component is exactly `..`.
`FS_FOpenFile` runs it after the clean-up, so `.//../x` is refused too, and returns -1 as for a missing file
(with `*f == 0`). It logs each refusal with `Com_DPrintf`, at most 64 bytes of the name. `a..b` and `..foo` are not
escapes. Stock game data has no `..` component, so what loads is unchanged.

The check and the join must read the same string. `FS_FOpenFile` copies the name into `handle->name`
(`MAX_QPATH`, 64 bytes) and joins that onto the search paths, so a name of `MAX_QPATH` bytes or more is
refused before the copy, as for a missing file. A longer name was truncated, could never match a pak entry or
a real asset, and truncation could leave a trailing `/..` that the check had not seen. Stock names are well
under 63 bytes.

Every other open of a name that can come from the network:

- `FS_LoadFile` and `FS_LoadFile2` open through `FS_FOpenFile`: covered. That covers the map `.ent` override,
  models, skins, images, sky and textures (the renderers' `ri.FS_LoadFile`), and sounds.
- The CD track: `OGG_PlayTrack` (`src/client/sound/ogg.c`) joins the server's `CS_CDTRACK` string (also a map's
  `music` key) onto each search path with `Q_fopen`, past `FS_FOpenFile`. It first calls `FS_TrackNameValid`,
  which refuses a track containing `/` or `\`, and `.` and `..`: a track is a bare file name under `music/`. A
  refused track plays nothing, as for a missing one, and is logged with `Com_DPrintf` (`%.64s`). The other
  `Q_fopen` in `ogg.c` opens a name from the local directory listing, not from the network.
- `FS_FOpenFile` has no write mode (`handle->mode = FS_READ`): nothing to check.
- The pak lookup (`FS_PackQuickSearch`) compares the name with directory entries in memory. A pak entry name is
  not a path on disk, so `..` in it opens nothing outside the pak. The loose-file join is behind the new check.
- `FS_FileInGamedir` is called from `FS_FOpenFile` only for the fixed names `maps.lst` and `players/...`
  and after the check.
- The download opens (temp and target) are gated by `CL_DownloadFilter`, which rejects `..`, a leading `.` or `/`,
  `:` and library extensions, and by `FS_CreatePath`, which refuses `..`.

Tests (`tests/unit/test_filesystem.c`, `fs_name_escape`): `../x`, `a/../../x`, `.//../x`, `a\..\x`, `a/..` and `..`
are refused although a file exists one level above the search directory; `a/b.txt`, `a..b.txt` and
`..foo/x.txt` open. A 64-byte name is refused although its 63-byte truncation exists as a file; the 63-byte name opens.
`fs_track_name` tests `FS_TrackNameValid`: `../../x`, `a/b`, `a\b`, `.`, `..` and the empty name are refused,
`track02` is accepted. `ogg.c` is not linked into the suite, so the helper is tested and `make client` confirms
`ogg.c` calls it. `cl_cin.c` is not linked either, so the cinematic path is tested through `FS_FOpenFile`
directly.

Round 3: a refusal skips only the open. Round 2 returned from `OGG_PlayTrack` as soon as `FS_TrackNameValid`
failed, which skipped the `strtol` handling after the open loop. An empty `CS_CDTRACK` (a map with no `music`
key) is refused by the helper, so the previous map's music kept playing where the base stopped it ("track 0
stops the music"): a gameplay change. Now a refused name only skips the `FS_NextPath`/`Q_fopen` loop (a
`trackValid` guard on the loop) and execution continues into the base's `trackNo` handling. The refusal is
logged with `Com_DPrintf` except for the empty string, the normal "no music" case.

Comparison with the base (`0fc28371`), per input; "open" is the `Q_fopen` of `<path>/music/<track>`:

| Input | Base | Head |
| --- | --- | --- |
| `""` | open of the `music/` directory path (normally fails, or fails as not Ogg), then `trackNo` 0: stop | no open, `trackNo` 0: stop (same; no log line) |
| `"0"` | open `music/0`, not found, `trackNo` 0: stop | same (valid name) |
| `"2"` | open `music/2`, not found, `trackNo` 2: numeric `track02` handling and shuffle | same (valid name) |
| `"track02"` | open `music/track02`, plays it if present, else `strtol` gives 0: stop | same (valid name) |
| `"../x"` | open `music/../x`, plays it if present, else `strtol` gives 0: stop | no open (the only difference); `strtol` gives 0: stop, as on the base |
