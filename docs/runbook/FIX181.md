# FIX181: the bench lock holds when a bounded command cannot be stopped

## What was wrong

[FIX172](FIX172.md) made the bench core hold the lock when it cannot identify a command that leads no
group: `bench_lock_stop_child` keeps the lock (`bench_lock_hold_untold`) while the command's PID
answers `kill -0`. The bounded path did not. `bench_on_signal` (`scripts/bench/bench.sh`) stopped the
bounded command with `bench_stop_group` and took no notice of its status 2 (no group, no identity,
nothing sent). The shell then exited, and the lock it ran under was freed while the bounded command
could still run. This needs a shell without job control (dash with no terminal) and a silent `ps`.

## The fix

`bench_on_signal` keeps the stop's status. On 2 it calls `bench_lock_hold_untold` with the bounded
command's PID, as `bench_lock_stop_child` does for the lock's command, and exits only when the hold
ends: when the PID is gone, when another process has it (another start time), or when a renewed stop
succeeds. A command that leads its group, or whose identity `ps` reads, is stopped as before.

The hold renews its stop of the bounded command, once `ps` answers again, with the bounded command's
grace (`BENCH_STOP_GRACE`, as `bench_bounded` and the first stop in `bench_on_signal` use), passed as
the new optional second argument of `bench_lock_hold_untold` (round 1). Without it the hold used the
lock's grace (`bench_lock_grace`), which is also the grace a lock shell gives the `bench.sh` it runs.
So after a TERM to the lock shell, the lock shell's KILL to that `bench.sh` could come before the
hold's KILL to the bounded command, and the lock was freed while the bounded command ran. The lock's
own hold (`bench_lock_stop_child`) passes no grace and is unchanged.

The stop's status is caught with `|| _os_r=$?`, so that under `set -e` a status of 2 does not end
the trap before the hold. That part is traced, not tested: every call site of `bench_bounded` today
runs under an `||` (directly, or through `adapter_run ... || _ro_st=$?` in `core/measure.sh` for the
null adapter), and the trap then runs with errexit off, so no case can tell the two forms apart.

The hold's lines go to the standard error the stop's lines already use: the one in effect where the
bound was called (fd 8, [FIX172](FIX172.md) round 1). Every call site of `bench_bounded` but the null
adapter puts that on `/dev/null` or a log file, so there the hold is seen in `bench.sh lock status`
(`lock=held`, `alive=yes`), not as a line. Moving the bench's lines to the shell's own standard error
would need a new descriptor that every spawned command inherits, and is left out.

## The case

`t_core_id`, in `tests/check-bench.sh`, case "bounded hold": `dash bench.sh lock run` of
`dash bench.sh host`, with a failing `ps` and a `system_profiler` stand-in on `PATH` that writes its
PID and its parent's and runs `sleep 3`. Neither shell has job control, so the bounded command leads
no group. Once the stand-in's parent is seen to be the lock shell's child, the case sends TERM to
that inner `bench.sh` alone.

- The lock is still held 1.5 s later, while the bounded command runs.
- The lock shell exits 143 once the command has ended, and the lock is free.
- Every process the case starts is recorded for its cleanup; nothing else is signalled.

On `26f3a70c` (the start point) it fails with
`core-id: bounded hold: the lock was freed while the bounded command it could not stop still ran:
lock=free`. With the fix it passes.

Case "bounded hold, lock shell" (round 1) is the same run with `BENCH_STOP_GRACE=1` (a lock grace of
6 s), a `ps` that is silent only for the bounded command while a flag file is there, and a stand-in
that ignores TERM and runs `sleep 15`. With the flag there, TERM goes to the inner `bench.sh`, which
holds; 1.5 s later the lock is still held, and TERM goes to the lock shell; 1.5 s after that the flag
goes, so `ps` answers again. The hold's KILL to the bounded command must come before the lock shell's
KILL to the inner `bench.sh`: the case fails if the bounded command still runs when the lock shell
has exited (and so freed the lock), and ends it by its identity before it reports. On `37167564` it
fails with `core-id: bounded hold, lock shell: the lock shell exited, and so freed the lock, while
the bounded command still ran`. With the fix it passes.

## Limits

Two limits of [FIX172](FIX172.md) are now written in its "What is left": a group signalled while `ps`
is silent after a full PID wrap, and the hold ignoring INT, TERM and HUP (only a KILL ends it early,
and `bench_lock_alive` then still keeps the lock while the lock's command runs).

The bounded hold had one more, closed by [FIX184](FIX184.md): the lock shell could not see the hold,
so a TERM to the lock shell, with `ps` silent for the bounded command, ended the hold with the lock
shell's KILL after the lock grace and freed the lock while the bounded command might still run; and
the 125 path freed it with no signal at all. The bounded command is now recorded in the lock state
and the lock shell's release waits for it. Once `ps` answers inside the lock grace, the hold's own
KILL still comes first (round 1); the "bounded hold, lock shell" case now also bounds the lock shell's
exit to 8 s after `ps` answers, since the release would otherwise keep the lock until the bounded
command's own end.
