# FIX157: pin runs must not depend on console notify text timing

Card: FIX157 (#615). Stacked on FIX155 (merged in #661). Scope: the pin harness, a new check, this
runbook and its index line. No engine source change, no new cvar or command.

## The cause, from FIX155

A line printed to the console is drawn by `Con_DrawNotify` (`src/client/cl_console.c`) over every frame for
`con_notifytime` seconds of wall time. The Retro report line was one, and pin frame 12 sometimes still carried it.
FIX155 moved that one print to stderr. Any other console print during a run would do the same, so the harness
no longer lets one reach a frame.

## The launch change

`scripts/pins.sh`, `build_args`: the driver's own arguments now hold `+set con_notifytime -1`, between
`r_customheight` and `s_initsound`.

- It is -1, not 0. `Con_DrawNotify` skips a line when `cls.realtime - time > con_notifytime * 1000`. `cls.realtime`
  is set once for each client frame, so a line printed in the frame that draws it has an age of 0, and 0 is not over
  0: `con_notifytime 0` would still draw a line printed in the current frame. With -1 every line is over the limit.
- It does not reach a player's `config.cfg`. `con_notifytime` is created with flags 0 (not `CVAR_ARCHIVE`), so it is
  never written; and a pin run is `-portable` with pin capture on, which neither reads nor writes `config.cfg` (the
  harness header), so it uses the binary's own directory, not the player's.
- `record` is the only command that runs the live client for a pin. `replay` feeds the recorded calls, in which a
  console draw is a recorded call or not; `make-demo` captures nothing. Both are left as they were.
- No scenario needs the notify text: none opens the console or sets `con_notifytime`, so none is declared. (`hud2d`'s
  "console text" is the status bar's and the layout's, not the notify area.) A scenario that sets `con_notifytime`
  gets the driver's value after its own, as for every other cvar the driver sets.

## The check

`tests/refrecord/charscan.c` (about 190 lines of C, built against the real `src/client/vid/refrecord.c`) reads a
`trace.q2r` and prints, for every frame the run captured (a `REC_CAPTURE` record in the frame) between the first
and last frame that draws the 3D view or a raw cinematic picture, the capture number and the number of
`REC_CHARSCALED` calls, if not 0. `pins.sh` compares those lines with the demo's table,
`scripts/pins/text/<demo>-every<PINS_EVERY>.txt`: the text the demo itself draws with the notify lines off
(`demo1.dm2` at every 30th frame: captures 5, 14, 18 and 21, with 11, 7, 7 and 7 characters, the same in all 23
stock `demo1` scenarios). A demo with no table declares none. A difference makes `record` mark the pin incomplete
and write the difference to `text.txt` beside the frames; `pins.sh check-text <trace> [demo [every]]` runs it on one
trace. The text a demo draws in frames no pin captures is not checked: it changes no pin.

`tests/check-pin-chars.sh` (in `tests/ci-checks.txt`: it needs a compiler only) checks the launch line, and
runs `check-text` on traces made by `charscan --make` through the real recorder: text in a captured demo frame
fails and names the frame, the same text in a frame no pin captures passes, a trace with none passes, and a file
that is not a trace fails.

## The outcome: frame 22 of every `demo1` pin changes (only by its removed character draws)

Every 23-frame `demo1.dm2` scenario drew one console notify line (78 characters, one row of the console) in pin
frame 22, printed by the demo near its end, a few frames before the capture. It was the same in all of FIX155's
runs, so it was stable, but it was notify text, and `con_notifytime -1` removes it. So the head's pins are not
byte-identical to FIX155's for those scenarios, and the card's expectation that they would be does not hold:

- Compared frame by frame with FIX155's head (`world`, `world-scale8`, `hud2d`, `models`, `rt-sun`, `hdr`, and
  `retro` and `retro-filter` run 1): frames 0 to 21 are byte-identical and only `000022.tga` differs. All 23 of the
  23-frame scenarios record a different run hash, for that one frame.
- Byte-identical to FIX155's hashes: `cinematic` (12 frames, `83cda5a3ee9b`), `skywater` (`bd6e66d3c43a`), `rt-water`
  and `rt-water-entities` (`60b1e91c2456`): `water.dm2` and the cinematic print nothing in a captured frame.
- `retro` and `retro-filter`: two runs each on the head are the same (`86bb4b4b5585`, `642b7b733363`), frame 12 is
  the common variant (`1cdbb957ffc5`, `553feccfd961`), and each `engine.log` holds the report line once.

The one-line way back, if the owner wants FIX155's frame 22 kept: take `+set con_notifytime -1` out of
`build_args` and `pin 22 78` back into the demo's table. Then the notify text of the demo stays in the pins, and
the check still catches a stray line anywhere else.

## Round 2: the check passes only a trace it has read to the end

Round 1 found that `check_trace_text` kept only the `pin` lines of charscan's output, so a trace charscan refused
(bad header, unfinished) gave an empty list, which equals the empty table of a demo with none (`water.dm2`, `.cin`):
it passed. The record path had the same hole when `cc` was missing.

- `scripts/pins.sh`, `check_trace_text`: charscan's exit status is taken apart from the `pin` filter. A scanner that
  cannot be built is "could not build the scanner"; a trace it cannot read is "charscan could not read the trace";
  both refuse, with or without a table. `record` also needs `cc` and `diff` unless `PINS_TRACE=0`.
- `PINS_TRACE=0` writes no trace, so there is nothing to read and no text check: `doc/100_renderpins.md` now says
  the check follows a record that writes a trace. (Chosen over a "not checked" file, so the doc and code agree
  with one sentence.)
- `tests/check-pin-chars.sh` runs a junk file and half of a real trace with `synth.dm2`, `water.dm2` and `demo1.dm2`
  and requires the refusal text. With `return 1` changed to `return 0` for the bad header in a scratch copy of
  `charscan.c`, the check fails on six cases: junk and half a trace are accepted with `synth.dm2` and `water.dm2` (four), and refused for
  the wrong reason with `demo1.dm2` (two).
- `build_tool` (new) builds `charscan` and `framediff` to a temporary name and moves it into place; `charscan` also
  depends on `src/client/vid/header/refrecord.h`. `difftool` had the same flaws and uses it too.
- An empty table no longer prints a blank `> ` line.

Frame 22 differs only in text. Read with a scratch reader on the trace format, the frame holding `REC_CAPTURE` 22:

## Round 3: a missing or cut-short trace is a refusal too

- `scripts/pins.sh`, `cmd_record`: with `PINS_TRACE` not 0, a `trace.q2r` that is absent makes the record incomplete,
  with the reason "the engine wrote no trace.q2r, so no text check was made". The engine exits 0 when it cannot open
  the trace file, so before this the text check was skipped. `PINS_TRACE=0` asks for no trace and is not refused.
- `tests/refrecord/charscan.c`: a trace with `REFREC_FLAG_TRUNCATED` set is refused ("the recorder stopped at its
  limit"), as `replay` refuses it. `tests/check-pin-chars.sh` flips the flag in a copy of a good trace and requires
  the refusal for a demo with a table and one without.
- Selftest (`scripts/pins.sh selftest`): the fake engine now writes a stub trace beside its frame (made by the new
  `charscan --make-table` from the demo1 table, so it declares exactly that text), and `FAKE_NOTRACE=1` omits it.
  `record_engine` has a case where the engine writes frames and a manifest but no trace: refused, `incomplete`
  names the missing trace; the same with `PINS_TRACE=0` passes; a truncated stub trace is refused.
- `build_tool`: a failed `mv` removes the temporary file before it dies.
- Round 2's mutant count is corrected above: with `return 1` changed to `return 0` for the bad header, the check
  prints six failures (`junk.q2r` and `half.q2r` each accepted with `synth.dm2` and `water.dm2`, and each refused
  for the wrong reason with `demo1.dm2`).
