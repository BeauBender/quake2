# FIX192: `ios-device.sh` on INT leaves nothing running, at any runner speed

## What happened

On a CI runner, `scripts/ios-device.sh --selftest` failed in `sign-int-hang` (PR #719), and the
`ios-device int` disposition probe of `tests/check-bounded-run.sh` failed (main, the push of #719):

```
ios-device: selftest: FAIL sign-int-hang: the fake (PID 43605) still runs after the script exited
check-bounded-run: probe: ios-device int: caller exit 137 (hung: killed by the probe); child runs; grandchild runs
```

Both pass on the bare-metal host. In the same CI run, the `term`, `kill` and `wall` probes of
`ios-device.sh`, and every probe of `pins.sh` and `ios-sim.sh`, passed.

## The trace

**Both failures are one cause, and it is a real defect, not an assertion that looks too early: the
script never acts on the INT.** It keeps watching its command until the command's limit, so the probe
kills it after 60 s and the selftest's launcher after 10 s, and the command and its children are left
running. The INT is not lost by the script's code: bash 3.2 drops it. The probe runs the script with
`/bin/bash` (3.2.57); the selftest runs it with the `bash` on `PATH`, which on this host is `/bin/bash`
too (which `bash` the runner's `PATH` gave was not checked).

### Where bash drops an INT

bash 3.2's `wait_for` (`jobs.c`), the wait for a foreground command, swaps its own SIGINT handler in
for the trap's whenever job control is off (`if (job_control == 0 || ...) old_sigint_handler =
set_signal_handler (SIGINT, wait_sigint_handler)`). Outside the `wait` builtin, that handler only
notes the INT (`wait_sigint_received = 1`). The trap is run from the note in one place only:
`set_job_status_and_cleanup`, when the command is reaped, and only for a job in the jobs table. So an
INT that comes while bash waits for a command that has already finished is noted and never run:

- a command substitution: bash reads its output to the end first (an INT then runs the trap), then
  waits for it with the swapped handler. A command substitution has no job, so an INT from the end of
  its output to the reap is never run;
- a plain foreground command: an INT after its reap and before bash puts the trap's handler back
  (read from the source; this one was not staged, since its window is inside bash).

The primitive's watch (`bench_watch`, under `bench_bounded`) spends its time in exactly these waits:
every poll is a `ps` command substitution (`bench_proc_read`), a `date +%s` one, and a `sleep`
(`bench_nap`), with job control off (`bench_spawn` turns it on only around the fork). On this host the
windows are too short to hit (the unstaged probe and selftest pass); how long they are on a runner was
not measured. TERM, QUIT and HUP are not affected: bash swaps no handler for them, which fits the CI
run, where only the INT probe and an INT case failed.

The bash behaviour, alone (a trap on INT, the INT sent 0.3 s in):

| the shell runs | the trap ran |
|---|---|
| `sleep 1` | yes |
| `x=$(sleep 1)` (the output still open) | yes |
| `x=$(exec >&-; sleep 1)` | no |
| `x=$(exec perl -e 'close STDOUT; select(undef, undef, undef, 1)')` | no |
| `x=$(perl -e 'close STDOUT; select(undef, undef, undef, 1)')` (bash keeps the output open while perl runs) | yes |

### The staged reproduction

A scratch copy (`git archive`), in which `bench_proc_read`'s command substitution, once a stage flag
file exists, closes its standard output after `ps` has answered and lingers 1 s before it exits, with
INT ignored (an exiting process is not ended by it), after it writes a marker: the window a slow exit
opens, made 1 s long. Nothing else changes; the stage is off until the flag is made.

- **The probe** (the `ios-device int` probe of `check-bounded-run.sh`, alone, against the copy): once
  the stand-in and its grandchild run, the flag is made; once the marker is there, the INT. Three runs
  out of three: `ios-device int: caller exit 137 (hung: killed by the probe); child runs; grandchild
  runs`, the CI line. The same copy with no flag: `caller exit 1; child gone; grandchild gone`.
- **The selftest** (the copy's selftest, its signal cases only; each launcher makes the flag once the
  fake hangs and sends its signal once the marker is there): two runs out of two, `FAIL sign-int-hang:
  the fake (PID N) still runs after the script exited` and the same for `install-int-hang`; the TERM,
  QUIT and HUP cases pass in the same staging.

The selftest's message is misleading: its launcher had killed the hung script, so the fake was left
running, but the case checked the fake before the hang. With the verdict below, the staged selftest
says `FAIL sign-int-hang: it outlived 10 s after the INT, and so did the fake (PID N)`.

### Ruled out

Each with a 2 s sleep staged in the scratch copy's primitive and the INT sent in it, two runs each,
the probe and the selftest's signal cases: after the fork with job control still on, after it is off,
between `bench_spawn` and the pid stored, inside `bench_undefer`, and at the start of the watch. The
INT is deferred and acted on in every one (`caller exit 1; child gone; grandchild gone`, the INT cases
`ok`). A slow `ps` (a shim on the probe's `PATH`, 0.3 s and 1 s per call) and the INT sent from 0 to
3 s after the stand-in started (twenty delays) pass too.

### Found on the way: HUP in the start window

The same staged sleeps between the fork and `bench_undefer` make `sign-hup-hang` fail, every run: `the
fake (PID N) still runs after the script exited`. HUP is not in the script's trap list (`trap 'on_signal
1' INT TERM QUIT`); bash ends by it and runs the EXIT cleanup, whose `stop_child` finds no command yet
(`BENCH_BOUNDED_PID` is set only after `bench_spawn` returns), so the deferral does not cover it. This
is not the CI failure; it is fixed here too, since it is in the same file (below).

## The fix

### The primitive waits for its polls with the wait builtin

`scripts/bench/core/common.sh` gets `bench_poll <command...>`: the command (a function of the shell,
or any command) runs in the background, and the shell waits for it with the `wait` builtin. bash 3.2
runs the trap at once for an INT in the `wait` builtin (its SIGINT handler there sets the trap pending
and leaves the wait), so a poll step no longer has a window. While `bench_watch` watches a command,
every step of a poll of its own goes through it: the ps read (`bench_watch_read`, which hands the
state back as its status: 10 a zombie, 11 stopped), the clock (`bench_past`, the `date +%s`
comparison) and the nap (`bench_nap`, everywhere it is used). The watch so waits for no foreground
command and no command substitution of its own.

- **Nothing is left running.** The poll job's pid is `BENCH_POLL_PID` until it is collected. A trap
  that ends the shell calls `bench_deferred` (every caller of `bench_bounded`) or bench.sh's
  `bench_on_signal` (the lock shell) first, and both call `bench_poll_end`, which sends the poll TERM
  and collects it. The poll is a child of this shell that the wait has not collected, so its pid is
  not another process's. A deferred signal (one that comes while a command starts) does not stop the
  poll; the trap returns and the wait goes on.
- **The waits are bounded.** A trap that returns ends the `wait` early (status above 128) and leaves
  the job running or uncollected. The wait goes on while the pid is there (running, or exited and not
  reaped), and once it is not, one more `wait` collects the status. bash keeps a collected job's
  status and gives it again (a TERM'd job: 143 the second time too, checked on 3.2.57), so the loop
  keys on the pid, not on 127. Each wait past the first needs a signal in the one before, and there
  are at most 100.
- **A Ctrl-C reaches the trap, not the poll.** The poll runs in the shell's process group with INT and
  QUIT ignored, as a background job of a shell without job control does.
- **The until test** stays in the shell, as before: it is the caller's code, and
  `check-bounded-run` pins that a test that unsets itself is refused at the next poll, which a
  subshell would not see. So a foreground command in it keeps the window: pins.sh's
  `pins_map_missing` is a `grep`, run at every poll of the engine.

`ios-device.sh` traps HUP too (`trap 'on_signal 129' HUP`, and `on_signal` ignores it with the rest
while it stops the command), so a HUP between `bench_spawn` and `bench_undefer` is deferred, and
`bench_undefer` stops the command. It exits 129, as the untrapped HUP did through the EXIT cleanup.

### What changed for the callers

Exit codes, the TERM, grace and KILL of every stop and every line the primitive prints are unchanged.
A signal now runs the trap at once at every poll step. Before, a TERM to the lock shell (`bench.sh
lock run`) waited for the current nap to end, up to 1 s (`lock.sh`'s comment said so, and now says
this); a Ctrl-C ended the nap's sleep, so it ran at once before too. The ps read and the clock each
cost one fork more than before (the background subshell); the nap costs the same.

### Not changed

The waits outside the watch keep their foreground commands: `bench_spawn_id` (the spawn's record, in
the window `bench_undefer` covers), `bench_end_group` (after the command has exited) and
`bench_stop_groups` (the stop, which a trap runs with the signals ignored). An INT in one of their
command substitutions' windows can still be dropped. The gate's scheduler (`scripts/gate-checks.sh`)
traps INT, TERM and HUP with a plain `exit`, so a nap of its stop (0.1 s at most) can outlive it.

## The proofs

### Pinned cases, red then green

Each stages the window: a copy of the primitive in which the ps read (`bench_proc_read`), once a stage
file exists, closes its output after ps has answered and lingers, INT ignored, until the signal is sent
(10 s at most), once. The stage's anchor is the ps read itself, which the fix does not change, so the
same stage applies before and after it.

| case | before (fb76c3d8) | after |
|---|---|---|
| `check-bounded-run`: `ios-device int-window` | `caller exit 137 (hung: killed by the probe); child runs; grandchild runs` | `caller exit 1; child gone; grandchild gone` |

### The disposition probe

`ios-device.sh install` under `/bin/bash` (3.2.57) runs a stand-in (a child and a grandchild, alive
while a flag file exists). A staged copy makes one step of the watch's poll, once a stage file exists,
record the pid of the poll job it runs in and linger there; once it lingers, the signal goes to the
script. Read once the script has exited, before the step is released (a scratch probe; the column for
the poll job turns to `runs` in every row when `bench_deferred` does not call `bench_poll_end`):

| step | INT | TERM | QUIT | HUP |
|---|---|---|---|---|
| ps read | exit 1 | exit 1 | exit 1 | exit 129 |
| clock (`date`) | exit 1 | exit 1 | exit 1 | exit 129 |
| nap (`sleep`) | exit 1 | exit 1 | exit 1 | exit 129 |

In every one of the twelve, the script exited within 0.1 s of the signal, and the child, the grandchild and
the poll job were gone.
