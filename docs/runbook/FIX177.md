# FIX177: the bench test helpers say "cannot tell", never "gone", when ps gives no answer

## What happened

FIX171's phase 3 review traced this in `tests/check-bench.sh` and `tests/check-bench-entry.sh`.
`pid_running` read liveness from `ps -o stat=` alone. When `ps` failed or printed nothing, it said
"not running". So `wait_gone` returned 0 at once, `reap_skip` and `reap` took the PID as ended, and
`ended`, `finish`, `reaped` and `run` went on to `collect` or `wait`. That wait was bounded only by the
child ending by itself. FIX171's comments said such a PID "gets no signal; that is a failure, and reap
is false". That held only when `ps -o lstart=` failed and `ps -o stat=` did not, the one case
`t_reap_id` fakes.

## The fix

The same helpers in both files:

- **`pid_running <pid>`** is three-valued. 0: the PID runs. 1: it has gone, or it is a zombie. 2: the
  check cannot tell, because the PID answers `kill -0` but `ps -o stat=` gives no answer for it.
  - Liveness comes from `kill -0`, which needs no `ps` and sends no signal. It is called as `command kill`,
    so a case's `kill` function (check-bench's `decoy`) never sees it.
  - A zombie answers `kill -0`, so `ps` is still what tells a zombie from a running PID, and only when it
    answers.
  - `kill -0` also fails for a process another user runs (pid 1, which `t_reap_id` reads). Then `ps`
    decides when it answers. Every PID these checks wait for is their own user's, so a PID that fails
    `kill -0` while `ps` gives no answer has gone.
- **`wait_gone <seconds> <pid>`** returns 0 only once the PID is seen gone. Past its bound it returns 1
  while the PID still runs and 2 while the check cannot tell. A silent `ps` never makes a PID gone.
- **`reap_skip`** is false in both cases. For 2 it says `reap: no TERM|KILL to pid <pid>: it answers kill
  -0 and ps gives no answer for it, so the check cannot tell whether it still runs, and it is not waited
  for`, and it counts the failure. `reap` is therefore false too. `listed_same` already failed, since
  `pid_id` needs `ps`, so no signal goes.
- **`finish`** (check-bench) is false when `ended` is, rather than going on to compare a status it never
  read.

`ended`, `reaped` and `run` needed no change of their own: each was already false (or set `ST` to 124)
when `reap` was, and `reap` now is.

## Cases

`t_reap_wait` in each file gains one kind per caller, in which `ps` is a function that returns 1 for
every call. The child, a shell that notes a TERM and goes on, is listed with its own identity in
check-bench and with none in check-bench-entry, since `record` there already runs with `ps` failing.

| file | kind | the caller |
| --- | --- | --- |
| check-bench | `finish:nops` | `finish reap-wait <pid> 0 1` |
| check-bench | `ended:nops` | `ended 1 <pid>`, then `collect` when it is true |
| check-bench-entry | `run:nops` | `run 1 <command>` |
| check-bench-entry | `reaped:nops` | `reaped <pid> 1` |

Each kind must:

- return within 10 s. Each one returns in about 1 s: `ended`'s or `run`'s 1 s bound, then `reap_skip`'s
  bound of 0;
- count the failure;
- say that it cannot tell;
- send no signal (the child's TERM file stays empty);
- take the PID as not ended. Every kind checks this, the older ones included: `finish` and `reaped` are
  false, and `run` sets `ST` 124.

The FIX106 zombie case (`t_lock_zombie_waiter`) still passes: `ps` answers there, and a `Z` state is gone.
