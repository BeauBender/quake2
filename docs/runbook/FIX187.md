# FIX187: check-gate-parallel's tdesc case stops its shell only once the shell has started its sleep, and fails with its own reason when the shell never shows T

## What happened

On PR #698 (which touches no gate code) the `invariants_macos` CI job failed in
`tests/check-gate-parallel.sh`, case `tdesc`:

```
check-gate-parallel: tdesc: the stop line does not name the stopped shell: check-gate-parallel: tty: stopped: [pid=79069 stat=S< pgid=61716 comm=/bin/sh args=/bin/sh -c sleep 30; : sh a\cb p\nq x\012y]
```

The case started `/bin/sh -c 'sleep 30; :' ...` in the background, started a second `sleep 30`
and a `sh -c 'exit 0'`, waited for the last one, then sent the shell `kill -s STOP`. It polled
`ps -o stat=` for a `T` 25 times, 0.2 s apart, and when no `T` showed it went on as if the shell
were stopped. `ps` showed `S<`: the shell had exec'd (its args are its own) and was sleeping in
its wait for `sleep 30`, not stopped. The same head passed in the merge gate on the build host.

## The trace

The card named two candidates. Neither holds.

**(a) The gate continues the shell.** Nothing in the gate sends SIGCONT.

- CI does not run `scripts/test.sh`. The job runs `scripts/ci-checks.sh`, which `exec`s
  `scripts/gate-checks.sh "" "" <checks>` with `GATE_JOBS=2`.
- `scripts/gate-checks.sh` sends signals in `gate_kill` alone, called from `gate_end`. That runs on
  the group of a check whose leader has already ended (`gate_reap`) and, on the way out, on the
  groups of the running checks (`gate_cleanup`). The signals are TERM, then KILL. No CONT anywhere.
- `scripts/test.sh` (the build host's gate) sends TERM in three places: its lock watcher to this
  run's own group, only after its parent changed (only under the lock), `gate_unwatch` to the
  watcher's group, and `gate_stop` to the scheduler. No CONT. Its FIX176 slice 2 work changed
  where a forked child's standard error goes. It added no watcher that acts on stopped processes.
- The shell is in the check's own process group (`gate_start` makes each check a group leader
  with `set -m`; `check-gate-parallel.sh` runs its background jobs without job control, so they
  stay in its group). That group keeps a member whose parent, the scheduler, is in another group
  of the same session for as long as the check runs, so it is never orphaned. The kernel's SIGCONT
  to a newly orphaned group that has a stopped member does not apply.
- `git grep` for CONT finds two senders. One is the fake check's `stopprobe` (case `sigs`), which
  continues the fake check itself. The other is `bench_stop_group` in `scripts/bench/core/common.sh`,
  which stops a group that `bench_spawn` started. Neither reaches another check's process.

Stand-in (`fix187-standin.sh`, run from the scratch directory, not committed): the scheduler as CI
runs it, `GATE_JOBS=2`, on two checks. `check-a.sh` starts the shell, stops it once its sleep child
exists, and sees `T`. It then writes the `stopped` flag and holds until the scheduler's scratch
directory has `2.end`, so `check-b.sh` has ended and `gate_end` has run on its group. Then it reads
the shell again. `check-b.sh` waits for the `stopped` flag and exits. Each process saw this:

```
a: after STOP: T    95479 (check-a pgid 95479)
a: check-b reaped and its group ended; shell now: T
b: saw a's stop; ending (pgid 95483)
standin: 0 of 10 runs saw the stopped shell continued
```

**(b) A slow runner, 5 s of polling not enough.** A longer wait would not have helped: the STOP
was lost, not late.

**What does hold: a STOP sent while the just-forked child is still in its exec is lost.** The case
sent the STOP after its other two forks and one wait, with nothing that showed the shell had
finished its exec. On a loaded runner that exec can still be running when the STOP is sent. This host shows the loss (`fix187-exp2.sh <mode> <n>`,
run from the scratch directory, not committed: n children, each stopped and then read until `T` or
3 s):

| Mode | The STOP is sent | Not stopped |
|---|---|---|
| `now` | right after the fork of `/bin/sh -c 'sleep 30; :'` | 26 of 100 (12 of 40 and 11 of 40 in two earlier runs) |
| `sleep` | right after the fork of `/bin/sleep 30` | 10 of 40 |
| `pre` | while the forked child waits on a flag file before its `exec` (the flag is set after the STOP) | 0 of 20 |
| `child` | once a child of the shell's pid exists (the shell has exec'd and forked its sleep) | 0 of 100 |

Every lost one reads as `S    /bin/sh -c sleep 30; : sh a`: the exec'd shell, sleeping and never
stopped. That is the CI line. A STOP that reaches the forked child before its exec stops it (`pre`).
One sent during the exec can be dropped (`now`, `sleep`). No flag file can hold a process inside
`execve`, so the exec window itself is shown by counts, with the `pre` and `child` modes as the
controls. The case fixed below waits on state alone.

## The fix

`c_tdesc` (in `tests/check-gate-parallel.sh`):

1. **The STOP waits on state.** It is sent only once a child of the shell's pid exists (`tkids`).
   Then the shell has exec'd and is in its own command, and a STOP is no longer lost (`child`: 0 of 100).
2. **No false verdict.** It then waits for `T` in the shell's `stat`. If `T` never shows within 30 s
   (150 polls of 0.2 s, a ceiling that only a hang reaches), the case fails with
   `tdesc: the shell never showed state T (stat=<stat>)`. None of the stop-line or `tsort` assertions run
   (they are in `tdesc_lines`, called only once `T` showed). A shell that never starts its sleep fails
   the same way, with `the shell never started its sleep (stat=...)`.
3. The shell and the other sleep run `sleep 120`, which outlasts both ceilings. With `sleep 30` a shell
   that never stopped would have ended by the 30 s ceiling, and the reason would read `stat=` (empty).
   The stop-line pattern names `sleep 120`.

The gate's scheduler and `scripts/test.sh` are unchanged: neither acts on a check's stopped child.

## Mutant

| Mutant | Change | Caught by |
|---|---|---|
| `tdesc-cont` | `kill -s CONT "$_dp"` right after the STOP | `ttyself tdesc`, only with its own reason: `tdesc: the shell never showed state T (stat=` |

To make a mutant's reason part of its catch, `c_ttyself` takes a second argument, `<want>`. A run
that fails without `<want>` in its output passes the case, so the mutant counts as not caught.
`smut` passes a sixth argument through as `<want>`. Without the fix the same mutant fails with the
old misleading line (`the stop line does not name the stopped shell`), so `<want>` would not match.

There is no mutant that restores the old STOP right after the forks: the loss it lets in is a race
(about 1 in 4 on this host), and a mutant caught only some of the time would be a timing flake. Cause (a)
does not hold, so there is no watcher mutant either.
