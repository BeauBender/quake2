# FIX179: the bench tests' negative pid assertions fail on "cannot tell"

## What happened

FIX177 made `pid_running` in `tests/check-bench.sh` and `tests/check-bench-entry.sh` three-valued: 0 the
PID runs, 1 it has gone, 2 the check cannot tell (it answers `kill -0` and `ps` is silent). Its review
found that the callers which assert a process has ended still read 2 as ended:

- `if pid_running X; then bad "...outlived..."; fi` is false for 2, so a live process went unseen.
- `pid_running "$_sl" || forget "$_sl"` runs `forget` for 2 as well as 1 (`||` fires on any nonzero), so a
  PID the check could not read was taken off the cleanup list and never stopped.
- `stray_stop`'s `pid_running "$1" || return 0` returned for 2 too; the old form went on to `pid_same`,
  which needs `ps` and also returned 0, so a stray process was skipped without a word.

## The fix

One helper per site kind, in each file that has the kind:

- `outlived <pid> <text> [<reporter>]` (both files): fails with `<text>` while the PID runs, and with
  `cannot tell whether pid <pid> outlived it, ps gives no answer for it: <text>` for 2. The optional
  reporter is for the sites that do not use `bad` (`nok` in `t_core_id`, `bfail` in `t_bounded`'s
  subshell, which prints and exits).
- `forget_ended <pid>` (check-bench): forgets only for 1. For 2 the PID stays on the cleanup list and the
  case fails.
- `stray_stop` (check-bench-entry): for 2 it sends no signal and counts `cannot tell whether pid ... still
  runs`.

## Sites

Negative assertions, now `outlived` (check-bench): `t_lock_stop` (six: the grandchildren on TERM, INT and
STOP, the stubborn command, the work a command left, `gc.left`), `t_lock_defer` (`d.gc`), `t_bounded`
(four, reporter `bfail`), `t_core_id` (two, reporter `nok`: `lock: ps silent` and `lock: no group`, last
check). In check-bench-entry: `t_nested` (the watcher), `t_cleanup_id` (stray_stop's stop), `t_grace` (the
check and the scheduler, written out because it names both; 2 is its own message).

`forget`: `t_lock_stop`'s `pid_running "$_sl" || forget "$_sl"` is `forget_ended`. The other `forget`
calls follow a `wait`, a `wait_gone` that returned 0 or a collect, and need no change.

`stray_stop`: its one `pid_running "$1" || return 0` (the others are its callers).

Positive checks, unchanged, with 2 read as running (the PID answers `kill -0`, so it exists, and only a
zombie is unknown): `t_cleanup_id` and `t_reap_id` ("a signal went to X" and "was it still there"),
`t_decoy_term` (the decoys were not ended), `t_lock_ps_fails`/`t_core_id`'s "the command is still
running" branch, the `tokens` holder check, the `give-up` waiter, and the polling loops
(`while ... pid_running`), which only wait for a PID to leave or to show a line. Each of those is
satisfied by "it still exists".

## Cases

`t_cant_tell` in each file starts a `sleep 30`, then makes `ps` a function that fails for every call, with
a `kill` function that logs any signal (`pid_running` calls `command kill`, so it does not reach it).
Each kind must count a failure, say `cannot tell whether pid <pid> `, send no signal and leave the sleeper
alive; `forget_ended` must also leave the PID on the cleanup list. The case ends the sleeper itself.

| file | kind |
| --- | --- |
| check-bench | `outlived`, `forget_ended` |
| check-bench-entry | `outlived`, `stray_stop` |

On the commit that routed the sites through the helpers with their old behaviour every kind was red (no
failure counted, nothing said, and for `forget_ended` the PID dropped from the list); on the fix both
files are green.
