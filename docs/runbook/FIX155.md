# FIX155: why Retro's frame 12 is nondeterministic

Card: FIX155 (#613). Stacked on TASK197 (`aad7ccc4`, reviewed, not merged). Scope: `src/client/refresh/metal/`
for the fix, this runbook and its index line.

## Starting evidence (FIX152)

FIX152 recorded `retro` and `retro-filter` seeded (`PINS_SEED=1`) on Metal at 640 x 480, `demo1.dm2`, 23 frames,
24 runs in two holds: TASK185's head `7550c9bc` and FIX152's branch `2d176b7f`, three rounds each, in one order
in the first hold and the opposite order in the second.

- Frame 12 flipped in `retro` and in `retro-filter`, on both builds; the other 22 frames never changed.
- 4 of the 24 runs were odd, with 2 distinct run hashes (`065cfd5ceed3` for `retro`, `5bbafb4d2dbf` for
  `retro-filter`; the common ones `3846977baf63` and `c4ad064a365a`). 3 of the 4 odd runs were the first run
  of their scenario row.
- FIX152 did not vary the shared Retro path (`rmb_post_pass`, the scratch copy): it compared builds whose
  Retro code is the same, so that path was not ruled out by it.
- PM4 (TASK186) records the Retro pins, so it stays blocked until FIX155 settles this.

## The source: the Retro report line, drawn as a console notify line for a wall-clock time

`RM_GB_Begin` (`rm_gbufscene.c`) prints TASK185's report line (`ref_metal: retro: 3D layer drawn at ...`) once
at the first Retro 3D view. It printed it with `R_Printf(PRINT_ALL, ...)`, so it went to the console. The
first view comes after the loading plaque has cleared the notify lines, so the console drew the line, four
rows of text at the top of the screen, over every frame for `con_notifytime` (3 s) of real time. At the
harness's rate (about 120 fps, `689 frames, 5.7 seconds`), 3 s from the first demo frame (frame 17 of the
trace) ends at demo frame 375 to 378, and pin frame 12 is trace frame 377. Whether frame 12 still carried the
four rows depended on the wall clock, so it took one of two hashes. Pin frames 0 to 11 always carried them;
frames 13 to 22 never did.

Stock prints nothing to the console after the plaque, so its frames hold no text: the `world` trace of
TASK197's store has no character draw in any demo frame (and runs at the same `119.9 fps`). That is why only
Retro flipped, and why it flipped at the same frame and rate with and without the filter.

### The evidence: the renderer was handed different calls

Every record writes `trace.q2r`, the calls the engine made into the renderer. A scratch reader (not committed)
walked the traces of FIX152's 24 runs frame by frame. The traces of a rare run (`2d176b7f` run 1, line
expired at frame 378) and a common one (run 2, expired at 376) differ in the loading console's frames 0 to 16
and the closing frames 705 and 706, which no pin frame captures, and otherwise only in frames 376 and 377,
where the rare run still has 312 `Draw_CharScaled` calls, the four rows of the report line, and the common
one has none. In the demo's frames (17 to 704) every `RENDERFRAME` (the refdef, the time, the view, the
lightstyles, the counts) and every other record but the character draws is identical. So the renderer drew a
different frame 12 because it was handed different 2D draws, not because a GPU pass read undefined memory or
raced the CPU; the Retro passes, `rmb_post_pass` and its scratch copy included, drew the same input the same
way (and the fixed build below is stable through the same passes).

All 24 FIX152 runs, by the first trace frame after the first capture with no character draw (the frame
where the notify line had expired):

| Line expired at trace frame | Runs | Characters at pin frame 12 (trace frame 377) | Frame 12 |
| --- | --- | --- | --- |
| 375 | 4 | 0 | common (`1cdbb957ffc5` / `553feccfd961`) |
| 376 | 9 | 0 | common |
| 377 | 7 | 0 | common |
| 378 | 4 | 312 | rare (`a48739457447` / `190a77b65001`) |

The 4 rare runs are exactly the 4 runs whose line was still on screen at frame 377; none of the 20 others
was. The trace sizes say the same (7064252, 7071740, 7079228 and 7086716 bytes, 7488 bytes, one frame's 312
character records, apart; the rare runs are all 7086716). Pin frame 0 has the 312 characters in all 24.

### The bisect

The card's toggle bisect was not run: the traces named the source before any toggle was built, and the
toggles would not have separated it. With the line on the MOTION path's begin, toggle (b) (no forced MOTION
path) would have made frame 12 stable only because it skips the print; (a) the upload quantize, (c) the
480-line target (which does nothing at 640 x 480, where the target is 480 lines already) and (d) the Retro
post-process would each have left the flip, since each leaves the print. The hold went to the fix's runs
instead, in which the before and after builds are compared directly (below).

## The fix

`rm_gbufscene.c`, `RM_GB_Begin`: the report line goes to stderr (`fprintf(stderr, ...)`), as the attachments'
line of `rmb_gbuf.m` does. It is still printed once for each target and render size, it is still in the
run's log (`engine.log` holds stdout and stderr), and it is no longer in the console, so no frame draws it.
Nothing else changes: no cvar, no API, no protocol or savegame change, and stock never reaches the print.
TASK185's runbook quotes the line from the log; it reads the same there.
