# FIX169: svc_serverdata's game directory is validated before it is stored

Property: the client never stores a game directory the filesystem would refuse.

Cause: `CL_ParseServerData` (`src/client/cl_parse.c`) copied the server's game string into `cl.gamedir` and
`Cvar_Set("game", ...)` unchecked. `Cvar_Set2` stores the value first (`cvar.c`), then calls
`FS_BuildGameSpecificSearchPath`. On a refused directory (`.`, `..`, `/`, `\`) that function printed a message and
returned without touching the cvar, so the client stayed connected with the old search paths while `game` held the
refused string until disconnect. Read paths use it (`src/client/sound/ogg.c` formats it into `"%s/music/"`). The
filesystem's only reset of `game` (`Cvar_FullSet("game", "")`) runs for `""` or baseq2, not for a refused
directory. It also let control bytes and `:` through.

The rule, `FS_GameDirValid` in `src/common/filesystem.c` (prototype in `common.h`): the empty string is valid
(it means baseq2); anything else is refused if it is `.`, contains `..`, `/`, `\`, `:`, or a byte below
space or 0x7f. `FS_BuildGameSpecificSearchPath` uses it, so its behaviour changes only for values with `:` or
control bytes.

The parser calls it before `cl.gamedir` and the cvar are written. On failure it calls
`Com_Error(ERR_DROP, "Server sent an invalid game directory")`: a server that sends one is broken or hostile.

The drop replaces "stay connected with a polluted cvar", not a fallback to baseq2: main never fell back. A drop
leaves `game` and `cl.gamedir` unchanged and ends the connection, which is the safe failure for a broken or
hostile server.

Trade-off: the rule also refuses `:` and control bytes, which are legal in POSIX directory names and which the old
check accepted, and it applies to a local `+set game` too. That is accepted: the card asks for `:` and control
bytes to be refused, no real mod directory uses them, and one rule for every writer is simpler than two.

Other writers of `game`, none a client-side network read, so left alone: `cl_network.c` `CL_Disconnect`
restores `userGivenGame` (the client's own startup value); the `game` cvar on a listen server is the local user's.
No `svc_configstring` path writes it.

Left for a card: a server's `svc_stufftext` can still run `game ../x`, unfiltered by design. The raw value stays in
the cvar and in `userGivenGame` (restored at disconnect), and only read paths use it (`ogg.c`). Option: make
`FS_GameDirValid` gate the cvar write for `game` itself.

Tests, `tests/unit/test_cl_parse.c`: `"x\ny"`, `"a/b"`, `".."`, `"a:b"`, `"a\\b"`, a name holding 0x7f and a lone `"."`
drop and leave `game` and `cl.gamedir` unchanged; `"ctf"` and `""` are accepted. A direct `FS_GameDirValid` table
test covers the same cases.
