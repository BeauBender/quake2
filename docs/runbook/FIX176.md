# FIX176: check-gate-parallel's tty case names the process that stopped (slice 1), and the gate's starts keep a forked child's line off the terminal (slice 2)

## What happened

On 2026-11-21 a merge gate went red on the `tty` case of `tests/check-gate-parallel.sh` with
"the run stopped on a terminal with tostop (test.sh pid N), and was ended by pid". FIX174 made
the case read the state of every process descending from `test.sh`, and one was in a `T` state, but the
line named only test.sh's pid. Nothing said which process wrote to the terminal from a background group.

## Slice 1: the message

On a stop, `c_tty` reads, before it ends anything, each process that descends from `test.sh`
(`tsort`). Each one in a `T` state is described by `tdesc <pid>`: pid, `stat` and `pgid` (one `ps`
call), `comm` and `args`. The stop line is `tty: the run stopped on a terminal with tostop (test.sh
pid N), and was ended by pid; stopped: [pid=.. stat=T.. pgid=.. comm=.. args=..]`. The other processes'
`pid=stat` go on one `tty: state:` line below it, as many whole entries as fit in 200 characters
(`tcut`). A pid that is gone between the snapshot and its `stat` read is on neither line. A slow run
prints its one timed-out line and no state line.

- **Printed as it is.** `say` and `bad` print with `printf '%s\n'`. macOS `/bin/sh` is bash in sh mode
  with `xpg_echo`, so its `echo` decodes backslashes, and `ps` keeps a backslash in args and writes a
  newline as `\012`: with `echo`, `\n` split the stop line and `\c` cut it and joined the state line to
  it. No `say` or `bad` call relies on an escape: the backslashes in their arguments are inside
  command substitutions.
- **No home path.** `comm` and `args` both go through `tscrub`, which joins its input on one line,
  prints the home directory as `~` and cuts to 120 characters. HOME is read with `ENVIRON["HOME"]`
  (`awk -v` decodes backslashes) and loses its trailing slashes. It is replaced only where a `/`, a space
  or the end of the text follows it, so `/Users/qqzz` stays as it is under `HOME=/Users/qq`. A space
  counts as an end because args is the words of a command line: `cd /Users/qq && ...` loses the path
  too. HOME empty, unset or `/` replaces nothing.
- **A stop ends the wait.** `c_tty` waits with `lwait <bound> keep tstopped <dir>`. Every 5 polls (1 s)
  `tstopped` reads one `ps` snapshot. Once a process that descends from the recorded `test.sh` is in a
  `T` state, the wait ends as at the bound. Nothing sends SIGCONT, so a stop never resumes. A run with
  no `T` waits out its full bound. Its line says how long it waited (`timed out after N s`, from the
  polls counted, not from the bound).

In the `ttymsg` mutant (the scheduler without its SIGTTOU ignore) the stopped process is the scheduler's
shell, the one that runs `gate-checks.sh` under `test.sh`. That case runs it with `HOME=/bin` and pins
`comm=~/sh args=~/sh`.

## Cases

- `tdesc`: a `/bin/sh -c 'sleep 30; :' sh 'a\cb' 'p\nq' "<x newline y>"` that the case starts and stops.
  `tdesc` through `say` prints exactly one line, ending in `]`, with the args as `ps` writes them. `tsort`
  on that shell, a running sleep and a pid that has exited puts the shell alone on the stop list, the
  sleep alone on the others' list, and the gone pid on neither. `tcut 200` on 60 entries keeps whole
  entries, 193 to 200 characters.
- `scrub`: `tscrub` on fixed text for each kind of HOME: a plain path, a trailing slash (one and two), a
  prefix that is not at a boundary, `/`, empty, unset, a backslash in HOME, a match that overlaps a
  longer name, two lines, and 200 characters.
- `ttymsg`: the stop (scheduler mutant, `HOME=/bin`): one stop line naming pid, `stat=T`, pgid, `comm` and
  `args` (`~/sh`), no path under `/bin` left, args within 120 characters, ending with `]`. Then one state
  line matching `state:( [0-9]+=[^ T]+)+`, holding test.sh's pid, within 200 characters. The slow run
  (3 s bound, 20 s hold) says `timed out after 3 s`, never tostop, and prints no state line.
- `ttylate`: `check-a.sh` holds 3 s, then writes to `/dev/tty` and stops (mode `holdtty`). With a 30 s
  bound, the run is reported as a stop after at least 3 s and before 30 s.
- `ttyself [<cases>]`: those cases (by default `tdesc scrub ttymsg ttylate`), run by the self-test in a
  process of its own, so a mutant of the self-test is run. Each `smut` line names the cases it needs.

## Slice 2: the writer

### Cause

The process that stops is a child that bash has just forked for a background start, before its
redirections and its exec. There are three such starts: `scripts/test.sh` starting the scheduler,
`test.sh` starting its lock watcher (only under the host lock), and `gate_start` in
`scripts/gate-checks.sh` starting each check. With job control on (`set -m`), bash makes the new
process group on both sides of the fork. Under load on macOS the child's `setpgid` can fail with EPERM
after the parent's call has made the group. bash then writes `child setpgid (<pid> to <pid>): Operation
not permitted` from the child, to the standard error the shell had before the command's redirections.
This is the same line [FIX83](FIX83.md) found in the bench lock's fork.

In the tty case that standard error is the `script(1)` terminal, set to `tostop`. The child is already
in its new group, which is not the terminal's foreground group, and its `SIGTTOU` is at the default
(`gate_start` restores it just before the fork, for the check, and test.sh never ignores it). So the write stops the child: a `T`-state
`sh` that leads its own group, before it has run anything. Nothing resumes it, so the run hangs. In
`ttylate` this happens at test.sh's start of the scheduler or at check-a.sh's start, before check-a.sh's
3 s hold begins. The probe sees the stop at its first read (1 s), so the case reports the stop after 1 s,
not 3 s: "the run ended in 1 s, inside check-a.sh's 3 s hold". In `tty` the same stop gives the tostop
line. A gate with no terminal (CI, the merge gate's checks) is not stopped: the line is written to a file
or a pipe there. Only the tty cases, which make their own terminal, show it.

### Evidence

- **The line, without a terminal.** A loop of 1,000 `set -m; /usr/bin/true ... &` starts under bash 3.2
  (`/bin/sh`), with no added load (1-minute load 4.6), wrote 2 `child setpgid` lines. A second loop
  read each job's pgid right after `$!`: of 1,000 starts under the contention below, 2 wrote the line,
  and both pids it named already led their own group.
- **The stop, on a tostop terminal.** The same starts on a `script(1)` terminal with `stty tostop`,
  from the foreground group (as test.sh starts the scheduler): 1 of 400 children stopped with no added
  load, `stat=T`, `pgid` equal to its own pid, `comm=sh`. The same probe under the contention below saw
  no stop in 1,500 starts from the foreground group and none in 1,500 from a background group (the
  scheduler's form): the line is rarer there than in a plain loop, so this probe gives no rate.
- **Deterministic.** xtrace makes the child write a line in the same place every time: the child traces
  the command it is about to run. `sh -x` of a three-line script (`set -m`, a start, `ps` of `$!`) on a
  tostop terminal left the child in `T` (pgid its own, comm `sh`). With the start in
  `{ ... & } 2> /dev/null` the child ran and ended.
- **The real case.** Under the contention below, `origin/main`'s three scripts: `ttylate` 30 runs, none
  failed; `tty` 30 runs, 1 failed (run 8):

  ```
  tty: the run stopped on a terminal with tostop (test.sh pid 14723), and was ended by pid; stopped:
    [pid=15218 stat=T pgid=15218 comm=/bin/sh args=/bin/sh scripts/gate-checks.sh  check-metalfx-report.sh ...]
  tty: state: 14723=Ss+ 14732=S 15251=S
  ```

  14723 is test.sh (the terminal's session leader and foreground group). The other two are running
  descendants (by their pids, the scheduler and a later child; their commands are not printed). The
  stopped process has the scheduler's own command line, so it is a fork of the scheduler that has not
  yet exec'd, and it leads a group of its own, so it is a job-control fork: `gate_start`'s start of a check, stopped before its redirections. (A command substitution's child
  stays in the scheduler's group.) The FIX172 sighting in `ttylate` is the same stop at the start of
  check-a.sh or of the scheduler, read at the probe's first poll, 1 s in.

### Fix

Each of the three starts runs inside a brace group whose standard error is `/dev/null` for the fork
alone, as FIX83's `bench_spawn` does:

- `gate_start`: `{ "$_gsc" < /dev/null > "$_gd/$1.log" 2>&1 & } 2> /dev/null`. The check writes into its
  log as before.
- test.sh's scheduler: `{ 2>&3 3>&- GATE_PARENT=$$ scripts/gate-checks.sh ... & } 3>&2 2> /dev/null`.
  fd 3 carries test.sh's standard error past the fork, and the scheduler gets it back as fd 2, with fd 3
  closed. The redirections come before the assignment so that the `wiring-*` and `no-parent-pid`
  mutants' text still applies.
- test.sh's watcher: `{ sh -c "$gate_watch_sh" ... & } 2> /dev/null`. It writes nothing anyway.

A closed standard error would break the scheduler's start: its `3>&2` fails, the group never runs, and
`gate_sched=$!` takes the last background pid. Under the lock that is the watcher's, so test.sh waits on
the watcher, holding the lock (review round 1). The lock's re-entry keeps a closed one, since `lock.sh`
runs the command with a plain `exec`. So test.sh starts with `bench_spawn`'s guard, the FIX83
primitive: `{ :; } 3>&2 2> /dev/null || exec 2> /dev/null`. This sits at the top rather than before
the start, because outside the lock a closed one already ended test.sh, on `origin/main` too, at the
"host lock is off" line (`set -e`, status 1, no output).

The `child setpgid` line is lost. It is harmless: the parent's call has made the group (the pgid
loop above), and `launch` in the self-test already keeps the same line out of its output for the same
reason.
