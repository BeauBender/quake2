# FIX148: server and demo text that outlives the connection, after FIX113

FIX113 ([its runbook](FIX113.md)) tags each byte of the command buffer and of the defer buffer
with its source and drops the server's bytes when the connection ends. Its review found three
older paths around it. Running console commands from a server or a demo stays by design (see
CLAUDE.md, "Security-relevant boundaries"); this card is about commands that are meant to refuse
during a demo or on a remote server.

## 1. A demo's text reaching a local game

A demo's `svc_stufftext` is tagged as the server's. When that text starts a local game that is
not a demo (`map`, `gamemap`, or the `nextserver` text a finished demo queues), `SV_Map` runs
from inside the demo's own line. On the `ss_game` branch, `SV_SpawnServer` is followed by
`Cbuf_CopyToDefer`, which parks the rest of the buffer with its tags, and the client's arrival in
the new game (`SV_Begin_f`, `Cbuf_InsertFromDefer`) runs it there: in a local game that is not a
demo, where the demo leg of a gate such as `CL_UpscaleAllowed` lets it through.

`gamemap` from a demo does not pass `SV_InitGame` (the server is not `ss_dead`), so no
`svc_reconnect` reaches the client and FIX113's drop on that message does not apply. `map` does
pass `SV_InitGame`, whose `SV_Shutdown(..., true)` sends `svc_reconnect`, but it parks the text
first and relies on the client reading that message before it reconnects.

The fix, at the top of `SV_Map` (`src/server/sv_init.c`): when the running server is a demo
(`sv.attractloop`) and the new one is not, `Cbuf_DropServerText()` runs before anything else. The
demo is treated as the connection its text came from. The player's text stays, in its order.
What does not change:

- The map change exception of FIX113: a local game's own `changing`/`reconnect` flow, and a
  `gamemap` from a game to a game, keep the server's text, as before.
- A demo that follows a demo (`demomap`, the demo loop's `nextserver`) keeps it too: the new
  server is a demo, and the gate still refuses there.
- A remote server's text that starts a local game already ends with the connection:
  `SV_InitGame` with no local server calls `CL_Drop`, which runs `CL_Disconnect` and
  `Cbuf_DropServerText` (FIX113).
- `load` from a demo calls `SV_InitGame` before `SV_Map`, and `SV_Shutdown` clears `sv` there, so
  `SV_Map` no longer sees the demo. That path is the `map` one above: `SV_Shutdown(..., true)`
  sends `svc_reconnect`, and FIX113's case for it drops the server's text in both buffers before
  the client can reconnect.

"A demo" is `sv.attractloop`, the flag the server sends in `svc_serverdata` and the client keeps
as `cl.attractloop`, which is what the gate reads.

## 2. The one-byte overrun

`Cbuf_CopyToDefer` writes the terminator at `defer_text_buf[cmd_text.cursize]`. `Cbuf_AddText`
refuses to fill the command buffer, but `Cbuf_InsertText` writes the old text back through
`SZ_Write`, whose `SZ_GetSpace` allows a buffer filled to the last byte, so `cursize` can equal
the buffer's size and the terminator lands one byte past the end. `defer_text_buf` is now one byte
longer than `cmd_text_buf` (`src/common/cmdparser.c`), so the copy keeps all the text and its
terminator; `defer_text_src` follows its size.

## 3. Aliases and `nextdemo` set by a server: out of the threat model

A server can define an alias, or set `nextdemo`, that runs later as engine-queued text tagged as
the player's: the console key's `Con_ToggleConsole_f` queues `d1` when disconnected, and
`SV_Map` copies `nextdemo` into `nextserver`, which `SV_Nextserver` queues when a local demo,
cinematic or picture ends.

The decision: out of scope, no code change. A server may run any command by design, and defining
an alias or setting a cvar is a command. What FIX113 guards is the gated commands' own refusal
against text the server itself queued, and that text is dropped. Each of these later runs starts
from a player action:

- `d1` from `Con_ToggleConsole_f` needs the player's key press; the menu's `d1` after a game
  change (`FS_BuildGameSpecificSearchPath`, `menu_startdemoloop`) needs the menu; the start-up
  `d1` (`Qcommon_Init`) runs before any server, and aliases do not survive a restart.
- `nextdemo` reaches `nextserver` only when a local map starts (`SV_Map`), which the player does.

One path is borderline and is reported to the owner, not fixed here: `set` with the `a` flag
archives a cvar, so a `nextdemo` a server set that way is written to `config.cfg` and survives a
restart. The start-up demo loop (`Qcommon_Init` queues `d1`, an alias from the game data) starts a
local map, and `SV_Map` copies `nextdemo` into `nextserver` then, unless the alias sets
`nextdemo` before it starts the map; the game data is not in the repository, so the order was not
checked. When that map ends, `SV_Nextserver` queues the text as the player's. The only player
action is starting the game. Aliases are not archived, so the alias path has no such case.

Apart from that path, no gated command was found that a server's alias or `nextdemo` reaches
with no player action. The search: every `Cbuf_AddText` and `Cbuf_InsertText` of a fixed command
in `src/client`, `src/common`, `src/server` and `src/backends`, and every reader of `nextdemo` and
`nextserver`.

## The tests

`tests/unit/test_cbuf_defer.c`, with the real `cmdparser.c` and `sv_init.c`. Each case runs in a
forked child, since `SV_Map` rebuilds the server state. The map change uses a picture level, so
`SV_SpawnServer` needs no BSP, and a game module that spawns nothing; the test then calls
`Cbuf_CopyToDefer` and `Cbuf_InsertFromDefer` as the `ss_game` branch and `SV_Begin_f` do.

| Test | What it shows | On FIX113's head |
| --- | --- | --- |
| `cbuf_demo_text_dropped_by_local_game` | a demo's text does not reach a game that is not a demo; the player's runs | red |
| `cbuf_demo_text_kept_by_next_demo` | a demo followed by a demo keeps it | green (unchanged behaviour) |
| `cbuf_local_text_kept_by_map_change` | a local game's map change keeps it (the map change exception) | green (unchanged behaviour) |
| `cbuf_copy_to_defer_full_buffer` | the defer copy of a buffer filled to the last byte stays in bounds | red under `make ASAN=1 test` |
