# FIX115: the gate's invariants in CI, required checks, and skips that must not pass

Review findings AR-01 and AR-02 ([the 2026-11-17 review](../reviews/2026-11-17-fork-window.md)):
CI ran the build, the unit tests, `tests/check-static-modules.sh --full`, `tests/check-ios.sh`
and coverage, but none of the other `tests/check-*.sh`, so those invariants held only on the host
that ran the gate; `main-protect` required no status check; and a check whose host tool was
missing printed a skip line and passed, so a green run covered only what the host happened to have.

## What changed

- **`invariants_macos`**, a new job of `.github/workflows/macos.yml` on the free standard
  `macos-latest` runner. It checks out the full history (`fetch-depth: 0`:
  `tests/check-cvar-docs.sh` reads the upstream base commit and fails on a shallow clone), with
  `persist-credentials: false`, and runs
  `scripts/ci-checks.sh`: every check named in `tests/ci-checks.txt`, through
  `scripts/gate-checks.sh`, the scheduler the gate uses, two at a time. No new action and no new
  pin: it reuses the build job's `actions/checkout` pin. `tests/check-ios.sh` moved from the build
  job into it, so it runs once.
- **`tests/ci-local-only.txt`**: the checks that run on the build host's gate only, one
  `name: reason` per line (below).
- **A `<NAME>_REQUIRE=1` for every skip** in `tests/check-*.sh` (below): set, the skip fails the
  check with a line that names the variable; unset, every check behaves as before.
- **`tests/check-ci-parity.sh`**, in the gate by the `tests/check-*.sh` glob and in CI through the
  list. It fails when a check is in neither list (or in both, or a list names no check, or a
  local-only entry has no reason, or a line of either list holds a carriage return, or a line of
  `tests/ci-checks.txt` is more than one name), when `scripts/ci-checks.sh --list` reads other
  names from `tests/ci-checks.txt` than it does, when a skip line is neither guarded nor in
  `tests/ci-skip-allow.txt`, and when the workflow is not as below.
  - **The workflow** is parsed by ruby's yaml, as `tests/check-workflow-pins.sh` parses it, so a
    key counts in any quoting (`"if"`, `'continue-on-error'`). Exactly one step's `run`, stripped,
    is `scripts/ci-checks.sh` alone (a run that names it with more, `|| true`, an env prefix or a
    comment, is refused); neither that step nor its job has an `if` or `continue-on-error` key;
    every `actions/checkout` step of the job has `fetch-depth: 0` and `persist-credentials:
    false`; and `CHECK_IOS_REQUIRE` is `1` in the step's `env` or, when the step does not set it,
    the job's. No ruby, a ruby without yaml or a file it cannot parse fails the check.
  - **The skip lint checks the shape of the guards, not that they work.** It reads the shell with
    a small reader of its own (quotes, comments, here-documents, separators), not a shell parser.
    That a skip fails under its `<NAME>_REQUIRE=1` is shown only by a forced-skip run: the check
    run with the tool it needs missing and the variable set (see [Forced-skip runs](#forced-skip-runs)).
  - A skip line is a command line, not a comment and not in a here-document (a `<<WORD` outside
    quotes and comments; one never closed is refused, as is a quote never closed), that prints
    text holding `skip` in any case through `echo`, `printf` or a function of the file that prints
    its arguments, with any redirection first (`>&2 echo`), to the terminal (`>/dev/stderr`,
    `>/dev/tty` and `>&N` are the terminal; a file or a pipe is not), and is not a failure. A
    failure, on that line or the next, is an `exit` or `return` with a literal status 1 to 9, or a
    `fail*=` of a literal non-zero number, not behind a `&&` or `||`: `exit $var`, `fail=0`,
    `fails=0` and `[ ... ] || exit 1` are not.
  - It is guarded when a `[` or `test` on that line or above it in the same branch reads a
    `<NAME>_REQUIRE` variable as an expansion (`${X_REQUIRE` or `$X_REQUIRE`; the name inside a
    message string does not count) and gates a branch that fails: the command after its `||` or
    `&&`, the `{ }` group there, or the `then` branch of its `if` holds, on its own level, a
    failure as above or a call to a function of the file whose body holds one. A guard that only
    prints (`|| echo required`), a bare `exit`, an inverted guard (`= 1 ] && <skip>`, a skip in
    the `then` branch) and a helper that only counts (`check-bench.sh`'s `bad`: a sub-test fails
    by its status, so `|| bad` and then `return 0` passed) are refused.
  - An allow-list entry matches exactly one line of its check: one that matches none (stale) or
    two or more is refused.
  - **What the lint does not see:** a message held in a variable (`msg=skipped; echo "$msg"`), text
    printed by `cat` from a here-document, a skip piped to another command, a helper that prints
    through another helper, and a guard that names a variable CI never sets.
  - Its self-test refuses 49 mutants on scratch copies (never the real tree) and accepts a guarded
    skip and a single-line allow-list entry. The lists: an unlisted check, a local-only entry with
    no reason, a name in both lists, a `name: reason` line and a carriage return in
    `tests/ci-checks.txt`. The skips: the two round-1 skips, the round-2 review's five (no `exit 0`
    after it, an unrelated `OTHER_REQUIRE=0` two lines above, `>&2 echo`, a `say` helper, a `:`
    line before the `exit 0`), a `_REQUIRE` only inside the message, a guard in a branch closed
    before the skip, an unclosed quote, a stale and a reasonless allow-list entry; and from round
    3 a `<<EOF` inside a string and in a comment (each followed by an unguarded skip), a
    here-document never closed, round 1's `|| bad` then `return 0` in a `check-bench.sh`-like
    sub-test, `|| echo required`, `|| { echo; exit; }`, an inverted guard in an `if` and after
    `&&`, a skip followed by `exit $rc`, `fail=0`, `fails=0` or `[ -n "$x" ] || exit 1`, a skip to
    `>/dev/stderr`, `> /dev/tty` and `>&3`, and an allow-list entry that matches two lines. The
    workflow: no `fetch-depth: 0`, `fetch-depth: 0` on another step, no `CHECK_IOS_REQUIRE`,
    `CHECK_IOS_REQUIRE` on another step, no job running `scripts/ci-checks.sh`, a job-level and a
    step-level `if:` and `continue-on-error:`, and from round 3 `"if": false` on the job and on the
    step, `'continue-on-error': true` on the step, `scripts/ci-checks.sh || true`,
    `true # scripts/ci-checks.sh`, `CHECK_IOS_REQUIRE=0 scripts/ci-checks.sh` and no
    `persist-credentials: false`. 22 of round 3's 23 passed round 2's reader (`>&3` did not).
- **`tests/ci-skip-allow.txt`**: the intended skips that need no variable (below), one
  `<check>|<text>|<reason>` per line.
- **The build host's gate** (`scripts/test.sh`) sets `CHECK_REF_METAL_REQUIRE=1` and
  `CHECK_METAL_SHIM_REQUIRE=1` on macOS when `xcrun -f metal` finds the Metal compiler (the test
  both checks use), unless the environment names them already; a host without it still runs both
  checks, with the build skipped and said.
- **`.github/rulesets/main-protect.json`** requires the status checks `build_macos_aarch64 (macos)`
  and `invariants_macos` from GitHub Actions (app id 15368, read from the check runs of a main
  commit).

## Forced-skip runs

The skip lint checks the shape of each guard. That a guard turns its skip into a failure is a
property of the check as it runs, shown by a forced-skip run: the check run with the tool or
platform it needs missing and its `<NAME>_REQUIRE=1` set, which must fail with the line that names
the variable. Record each such run here, with the check, the variable, how the skip was forced and
the failure line.

The runs below were made on commit `4544f38c`, in one `heavy.sh` hold on an Apple M6. Each check was run with its skip forced and its variable set. A forced skip is a stub ahead of `PATH` (a `uname` printing Linux, an `xcrun` refusing one SDK or tool, a `script` that exits 1, a `git` that fails `cat-file`), a `PATH` without the tool, or a `TMPDIR` inside a scratch git repository. A `wants pass` row is the same forced run with the variable unset.

Round 3 (`f44dc13c`) changed one guard, `check-bench.sh`'s `t_lock_stop` TTY guard. It went from `bad` alone to `{ bad ...; return 1; }`, which is the same failing effect. A committed test that repeats these runs is FIX136.

## The local-only checks

- `check-no-local-identity.sh`: it guards the names of the host that commits. On the runner the
  user name is `runner`, a word the tracked text uses in prose, so it would fail there on words
  that name no host.
- `check-identity-env.sh`: **unverified on runner**; it runs the identity check and the hooks with
  the host's real user and host names beside made-up ones.
